# I18n

Ankole keeps server and browser text in the same TOML files. `Ankole.I18n`
provides translations to server code.

## Where Translations Live

The shared catalogs are:

- `app/locales/en-US.toml`
- `app/locales/zh-Hans-CN.toml`

The file name without `.toml` is the locale ID. Ankole stores locale IDs as strings and does not create runtime atoms.

Catalogs ship with the application. Operators cannot edit them through
AppConfigure.

The repository has no separate client catalog directory. The browser build imports the two shared TOML files directly.

## How Ankole Selects the Default Locale

I18n owns the AppConfigure key `i18n.default_locale`. The key has a plaintext string value and the `en-US` default.

The definition permits Agent scope, but `Ankole.I18n.Config.put_default_locale/1` writes the global value.

AppConfigure checks that the value is not empty. I18n also requires a loaded
catalog with that ID.

`Ankole.I18n.put_default_locale/1` checks, stores, and applies the locale.
A direct AppConfigure write does not reload I18n.

The catalog directory is bootstrap configuration. The default path resolves from `../locales` in `app/control_plane`.

Set `config :ankole, :i18n, locales_dir: ...` when a release uses a different path.

## How the Server Loads Catalogs

OTP supervises the `Ankole.I18n.Catalog` GenServer. It starts after the AppConfigure cache.

At startup, the catalog:

1. registers `i18n.default_locale`
2. reads each `*.toml` file
3. validates the configured default locale
4. updates the Localize locale set and default
5. stores normalized messages in `:persistent_term`

`reload/0` reapplies the AppConfigure default. It does not read catalog files.

`reload_locales/0` reads the files again and then reapplies the default. It also
removes a runtime catalog when its file no longer exists.

## TOML Format

A locale file can include this metadata:

```toml
[__meta__]
bcp47 = "zh-Hans-CN"
fallback = "en-US"
revision = "optional-revision"
```

Nested TOML tables become dotted translation keys. Each string contains one MF2
message.

A rich leaf uses this shape:

```toml
[example.cta]
__mf2__ = true
message = "Open {#strong}Ankole{/strong}"
description = "Optional translator note"
```

The runtime reads only `message`. Translators use the descriptions and
placeholder details.

The loader rejects unsupported leaves, unknown rich-leaf fields, duplicate keys, and invalid MF2 messages.

## What Happens When a Translation Is Missing

I18n tries these catalogs in order:

1. the requested locale
2. the requested catalog's `__meta__.fallback`
3. the application default locale
4. `en-US`

I18n uses only complete locale tags with loaded catalogs. It does not remove
BCP 47 subtags to invent a parent locale.

The resolver caches fallback chains in `:persistent_term`. A catalog or default-locale change clears this cache.

## Server Functions

`Ankole.I18n.t/3` returns translated text. On failure, it logs the error and
shows the key or raw MF2 source.

`Ankole.I18n.translate/3` returns success or an error. Use it when the caller
must not send fallback text to an external system.

The I18n API also provides:

- `default_locale/0` and `configured_default_locale/0`
- `put_default_locale/1`
- `get_locale/0`, `put_locale/1`, and `with_locale/2`
- `reload/0` and `reload_locales/0`
- `available_locales/0`
- `locale_id/1`
- `apply_scope/2` and `locale_from_opts/1`

`put_locale/1` accepts only a loaded catalog ID. `with_locale/2` applies the same validation.

## Phoenix and Browser Use

Phoenix writes the configured locale to `<html lang>`. It uses `en-US` when AppConfigure cannot provide a locale.

The shell does not emit a `dir` attribute. The control plane has no general changeset-translation layer.

`app/webapps/common/i18n.ts` initializes i18next with the shared TOML files. It reads `<html lang>` before browser state loads.

The browser uses `en-US` as its fallback locale. Its TOML converter enforces the same rich-leaf shape.

## Check the Catalogs

Run this command from `app/control_plane`:

```sh
mix i18n.check
```

The task requires the `en-US` source catalog. It validates file shape, MF2
syntax, and extra translation keys. It also checks that each translation uses
the same external variables as the source message.

The task checks an optional client catalog directory only when that directory exists or the caller supplies `--client-dir`.

Tests cover the loader, resolver, catalog, server API, shell locale, and AppConfigure integration.

## Rules

- Catalogs do not store credentials, private data, or provider payloads.
- Locale IDs use full tags such as `en-US` and `zh-Hans-CN`.
- AppConfigure stores only the selected default locale.
- Deployment configuration selects the catalog path.
- Missing translations produce visible text and log records.
- I18n renders text. The owning subsystem makes authorization and business decisions.
