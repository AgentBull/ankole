# I18n

Ankole keeps server and browser UI strings in a single set of shared TOML
files. On the server, `Ankole.I18n` resolves translations from these catalogs;
in the browser, the frontend build imports the same TOML files directly.

## Where Translations Live

The shared locale catalogs live under `app/locales`:

- `app/locales/en-US.toml`
- `app/locales/zh-Hans-CN.toml`
- `app/locales/ja-JP.toml`
- `app/locales/ko-KR.toml`

Each filename without the `.toml` suffix is its locale ID. Ankole stores locale
IDs as strings and never converts them into runtime atoms. The repository has
no separate directory for client catalogs, and because catalogs ship with the
application release, operators cannot edit translation text through
AppConfigure.

## How Ankole Selects the Default Locale

`Ankole.I18n.Config` declares the `i18n.default_locale` AppConfigure key with
`:pod` scope, a plaintext string schema, and the release fallback `en-US`. Each
Pod stores its own default locale in `app_configurations` under
`tenant:<tenant_id>`. AppConfigure rejects `global` and `agent:<uid>` reads,
writes, and deletes for `i18n.default_locale`, and resolves an unconfigured Pod
directly to `en-US`. AppConfigure also rejects empty strings, and `Ankole.I18n`
requires an exact match against a loaded catalog ID.

Pod administrators read and update their workspace's `defaultLocale` through
`Ankole.Principals.PodAdministration` (`/api/v2/pod/admin/settings`), and site
operators can inspect or edit each tenant's value in the Console's tenant
settings column. Internally, `Ankole.I18n.put_default_locale/1` validates and
stores the locale for the active tenant context, while
`Ankole.I18n.put_default_locale_in_tx/1` composes that write inside an enclosing
`Ankole.Repo` transaction before the caller refreshes the AppConfigure cache on
commit. When server code calls `Ankole.I18n` without an explicit `locale`
option, `Ankole.I18n` reads the effective locale from the current tenant
context, falling back to `en-US` when no tenant context is bound. Updating one
Pod's locale never alters the shared catalogs or affects another Pod.

The catalog directory path is a bootstrap setting that defaults to `../locales`
relative to `app/control_plane`. When a release stores catalogs elsewhere, set
`config :ankole, :i18n, locales_dir: ...`.

## How the Server Loads Catalogs

AppConfigure registers `Ankole.I18n.Config.definitions/0` at startup, and OTP
starts the supervised `Ankole.I18n.Catalog` GenServer after the AppConfigure
cache is ready. During startup, `Ankole.I18n.Catalog` runs four steps in order:

1. Reads each `*.toml` catalog file from the configured directory and removes
   any absent runtime catalog.
2. Synchronizes Localize's supported locale set with the loaded catalogs and
   stores normalized messages in `:persistent_term`.
3. Validates the release fallback locale (`en-US`) against the loaded catalogs.
4. Publishes the release fallback locale to Localize and clears cached lookup
   chains.

At runtime, `Ankole.I18n.Catalog` exposes two reload functions. `reload/0`
re-validates and applies the release fallback locale against the loaded catalog
set without re-reading catalog files from disk. `reload_locales/0` reads the
`.toml` files again, removes any runtime catalog whose file is absent from disk,
and then reapplies the release fallback locale.

## TOML Format

A locale file can declare file-level metadata in a `[__meta__]` table:

```toml
[__meta__]
bcp47 = "zh-Hans-CN"
fallback = "en-US"
revision = "optional-revision"
```

Nested TOML tables flatten into dotted translation keys, and each string value
contains one MF2 message. When a message needs translator context, authors can
write a rich-leaf table instead of a bare string:

```toml
[example.cta]
__mf2__ = true
message = "Open {#strong}Ankole{/strong}"
description = "Optional translator note"
```

At runtime, the loader reads only `message`, while translators use the
descriptions and placeholder details. The loader rejects unsupported leaf
values, unknown fields in a rich-leaf table, duplicate keys, and invalid MF2
messages.

## What Happens When a Translation Is Missing

When looking up a key, I18n checks these catalogs in order:

1. The requested locale
2. The `fallback` locale declared in the requested catalog's `[__meta__]`
3. The Localize release fallback locale
4. `en-US`

I18n matches only complete locale tags that correspond to loaded catalogs; it
never strips BCP 47 subtags to synthesize a parent locale. The resolver caches
these fallback chains in `:persistent_term`, and I18n clears that cache
whenever catalogs reload.

## Server Functions

`Ankole.I18n.t/3` formats and returns translated text. If formatting or lookup
fails, it logs the error and returns the translation key or raw MF2 source so
the UI still shows visible text.

Alongside `t/3`, `Ankole.I18n` provides:

- `default_locale/0` and `configured_default_locale/0`
- `validate_locale/1`
- `put_default_locale/1` and `put_default_locale_in_tx/1`
- `available_locales/0` and `negotiate_locale/1`

`Ankole.I18n.Catalog` manages runtime reloads: `reload/0` reapplies the release
fallback locale, and `reload_locales/0` re-reads the locale files from disk
first.

Callers can pass `locale: "zh-Hans-CN"` to translate into a specific locale for
one call. The API has no separate per-process locale override; instead, it
resolves the implicit default from the current tenant context.

## Phoenix and Browser Use

`AnkoleWeb.SpaController` selects each HTML shell's language from its purpose.
Pod workspace entries use the controller's bound Pod, and Pod sign-in and
invitation pages use their login target or Pod host. Setup, the site Console,
and Console sign-in use the privileged Pod (and editing the privileged Pod's
`i18n.default_locale` in Console Settings updates the active Console UI
immediately, while inspecting or editing another data tenant leaves the Console
language aligned with the privileged Pod). These shells write the Pod's
`i18n.default_locale` into `<html lang>` and preload the matching locale asset,
falling back to `en-US` if AppConfigure cannot provide a locale.

Tenant-less public account and sign-out shells negotiate `Accept-Language`
against the loaded catalogs via `Ankole.I18n.negotiate_locale/1` and fall back
to `en-US`. The HTML shell does not emit a `dir` attribute, and the control
plane has no general layer for translating changesets.

In the browser, `app/webapps/common/i18n.ts` reads `<html lang>` before client
state loads and initializes i18next from the shared TOML files. The browser
uses `en-US` as its fallback locale, and its TOML converter enforces the same
rich-leaf table rules as the server loader.

In the Pod, the host passes the `pod.editor` catalog slice to `BlockEditor`
through its `labels` prop. `BlockEditor` reads this `PhraseSet` for menus,
toolbars, accessible names, link validation messages, and empty-page prompts.
When the user switches locales, the Pod updates those labels in place without
replacing the editor instance, document, selection, or undo history. For hosts
that supply no `labels` prop, the editor package falls back to its built-in
Chinese defaults. Document parser errors and warning codes keep their specified
form and are not localized.

Application fonts do not depend on a public font service. The UI package
bundles its Plex Sans and Mono fonts and falls back to system fonts, including
for serif text, so selecting a locale never triggers an external font request.
Website font policy is separate from the application.

## Check the Catalogs

To validate the translation catalogs, run this command from
`app/control_plane`:

```sh
mix i18n.check
```

`mix i18n.check` requires the `en-US` source catalog and validates file
structure, MF2 syntax, and unexpected extra keys across locales. It also
verifies that every translated message references the exact same external
variables as its `en-US` source message. If an optional client catalog
directory exists—or if you pass `--client-dir`—the task checks that directory
as well. Automated tests cover the loader, resolver, catalog server, server
API, HTML shell locale, and AppConfigure integration.

## Rules

- Do not store credentials, private data, or provider payloads in translation catalogs.
- Use full locale tags such as `en-US` and `zh-Hans-CN` for all locale IDs.
- Store only the selected default locale in AppConfigure, and set the catalog directory path through deployment configuration.
- When a translation is missing or fails to format, log the error and return visible fallback text.
- Keep authorization and business logic in the owning subsystem; I18n only formats text.
