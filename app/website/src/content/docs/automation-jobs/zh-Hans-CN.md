Cron 定时计划、Checkback 延迟回查与 Webhook 端点这三类触发器，默认都会直接唤醒一个 Agent 会话。Automation Job 则提供了第二种承接方式：由 Agent 编写一段确定性脚本并保存在自己的云盘中；将触发器绑定到该脚本后，每当时间到达或收到外部事件时，系统会直接运行这段脚本，而不必每次都启动一轮大模型推理。

至于什么情况才值得打扰你，完全由脚本按规则把关：若一切正常，脚本可直接静默退出；若发现需要关注的异常或变化，脚本只需调用 `emitEvent` 将事件发回归属会话，唤醒 Agent 带着整理好的现场数据接手处理。这样一来，高频的机械巡检全部由轻量代码值守，大模型只用在真正需要语义判断的关键节点上。

## 适合与不适合

凡是处理过程可以归纳为确定性的数据拉取、阈值比较、格式解析或预设规则动作的场景，都非常适合交给 Automation Job。典型例子如盯盘巡检：每 5 分钟拉取一次标的价格，只要价格高于阈值就直接结束；一旦跌破阈值，脚本便上报最新价格唤醒 Agent 复核上下文并向你发出提醒。如此一来，日常每次巡检的开销仅是一次极轻量的脚本运行，而非一轮完整的模型调用。

反之，如果每次触发都离不开历史记忆、综合权衡或多轮对话，就应保持让触发器直接唤醒 Agent。这两种方式随时可以互换：初期不妨先直接唤醒 Agent 跑通流程，等确认其中哪些步骤纯属机械劳动后再沉淀为脚本；日后需求变化时也可随时切回。

## 直接让 Agent 创建

你无需手动进 Console 配置，直接在聊天中向 Agent 交代清楚检查对象、触发条件、静默规则与汇报要求即可：

```text
帮我盯住 7709 的价格：每 5 分钟查一次，跌破 3.5 再提醒我，
其余时间保持安静。收盘后汇报一次当天的检查是否正常。
```

收到指令后，Agent 会在本地工作区编写脚本并先行手动测试验证，确认无误后将其注册为 Automation Job，接着创建 Cron 定时计划绑定到该脚本，最后再补设一个收盘后的对账 Checkback。注册时，脚本目录会被完整上传至该 Agent 的控制面云盘。此后每次触发运行，系统都会把触发时刻云盘目录中的内容复制到一个全新的临时运行目录中执行——因此脚本在运行目录旁临时写入的本地文件不会留存到下一次运行。后续如需修改逻辑，Agent 只需将改好的代码覆盖回云盘同一目录即可生效，无需重新注册。

## 运行记录与失败处理

每一次脚本触发都会留下一条完整的运行记录，包含起止时间、执行状态、退出码（exit code）、报错信息与有界输出日志。你可以随时在对话中让 Agent 查询历史运行情况，也可以打开 Console 的 **Automation Jobs** 页面查看相同的只读记录。

- **默认静默记录失败**：默认情况下，脚本报错只会记入运行历史，不会主动发消息打扰任何人。
- **按需开启失败唤醒**：创建任务时可要求 Agent 开启 `wake_on_failure`，开启后一旦脚本运行失败便会立即唤醒归属会话介入排查。
- **搭配对账巡检更稳妥**：对于长期运行的监控值守，建议额外搭配一个定期对账的 Checkback——让 Agent 每天固定醒来核查一遍运行记录，万一出现“下午两点后上游接口挂死导致巡检中断”这类静默异常，也能及时主动告警。

如果脚本自身抛出异常、返回非零退出码或执行超时，系统将其视为当次运行的最终结果，不会自动重跑，而是等待下一个调度周期自然触发。但如果是底层 Worker 容器发生故障中断，系统会重新派发当次运行——因此极端情况下可能出现两次运行重叠或事件重复上报，Agent 在编写脚本时会默认按幂等安全原则实现。

## 数据纪律

脚本通过 `emitEvent` 上报给会话的数据载荷，与外部 Webhook 推送的回执遵循同一套安全准则，一律作为不可信输入呈现给 Agent：凡涉及有实际业务后果的关键事实，Agent 都会先向外部权威数据源核实确认，再据此采取行动或向你汇报。

## 收尾

不再需要某项值守任务时，请让 Agent **先取消指向该脚本的 Cron、Checkback 或 Webhook 端点，最后再取消 Automation Job 本身**——如果先取消了 Job 而未解绑触发器，后续触发器继续打过来时会留下一条失败运行记录。没有任何触发器绑定的 Automation Job 不会产生任何运行开销，留在列表中仅占一行静态记录。
