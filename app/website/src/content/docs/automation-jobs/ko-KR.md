Cron, Checkback, webhook 엔드포인트 세 가지 트리거는 기본적으로 모두 Agent 대화를 직접 깨웁니다. 여기에 연결할 수 있는 두 번째 소비자가 바로 automation job입니다. automation job은 Agent가 직접 작성해 자신의 드라이브에 저장해 두는 결정적(deterministic) 스크립트로서, 트리거를 이 스크립트에 바인딩하면 발동 시점에 모델 턴을 여는 대신 스크립트만 가볍게 실행합니다.

어떤 상황이 사용자의 주의를 끌 만한지는 스크립트 코드가 일차적으로 걸러냅니다. 별다른 이상이 없으면 조용히 종료하고, 조치가 필요할 때만 `emitEvent`를 호출해 소유자 대화로 이벤트를 올려 보냅니다. 그러면 Agent는 스크립트가 추려 놓은 핵심 컨텍스트를 받아 깨어납니다. 반복적인 상태 감시는 코드가 맡고, 모델은 실제 판단이 필요한 순간에만 개입하는 구조입니다.

## 언제 적합한가

데이터 조회, 수치 비교, 응답 파싱처럼 절차와 기준이 명확히 정해진 점검 작업은 automation job에 맡기세요. 대표적인 예로 5분마다 특정 시세를 조회해 기준선 이상일 때는 조용히 종료하고 기준선 아래로 내려갔을 때만 현재 가격을 이벤트로 발행하도록 구성할 수 있습니다. 그러면 조건이 충족된 순간에만 Agent가 깨어나 데이터를 재검증하고 사용자에게 알림을 보냅니다. 평상시 매 5분 점검에는 모델 추론 비용 대신 가벼운 스크립트 실행 비용만 듭니다.

반대로 매 실행마다 장기 기억을 조회하거나 맥락을 해석해 대화를 작성해야 하는 작업이라면 Agent를 직접 깨우는 기본 방식을 유지하세요. 처음에는 직접 깨우기로 운영하다가 처리 절차가 정형화되면 스크립트로 분리하고, 필요하면 언제든 다시 직접 깨우기로 되돌릴 수도 있습니다.

## Agent에게 생성 요청

별도로 Console 화면을 조작할 필요 없이 채팅창에서 감시할 대상과 조건, 알림 기준을 자연어로 지시하면 됩니다.

```text
Watch the price of 7709 for me: check every 5 minutes and alert me
only when it drops below 3.5. Stay silent otherwise. After market
close, report once whether the day's checks ran normally.
```

요청을 받은 Agent는 작업 공간에서 스크립트를 작성해 직접 테스트한 뒤 automation job으로 등록하고, 여기에 연결된 5분 주기 Cron과 장 마감 후 일일 점검 결과를 요약할 정산용 Checkback까지 함께 설정합니다. 등록 시 스크립트 디렉터리는 Agent 드라이브로 복사되며, 매번 실행될 때마다 드라이브 폴더의 내용을 새로운 임시 실행 디렉터리로 복사해 실행하므로 스크립트가 실행 도중 로컬 경로에 생성한 파일은 다음 실행으로 이어지지 않습니다. 나중에 로직을 수정할 때도 재등록할 필요 없이 Agent가 수정된 파일을 같은 드라이브 폴더에 덮어쓰기만 하면 됩니다.

## 실행 기록과 실패

매 실행이 끝날 때마다 시작·종료 시각, 상태, 종료 코드, 오류 내역, 길이 제한이 적용된 실행 로그가 기록으로 남습니다. Agent가 대화 중에 이 실행 이력을 직접 조회할 수 있으며, Console의 **Automation Jobs** 페이지에서도 동일한 읽기 전용 보기를 확인할 수 있습니다.

- 기본적으로 실행이 실패하더라도 실패 기록만 남을 뿐 대화방을 자동으로 깨우지는 않습니다.
- 생성할 때 Agent에게 `wake_on_failure` 옵션을 켜 달라고 요청하면 실행이 실패할 때마다 소유자 대화가 즉시 깨어납니다.
- 장기간 돌아가는 감시 작업에는 정산용 Checkback이나 일일 점검 스케줄을 함께 묶어 두는 것이 좋습니다. 정해진 시각에 Agent가 깨어나 실행 이력을 훑어보고 “14:00 이후 점검 스크립트가 계속 실패하고 있습니다”처럼 조용히 누적된 장애를 사용자에게 명확히 보고할 수 있습니다.

스크립트 내부의 예외 발생(`throw`), `0`이 아닌 종료 코드, 실행 타임아웃은 스크립트 자체의 실행 결과로 간주되므로 시스템이 자동으로 재시도하지 않으며 다음 주기가 도래할 때 새 실행이 시작됩니다. 반면 Worker 인프라 자체가 중단된 경우에는 컨트롤 플레인이 해당 실행을 다시 배정하므로 실행이 겹치거나 이벤트가 중복 전달될 수 있습니다. 이에 대비해 Agent는 여러 번 실행되어도 부작용이 없도록 스크립트를 작성합니다.

## 데이터 규율

스크립트가 `emitEvent`로 올려 보낸 payload는 웹훅 수신 데이터와 마찬가지로 신뢰할 수 없는 외부 입력으로 취급됩니다. 따라서 Agent는 중요한 사실에 근거해 행동을 취하거나 사용자에게 보고하기 전에 반드시 신뢰할 수 있는 원본 출처에서 값을 다시 검증합니다.

## 정리

감시를 종료하려면 먼저 해당 스크립트를 가리키는 Cron, Checkback, 또는 webhook 엔드포인트부터 취소한 뒤 마지막으로 automation job을 취소하세요. 이미 취소된 job을 향해 남아 있던 트리거가 발동하면 실패한 실행으로 기록됩니다. 연결된 트리거가 하나도 없는 job은 아무런 실행 비용도 발생시키지 않으며 목록에 기록 행 하나로만 남습니다.

트리거 구성 방법은 [Schedules](../schedules/)와 [Webhook delegations](../webhook-delegations/)를, 실무 활용 패턴은 [Automation blueprints](../automation-blueprints/)를, 스크립트 SDK 및 명령줄 상세 규약은 [Worker CLI capabilities](../cli-capabilities/)를 참조하세요.
