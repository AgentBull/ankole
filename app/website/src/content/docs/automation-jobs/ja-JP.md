Cron、Checkback、webhook エンドポイントの 3 つのトリガーは、既定では発火時にそのまま Agent の会話を起動します。これに対する 2 つ目の受け皿が **Automation Job** です。Agent 自身が作成して専用ドライブに保存する決定論的なスクリプトであり、トリガーを紐付けると、発火時にモデルの Turn を開始する代わりにスクリプトが実行されます。

人間の注意を引くべき状況かどうかはスクリプト側で判定します。異常がなければ何もせず静かに終了し、対応が必要な変化を検知したときだけ `emitEvent` を呼んでオーナーの会話へイベントを送ります。これにより、スクリプトが集めた正確なコンテキストを渡した状態で Agent を起動できるため、定型的な監視はコードに任せ、モデルは本当に判断が必要な場面だけに集中できます。

## 向いている場合

データの取得、数値の比較、レスポンスのパース、あらかじめ決まった定型アクションなど、手順が完全に決まっている処理は automation job に向いています。典型的な例は「5 分ごとに価格を確認し、しきい値以上の間は何もせず終了し、下回ったときだけ現在価格をイベント発火して Agent に検証・通知させる」といった監視です。毎回のチェックにかかるコストを「モデルの Turn 1 回分」から「軽量なスクリプト実行 1 回分」に抑えられます。

一方、発火のたびに記憶の参照や文脈判断、人間とのやり取りが必要な作業では、従来どおり Agent を直接起動する構成（direct wake）を使ってください。なお、この選択は後からいつでも切り替えられます。最初は Agent の直接起動で運用を始め、手順が定型化できた段階でスクリプトへ移行し、必要になればまた直接起動に戻すことも可能です。

## Agent に作成を依頼する

Console での手作業は必要ありません。チャットで「何をチェックしたいか」「どの条件で知らせてほしいか」「いつ動作確認の報告がほしいか」をそのまま伝えるだけです。

```text
Watch the price of 7709 for me: check every 5 minutes and alert me
only when it drops below 3.5. Stay silent otherwise. After market
close, report once whether the day's checks ran normally.
```

依頼を受けると、Agent はワークスペース上でスクリプトを作成して手動テストを行い、automation job として登録したうえで、そこに紐付く Cron スケジュールと市場終了後の確認用 Checkback を設定します。登録時にはスクリプトのディレクトリ一式が Agent のドライブへコピーされます。毎回の実行時には、発火時点でそのドライブフォルダーにある内容が新しい一時実行ディレクトリへコピーされるため、実行中にスクリプトと同じ階層へ書き出したファイルは次回には残りません。スクリプトを修正したい場合は、Agent が編集後のディレクトリを同じドライブフォルダーへ書き戻すだけで反映され、再登録は不要です。

## 実行履歴と失敗

トリガーが発火するたびに、開始・終了時刻、ステータス、終了コード、エラー内容、上限付きログを含む実行レコードが保存されます。Agent は会話の中からこの履歴を参照でき、運用者も Console の **Automation Jobs** ページで同じ内容を閲覧できます。

- 既定では、スクリプト実行が失敗しても履歴に記録されるだけで、自動的に Agent が起動することはありません。
- 設定時に `wake_on_failure` を有効にしておくよう Agent に依頼すると、実行が失敗するたびにオーナーの会話が起動して通知を受け取れます。
- 長期間の継続監視では、定期的な確認用 Checkback を組み合わせるのが効果的です。予定時刻に Agent が起きて実行履歴を点検し、「14:00 以降チェックが失敗し続けています」といったサイレント障害を確実に報告できます。

例外のスロー、非ゼロの終了コード、タイムアウトはいずれもスクリプト自身の実行結果として記録され、システム側での自動リトライは行われません（次回のスケジュール発火を待ちます）。一方、Worker インスタンス自体の障害が発生した場合は実行が再ディスパッチされるため、実行の重複やイベントの二重送信が起こり得ます。そのため、Agent は再実行されても問題が起きない（冪等な）スクリプトを作成します。

## データの規律

スクリプトが `emitEvent` で送るペイロードは、外部からの webhook 受信時と同じルールに従い、「信頼できない入力（untrusted input）」として Agent に渡されます。重要な事実にもとづいてアクションを起こしたりユーザーへ回答したりする前に、Agent は信頼できる正本の情報源であらためて裏付けを取ります。

## 終了

監視を終了するときは、まずそのスクリプトを参照している Cron、Checkback、または webhook エンドポイントを先にキャンセルし、そのあとで automation job 本体をキャンセルします。先に job だけをキャンセルすると、残っているトリガーが発火した際に失敗レコードとして記録されてしまいます。なお、どのトリガーからも参照されていない automation job は残しておいても実行コストはかからず、一覧上に 1 行残るだけです。

トリガーの設定については [Schedules](../schedules/) と [Webhook delegations](../webhook-delegations/)、実践的な構成パターンについては [Automation blueprints](../automation-blueprints/)、スクリプト・SDK・CLI コマンドの詳細な仕様については [Worker CLI capabilities](../cli-capabilities/) を参照してください。
