同じデプロイの PostgreSQL、ファイルストア、永続 Agent Home、元の秘密情報を一緒に復元します。対象データと整合性のある取得手順は[バックアップガイド](../backup-and-restore/)を参照してください。

## 復旧前

旧 control plane と Worker が復元後の Home に書き込めないことを確認します。通信断だけでは停止の証明になりません。一時停止中のインスタンスや結果不明の作成要求も対象です。未確定 generation と認証情報を PostgreSQL に保持し、プラットフォームが確定結果を返すまで同じ generation を使います。

演習では隔離したプラットフォームリソースを使います。本番 provider の配置を持つデータベースのコピーは、本番インスタンスを操作できます。provider 間やストレージ構成間の自動移行はありません。

## 復旧手順

1. control plane を停止した状態で代替インフラを準備し、provider の配置と永続ストレージ構成を保持します。空 volume が作成される前に Docker Home を復元します。
2. PostgreSQL、対応するファイルストア、全 Home を[バックアップとリストア](../backup-and-restore/)の順序で復元します。Agent UID、volume 名、所有者、権限を保持します。
3. secret manager から元の `ANKOLE_SECRET_BASE` を復元します。provider の秘密情報と未確定 generation の認証情報の復号に必要です。紛失した場合は別の認証情報復旧計画が必要です。provider 認証情報の再入力だけでは generation の認証情報は戻りません。
4. 他の起動情報と接続先を設定して control plane を起動し、通常の調整処理で実際のプラットフォーム状態を確認します。表示を正常にするために generation やインスタンス参照を消去しないでください。未確定結果では `starting` または `deleting` に留まり、原因は `last_error` に記録します。
5. Agent を有効にします。既知の Home ファイルとドライブファイルを読み、Background Job を再開し、実際の Turn を実行します。通信先を切り替える前に旧デプロイの停止を再確認します。

## 復旧範囲

PostgreSQL は永続作業状態、Home は workspace と Codex スレッドを復元します。SQLite キャッシュは再作成できます。バックアップ後の書き込み、プロセスメモリ、実行中のモデル要求は Home バックアップの対象外です。

Docker のホストが失われた場合、ローカル volume には外部バックアップが必要です。Cloudflare は R2 バックアップとデータベース参照の両方が必要で、強制停止は最終バックアップ後の変更を失う場合があります。[Worker](../worker-management/)の制限も確認してください。

計画的なホスト移動では、まず書き込みを止めて最後の整合バックアップを取得します。演習は隔離リソースで同じ手順とユーザーフローを検証し、復旧時点と所要時間を記録します。Home や暗号化キーを省く演習は完全復旧の証明になりません。
