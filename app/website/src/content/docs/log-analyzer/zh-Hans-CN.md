一个日志分析器 agent 读一批结构化日志、找模式（反复错误、延迟飙升、异常事件序列）、并报告要紧的——不是每行，是信号。本指南是那个 agent 的实际形态。

先把决定性的性质说清楚：agent **在噪声中找信号，不倒日志**。它读成百上千行、识别要紧的模式（新错误类型、延迟回归、特定事件飙升）、报告那些。价值在于过滤和推理，不在于读。

## 需要什么

- **绑定 `primary` profile**——跨日志的模式识别需要推理。
- **一个 signal binding** 到分析报告发帖的频道。
- **一种交付日志的方式**——Agent Home 上的文件、粘贴的批量、或通过 `web_fetch` 从日志摄入器 API 抓取。
- **一个调度（可选）**——用于周期分析，或出问题时按需。

## 工作流

1. **日志到达**——文件、粘贴批量、或从 API 抓取。
2. **agent 读取**——解析结构化 JSON 行、按事件名、严重度和时间戳分组。
3. **agent 找模式**——反复错误、延迟飙升、异常事件序列、错误率变化、自上次分析后出现的新事件类型。
4. **agent 分类**——已知问题（匹配 Brain 条目）、新问题（之前未见）、异常（一个指标越出正常范围）。
5. **agent 报告**——结构化摘要：找到什么、多少次、时间窗口、严重度、是否匹配已知问题。

## 什么是让它成为 agent 而非 grep

`grep` 找匹配模式的行。agent 推理：

- **"这个错误在过去一小时出现 47 次，但之前 24 小时零次。有东西变了。"**——grep 做不到的速率变化检测。
- **"这五个错误都追溯到同一个上游超时。根因是 provider，不是我们的代码。"**——需要读多行日志并连接它们的因果链。
- **"这和 Brain 里的已知问题（issue #123）是同一模式。指向它的修复。"**——基于召回的分类。

## 一个完整示例

设置一个每小时分析日志的 agent：

1. 绑 `primary`/`light` + `embedding`（已知问题召回）。
2. 撰写 `MISSION.md`："读每小时日志批量。找：新错误类型、错误率飙升（>2 倍前一小时）、延迟离群值。每个分类为已知（查 Brain）或新。报告：什么、多少、时间窗口、严重度、已知问题链接。不倒原始日志。"
3. 设置日志投递到 Agent Home 上的文件（或通过 `web_fetch` 从摄入器 API 抓取）。
4. 加一条每小时调度：`cron: "0 * * * *"`。
5. agent 读、找模式、分类、发摘要。

## 本指南不是什么

它不是 SIEM——agent 读日志和推理；它不做跨系统实时关联。它不是仪表盘——agent 发文本摘要；它不画图。它也不是日志摄入器的替代——agent 读摄入器收集的东西；它不自己收集日志。
