**Ankole 是一个自托管的 AgentOS，用来运行共享的 AI 同事。**一套部署，多个 agent，每个都承担真实的工作，跑在你自己的基础设施上。

出发点很简单。聊天框一次只回答一个问题；而真正的工作需要一个负责人，能够陪伴任务几小时甚至几天，读懂周围的上下文，并接受结果的检验。Ankole 给 agent 这些当家人需要的东西：身份、记忆、权限、工具、工作空间和清晰的职责范围，再让工作从它本来的发生地——聊天、webhook、定时任务、内部系统——流向 agent，而不用人把上下文一点点搬进 prompt。

[Claude Tag](https://claude.com/product/tag) 是一个好理解的公开参照：在 Slack thread 里 @ 一个 AI，让它读取共享上下文、调用组织工具，并在工作耗时较长时主动跟进。Ankole 想做的是这件事的开放版本：不限于 Slack，不限于 Claude，不限于单个 agent，也不把上下文交给某个厂商托管。

## Ankole 的不同之处

多数 AI 产品在优化“单次回答”。Ankole 优化的是“这个岗位”。

- **共享，而不是私聊。** Agent 进入团队可见的频道和 provider 上下文，多个人都能观察、引导并接手同一件事。
- **身份是运行时事实，而不是 prompt 约定。** 人和 agent 都是 Principal，带着权限授权和审计轨迹，授权在边界上强制执行，而不是去问模型。
- **长时 actor，而不是请求/响应。** 一个 session 能被唤醒、接收信号、做检查点、流出进度、休眠，并带着完整上下文恢复。
- **上下文归你所有。** 记忆、配置、凭证和审计都在你自己的基础设施里，在你自己的控制面背后，而不是某个厂商的多租户里。
- **实时控制与持久事实并存。** ZeroMQ RuntimeFabric 承载 actor 与 worker 的实时流量，PostgreSQL 仍然是回放、隔离与最终提交的来源——两者不必二选一。

## 一套 Ankole 部署提供了什么

- **多种来源，统一形态。** IM、webhook、定时提醒、内部系统以及未来的 provider 适配器，都会被归一化为统一的信号输入。
- **多个 agent。** 一套部署可以托管多个 agent，各有各的使命、访问权限、工具、记忆和对外身份。
- **Session 即 actor。** 长时执行单元是 `actor_id = {agent_id, session_id}`。上下文、工作空间状态、引导、取消和恢复都在这里交汇。
- **上下文自有。** 对话、模型回合、摘要、信号投影、决策、纠正以及未来的领域记录，全部留在你的基础设施里。
- **由部署者掌控。** 访问控制、配置、Agent Library 默认值、Control Plane Plugin 启停、actor 租约、outbox 副作用和审计，都归部署和运维 Ankole 的人所有。

## Ankole 适合什么

当一件工作有可见的结果、并且需要有人盯着时，Ankole 就有了用武之地。

- **代码 agent** 关注 issue、复现 bug、修改代码、开出 draft PR，并告诉你哪些决定还得由人来做。
- **客户成功 agent** 读取共享群聊，记下要紧的事实，更新工作状态，只在真正需要时私下升级。
- **研究 agent** 跟踪市场、政策、竞品和内部笔记，只在变化真正要紧时跟进。
- **QA agent** 推进测试积压，收集证据，把带着上下文的失败用例交给人复核。
- **运维 agent** 盯着告警，起草 runbook，在动用高风险动作前先请示。

共同点不是“回答这个问题”，而是**“守住这个岗位、用上能用的上下文、并由结果来评判”**。

## 当前状态

Ankole 是一套完整、可自托管的 AgentOS，已在生产环境运行。控制面、Agent Computer、内核和运维控制台端到端可用。公共 API 目前还没有兼容性承诺，在此之前版本之间会有破坏性变更。
