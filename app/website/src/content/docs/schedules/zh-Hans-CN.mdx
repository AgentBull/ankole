Ankole 提供两类互补的定时调度工具：

- **Cron**：按周期反复执行同一项工作，例如每天早上生成工作简报、每周汇总项目进度，或每隔 30 分钟巡检一次服务状态。
- **Checkback**：仅在指定时刻唤醒当前会话一次，适合让 Agent 暂停等待一段时间后再回来跟进后续进展。

## Cron

Cron 用于管理需要周期性重复运行的任务，既支持按固定日历时刻触发，也支持从某一基准时刻起按固定时间间隔循环运行。

### 直接让 Agent 创建

日常使用时无需打开 Console 配置界面——直接在希望接收结果的聊天会话中告诉 Agent 要做什么、何时执行以及采用哪个时区，Agent 便会自动创建好计划任务，并在每次触发后将结果发回当前会话。

```text
请创建一个计划任务：每个工作日上午 9 点整理昨天的工作进展、
当前阻塞和今天要跟进的事项，并把结果发到当前会话。
时区使用 Asia/Shanghai。创建后先立即运行一次，
让我确认内容和投递位置。
```

<DocsKnowledgeNote label="💡 你知道吗？">系统会自动为每条计划任务建立并维护一条<strong>信号路由规则</strong>，借此将执行结果发回聊天渠道。</DocsKnowledgeNote>

### 高级：从控制台创建计划任务

手动在控制台创建计划任务前，请先在目标聊天窗口中与该 Agent 正常对话一次，确认对应的信号路由规则已能顺畅收发消息。

1. 打开 Console 的**计划任务**页面。
2. 选择目标 Agent 及希望延续的会话；若下拉列表中未显示目标会话，可直接粘贴已知的会话 ID。
3. 切换到 **Cron** 标签页，点击**新建计划任务**。
4. 选择用于回传结果的路由规则，并填写便于辨识的任务名称。
5. 选择调度类型并设置执行时间。
6. 填写目标投递渠道；如需固定回复到特定话题或消息线程下，请一并填写投递线程 ID。
7. 保存后点击**立即运行**先行实测一次，确认任务内容与消息投递位置均准确无误后，再交由系统按计划自动调度。

### 选择时间规则

**Cron（表达式）** 适合具有明确日历语义的排期（例如每个工作日上午 9 点），支持标准的 5 字段表达式或带秒位的 6 字段表达式。

时区请务必填写标准 IANA 时区名称（如 `Asia/Shanghai`），切勿使用 `UTC+8` 这类容易引起夏令时或解析歧义的偏移量写法。

```text
0 9 * * 1-5
```

上例代表每周一至周五上午 9 点整触发。系统严格按照该计划任务自身配置的时区换算触发时刻，不受操作者浏览器时区或 Worker 宿主机系统时区的影响。

**间隔（周期）** 则适合“每隔固定时长巡检一次”的场景（如每 30 分钟检查一次），间隔时长以毫秒为单位填写，并由锚点时间决定首个周期的起算点。无特定日历时刻要求的轮询任务更适合采用这种方式。

### 任务内容和投递位置

由于计划任务默认唤醒既有会话，Agent 会自然继承该会话的历史上下文；因此编写任务指令时只需交代当次要执行的具体动作，无需重复交代 Agent 的角色设定、回复口吻或长期准则。

投递渠道与投递线程均对应外部聊天平台的标识符：渠道栏请填入目标会话所属的频道 ID；若希望每次汇报都归集到同一个话题串下，再补充对应的线程 ID。

首次配置完毕后，请务必点击**立即运行**验证一遍，以免等到预定时刻才发现消息投递到了错误的位置。

### 暂停、恢复和删除

- **暂停**：保留全部配置但停止按时触发，适合节假日静默或临时停用。
- **恢复**：重新启用任务，并基于当前时间重算下一次触发时刻。
- **立即运行**：立刻额外触发一次执行，不影响原有的周期排程。
- **删除**：彻底移除该计划任务；若后续仍可能重新启用，建议优先选择“暂停”。

点开任意计划任务即可查看最近的历史运行记录。排查异常时，建议先看任务是否按时触发，再顺藤摸瓜定位究竟是时间规则、Agent 推理执行还是消息投递环节出了问题。

## Checkback

Checkback 是 Agent 在处理工作途中为自己预约的一次性定时回访，例如“30 分钟后再回来确认本次部署是否成功”。到期后，系统默认唤醒原会话，让 Agent 带着之前的上下文无缝继续处理。

这一机制与 <a href="https://docs.openclaw.ai/gateway/heartbeat" target="_blank" rel="noreferrer">OpenClaw 的 heartbeat</a> 解决的是同类需求：在外部没有新消息进入时，让 Agent 能够主动回访跟进。

区别在于，传统 Heartbeat 会按固定周期无差别唤醒 Agent，每次都要调用模型去判断当前是否有事需要处理；而 Checkback 采用按需预约的推送模式——只有当 Agent 明确知道稍后需要回访时才会登记一次提醒，到点后再由系统推送唤醒事件。两次检查之间完全不会为了轮询而调用模型，既避免了无意义的空转，也大幅节省了 Token 消耗。

使用时，只需在对话中自然说明多久之后回来、检查什么内容，以及遇到哪些情况需要发消息通知你。例如：

```text
30 分钟后回来检查这次部署是否完成。
如果失败、遇到阻塞或状态发生变化，请告诉我；没有变化就保持静默。
```

打开 Console 的 **Checkbacks** 标签页，可以查看当前会话下所有尚未到期的待触发回访，核对预计触发时间、预约原因与投递规则，或随时手动取消不再需要的提醒。

## 机械检查交给 Automation Job

默认情况下，Cron 与 Checkback 到期时都会写入触发事件并直接唤醒目标 Agent 会话。但如果每次触发要做的只是拉取接口、比对数值、解析字段等完全确定性的机械检查，可以让 Agent 先创建一个自动化任务（Automation Job），再将其 `automation_job_id` 绑定到定时触发器上。如此一来，到点触发时系统只会拉起一次持久化的轻量脚本运行，而不会直接启动消耗模型的 Agent 回合：一切正常时脚本可直接静默退出；一旦发现异常或需要模型介入判断，再调用 `emitEvent` 唤醒归属会话。

例如，每隔五分钟巡检一次商品价格时，可以交由脚本独立轮询：只要价格高于设定阈值便静默结束；一旦跌破阈值，再将最新价格与来源明细作为事件发送给 Agent 处理。反之，若每次触发本身就需要结合记忆、综合判断或组织自然语言对话，则保持默认直接唤醒 Agent 即可。

关于自动化任务的完整说明、运行记录与收尾契约，请参阅 [Automation Job](../automation-jobs/)；脚本 SDK 与命令行接口规范见 [Worker CLI 能力](../cli-capabilities/)。

## 常见问题

- **到期未触发**：确认任务处于启用状态，并核查 Cron 表达式、所选时区及页面显示的“下次触发”时间。
- **已触发但聊天窗口未收到消息**：先查看任务运行记录，再依次检查信号路由规则、目标投递渠道与对应 Agent 是否均处于正常可用状态。
- **触发时间固定偏差几个小时**：请改用准确的 IANA 时区名称，并核查实例的全局时区配置。
- **消息发到了错误的窗口或话题**：修正投递渠道 ID 或线程 ID，随后点击**立即运行**重新验证。
- **预约的 Checkback 没有回访**：前往 Console 的 **Checkbacks** 标签页确认该提醒未被取消，并核对到期时间与原会话的投递规则。

更多复杂故障的排查与恢复步骤，请参阅 [计划任务故障排查](../faq/)。
