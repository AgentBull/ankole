Ankole은 용도에 따라 선택할 수 있는 두 가지 스케줄링 도구를 제공합니다.

- **Cron**: 매일 아침 브리핑, 주간 프로젝트 점검, 30분 간격 상태 확인처럼 정해진 주기로 작업을 반복 실행합니다.
- **Checkback**: 일정 시간이 지난 뒤 현재 대화를 한 번 깨워 Agent가 후속 작업을 이어가게 합니다.

## Cron

Cron은 반복 실행되는 작업을 관리하며, 달력 시각 기준이나 기준 시각(anchor)으로부터의 고정 간격 기준으로 동작할 수 있습니다.

### Agent에게 만들도록 요청하기

대부분의 경우 Console을 직접 열지 않아도 됩니다. 결과를 받아 볼 채팅 대화방에서 수행할 작업, 실행 시각, 적용할 시간대를 Agent에게 바로 알려 주세요.

그러면 Agent가 스케줄을 등록하고, 이후 실행될 때마다 결과를 해당 대화방으로 전달합니다.

```text
Create a schedule for every workday at 09:00. Summarize yesterday's progress,
current blockers, and today's follow-up items, then post the result in this
conversation. Use Asia/Shanghai. Run it once now so I can confirm the content
and delivery location.
```

<DocsKnowledgeNote label="💡 알고 계셨나요?">Agent가 처리하는 Cron 규칙은 전용 Session에서 실행하고 설정한 대화로 최종 결과를 전달합니다.</DocsKnowledgeNote>

### 고급: Console에서 스케줄 만들기

Console에서 직접 스케줄을 등록하기 전에, 대상 채팅방에서 Agent와 먼저 한 번 대화를 나누어 라우팅 규칙으로 메시지 송수신이 정상 동작하는지 확인하세요.

1. Console에서 **Schedules**를 엽니다.
2. 대상 Agent와 스케줄을 관리할 Session을 선택합니다. 목록에 보이지 않으면 Session ID를 직접 입력합니다.
3. **Cron** 탭을 열고 **New schedule**을 선택합니다.
4. 결과 전달에 사용할 라우팅 규칙을 고르고 알아보기 쉬운 이름을 입력합니다.
5. 필요한 배경 정보를 포함한 작업 지시를 입력하고 스케줄 종류와 실행 주기를 선택합니다.
6. 전달할 대화를 선택하거나 Ankole의 Conversation ID를 입력합니다. 외부 채팅의 특정 topic이나 thread에 답글을 달아야 할 때만 Provider의 thread ID를 추가합니다.
7. 스케줄을 저장한 뒤 **Run now**를 눌러 정기 실행에 맡기기 전에 작업 내용과 전달 위치를 먼저 검증합니다.

### 시간 규칙 선택

**Cron(표현식)** 은 매일 09:00처럼 달력 시각에 맞춰 실행할 때 사용합니다. 5개 필드 형식이나 맨 앞에 초 필드가 붙은 6개 필드 형식을 사용할 수 있으며, 시간대는 `UTC+8`처럼 모호한 표기 대신 `Asia/Shanghai` 같은 표준 IANA 시간대 이름을 지정하세요.

```text
0 9 * * 1-5
```

위 예시는 월요일부터 금요일까지 매일 09:00에 실행하라는 뜻입니다. Console은 사용자의 브라우저나 Worker 시간대가 아니라 해당 스케줄에 저장된 시간대를 기준으로 표현식을 계산합니다.

**Every(간격)** 은 30분마다 상태 확인을 수행하는 것처럼 일정 시간 간격으로 반복할 때 사용합니다. 간격을 입력하고 초·분·시간·일 중 단위를 선택합니다. 기준 시각(anchor)을 기준으로 반복 시점이 정렬됩니다. 특정 달력 시각과 무관한 주기적 확인 작업에는 이 방식을 선택하세요.

### 작업과 전달

Agent가 처리하는 Cron 규칙은 생성한 대화와 분리된 전용 Session에서 실행됩니다. 원래 Session의 기록을 상속하지 않으므로 각 실행에 필요한 배경 정보를 포함해 작업 지시만으로 수행할 내용을 알 수 있도록 작성하세요. Agent의 기본 역할과 영구 지침은 읽어 들이므로 `AGENTS.md`나 문체 지침을 중복해서 적을 필요는 없습니다.

전달할 대화를 선택하거나 Ankole의 Conversation ID를 입력합니다. 외부 채팅에서는 해당 라우팅 규칙도 선택하고, 매번 같은 topic이나 thread에 답글을 달아야 할 때만 Provider의 thread ID를 덧붙이세요.

처음 스케줄을 만든 직후에는 반드시 **Run now**를 한 번 실행해, 작업 결과가 엉뚱한 채널에 게시되지 않는지 확인하는 것이 안전합니다.

### 일시 중지, 재개, 제거

- **Pause**: 설정을 그대로 둔 채 예약 실행만 멈춥니다. 연휴 기간이나 일시적인 중단이 필요할 때 사용하세요.
- **Resume**: 일시 중지된 스케줄을 다시 켜고 다음 실행 시각을 새로 계산합니다.
- **Run now**: 기존 스케줄 주기는 건드리지 않고 즉시 실행을 한 번 추가합니다.
- **Remove**: 스케줄을 완전히 삭제합니다. 나중에 다시 켤 계획이라면 삭제 대신 **Pause**를 사용하세요.

스케줄 상세 화면을 열면 최근 실행 이력을 볼 수 있습니다. 예상한 시점에 결과가 오지 않았다면 먼저 스케줄 자체가 트리거되었는지 확인한 뒤, Agent 실행 상태와 메시지 전달 결과를 차례로 점검하세요.

## Checkback

Checkback은 작업 도중 Agent가 직접 등록하는 일회성 지연 후속 작업입니다(예: “30분 뒤에 배포 상태를 다시 확인해 줘”). 지정한 시각이 되면 기본적으로 원래 대화를 깨우므로, Agent가 기존 맥락을 유지한 채 작업을 이어갈 수 있습니다.

Agent는 구체적인 후속 확인이 필요할 때 Checkback 하나를 예약합니다. 기한이 되면 제어면이 일회성 기동 이벤트를 전달하며, 기다리는 동안 확인용 모델 턴을 반복할 필요는 없습니다.

채팅에서 요청할 때는 언제 다시 확인할지, 무엇을 점검할지, 어떤 조건에서만 알림을 보낼지를 분명히 적어 주세요. 예시는 다음과 같습니다.

```text
Check this deployment again in 30 minutes.
Tell me if it failed, became blocked, or changed state. Stay silent if nothing changed.
```

Console의 **Checkbacks** 탭에서는 선택한 대화에 등록된 대기 중인 알림 목록을 볼 수 있습니다. 예정 기한, 등록 사유, 라우팅 규칙을 확인할 수 있으며, 더 이상 필요 없는 항목은 취소할 수 있습니다.

## Applet Job 일정

정형 처리를 Applet Action으로 게시하고 자동화 패널에서 Job과 소유 일정을 만듭니다. Agent 세션, 작업 프롬프트, 채팅 대상은 필요하지 않습니다. Cron, 고정 간격, 지정 시각 중 하나를 선택하고 시간대와 Action에 전달할 JSON을 설정합니다.

수정, 일시 중지, 재개, 즉시 실행, 삭제를 지원하며 실행 이력에서 Run 결과, 실패, 입력 병합 상태를 확인할 수 있습니다. Action은 `ctx.signal.data`와 영구 저장되는 `ctx.state`를 사용합니다. 개인 일정은 Job 소유자 권한, 팀 일정은 페이지 편집 권한을 따릅니다.

Agent가 만든 Cron과 Checkback도 소비자 연결을 통해 Applet Job에 전달할 수 있습니다. 매번 판단이나 대화가 필요하면 Agent를 소비자로 유지하세요. [Automation Jobs](../automation-jobs/)와 [Worker CLI](../cli-capabilities/)를 참고하세요.

## 흔한 문제

- **스케줄이 실행되지 않음:** 스케줄이 활성 상태인지 확인하고 Cron 표현식, 시간대, 다음 예정 실행 시각을 점검하세요.
- **실행 기록은 있는데 결과가 오지 않음:** 실행 이력을 열어 라우팅 규칙, 전달 channel, 대상 Agent가 모두 사용 가능한 상태인지 확인하세요.
- **예상보다 항상 몇 시간 빠르거나 늦게 실행됨:** 표준 IANA 시간대가 올바르게 지정되어 있는지, 그리고 인스턴스 시간대 설정이 맞는지 확인하세요.
- **결과가 다른 대화방에 올라감:** 전달할 대화 또는 Provider의 thread ID를 수정한 뒤 **Run now**로 다시 검증하세요.
- **Checkback이 실행되지 않음:** **Checkbacks** 탭에 항목이 남아 있는지 먼저 확인하고, 예정 기한과 원래 대화의 라우팅 규칙 상태를 점검하세요.

상세한 실패 진단과 복구 절차는 [Schedule troubleshooting](../faq/)을 참조하세요.
