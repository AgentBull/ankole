信号路由规则决定了外部传入的消息或业务事件应当交由哪个 Agent 处理。一条聊天路由规则负责将一个外部聊天应用绑定到指定的单个 Agent；同一个 Agent 则可以通过多条路由规则同时接入多个不同的聊天应用。

收到消息后，聊天渠道适配器会将其记录到共享对话（Conversation）中，并为目标 Agent 生成对应的信号（Signal）；此外，CloudEvents Webhook 端点也能接收外部业务系统推送的事件，并将其转化为信号投递给目标 Agent。

如果尚未在 Slack、Microsoft Teams、飞书 / Lark 或钉钉后台创建机器人应用，请先参照 [快速开始](../quickstart/#4-连接聊天渠道并创建信号路由规则) 完成平台侧接入配置。

## 创建路由规则

1. 打开 Console 的**信号路由**页面，点击**新增路由规则**。
2. 选择负责接收消息的目标 Agent 与对应的聊天渠道适配器。
3. 填写便于辨识的规则名称，例如 `support-slack`。
4. 选择群聊消息处理模式。
5. 填入该聊天应用的连接凭证与参数并保存。
6. 前往对应的聊天客户端向机器人发送一条测试消息，确认目标 Agent 能够正常回复。

建议为每个聊天机器人（Bot）账号单独创建对应的平台应用与路由规则。若希望多个 Agent 在聊天软件中各自拥有独立的机器人身份，请分别为它们注册独立应用并配置各自的路由规则——这样既便于单独轮换密钥，也能彻底避免不同 Agent 的身份与消息相互串扰。

## 选择群聊消息模式

Console 界面仅会展示当前所选聊天渠道实际支持的群聊模式：

| 模式 | 未明确 @ 提及 Agent 的群消息如何处理 |
|---|---|
| **仅处理明确提及** | Agent 既不会读取该消息，也不会作出回复。 |
| **记录未提及消息** | 消息会写入对话上下文，但不会立即唤醒 Agent；待后续有人 @ 提及 Agent 时，它可结合此前积累的群聊记录理解前因后果。 |
| **可主动介入** | Agent 会先评估当前讨论是否需要自己参与，仅在判断发言确有帮助时才主动回复。 |

Slack、Microsoft Teams 与飞书 / Lark 均完整支持以上三种模式；钉钉与企业微信受平台机制限制，仅能接收明确 @ 提及机器人的群消息，因此 Console 中只提供第一种模式。尤其需要注意，企业微信还存在无法撤回消息、群聊无法接收文件附件、机器人无法主动发起会话等诸多平台限制，不建议将其作为主力渠道；完整限制说明见 [快速开始](../quickstart/#4-连接聊天渠道并创建信号路由规则) 中的企业微信标签页。

开启“可主动介入”并不意味着机器人会逢消息必回——它只是允许 Agent 在无人点名时自行评估一次是否应当搭话，且每批新消息仅触发一次判断。若想明确约定某个群的发言时机，可直接在群里向 Agent 下达一条频道常驻指令（例如“只有 CI 构建失败变红时才出声提醒”）；如果觉得它插话过于频繁，可收紧常驻指令或角色说明；若该群只需被动一问一答，直接切回“仅处理明确提及”即可。详细的评估机制与常驻指令用法见 [群聊主动介入](../ambient-intervention/)。

## 选择未知发信人的处置

收到外部消息时，Ankole 会尝试将发信人自动映射至实例内的已知人员账号：此前已通过目录同步或单点登录导入的员工，直接按平台用户 ID 匹配；首次出现的平台账号，若平台返回了经过验证的邮箱或手机号且恰好与现有账号吻合，也会自动归并。不过这种自动映射属于尽力匹配——不在企业通讯录内的外部合作伙伴，或是仅使用邮箱验证码（Email OTP，`SiteCredential`）登录、尚未关联过聊天账号的用户，都可能无法自动匹配。

规则中的**自动映射账号失败时**选项决定了如何处置这类未识别发信人：

| 选项 | 处理行为 |
|---|---|
| **手动审核**（默认） | 发信人会进入控制台 **身份 → 待绑定账号** 待办列表。在管理员完成账号绑定前，凡是点名该 Agent 的消息只会收到一条固定提示，引导对方联系管理员完成绑定；消息正文既不会进入对话上下文，也不会被 Brain 收录学习。 |
| **自动创建独立账号** | 系统立即为该发信人自动创建一个独立账号并正常提供对话服务，适合允许外部人员自由提问的开放频道。注意，如果发信人的平台标识本身已与某个现存账号的登录标识重合（例如与某邮箱验证码 `SiteCredential` 账号或已验证的 Pod `email` 身份同名），系统既不会新建重复账号也不会擅自合并，而是转交手动审核——因为只有管理员才能核实两边是否确属同一自然人。 |

无论选择哪种方式，未知发信人在群聊中未点名 Agent 的日常闲聊都会被直接忽略。

各聊天平台的身份识别特性有所不同：
- **Telegram、Discord 与 LINE**：此类消费级通讯工具没有企业组织架构，也不向机器人提供用户邮箱或手机号，因此每位发信人初次发言时均视为未知身份。建议保持默认的**手动审核**，由管理员逐一关联至对应账号。
- **WhatsApp**：平台会提供经过验证的发信人手机号，只要实例内已有绑定该手机号的账号即可当场自动匹配。
- **电子邮件**：由于未经校验的邮件 `From` 头本身不足以证明真实身份，系统绝不会单凭未绑定的资料邮箱或 `SiteCredential` 登录邮箱放行来信；发信地址必须先建立显式的 Pod `email` 身份绑定才能接入（内部员工的绑定由目录同步或身份源登录自动生成，外部联系人的绑定则由管理员在此页面手动添加）。
- **飞书与 Lark 外部群**：跨企业互通群中的外部租户成员没有本企业的员工 ID，同样通过该页面走手动审核绑定或自动创建独立账号流程。管理员也可随时在同一页面预先绑定账号关系，例如提前把某位邮箱验证码（`SiteCredential`）用户与其个人聊天账号关联起来。

## 聊天内容如何成为 Brain 知识

信号路由规则只负责将消息分发给指定 Agent，本身不设知识可见性开关。当 Brain 从聊天记录中提炼沉淀知识时，会严格依据会话类型与已知参与人身份自动划定披露范围：

- **群聊**：提炼出的知识可供该群对应的成员权限组全体成员及相关 Agent 检索使用；若所用聊天渠道无法同步群成员权限组，Brain 则不会从该群聊天中学习任何内容。
- **私聊**：提炼出的知识仅对私聊本人及当前路由规则绑定的那个 Agent 可见，其他 Agent 默认无权读取。

在此基础上，明确属于公开常识或公司通告的事实可升级为租户内共享知识，而当事人明确要求保密的内容则可收紧为仅对发言人可见；其余常规交流均维持上述群聊或私聊默认边界。关于底层模型配置与检索逻辑，请参阅 [Brain](../brain/)。

## 编辑、停用或启用

路由规则列表默认仅展示启用中的规则；如需查阅或恢复历史规则，可勾选打开“显示已停用”。

点击某条规则的“编辑”，即可查看非敏感配置项，或更换目标 Agent、调整群聊消息模式、轮换聊天应用凭证。更改目标 Agent 保存后，后续新流入的消息将立即转交新 Agent 处理。

出于安全考虑，已保存的 Token 与 Secret 不会回传至浏览器端。编辑规则时若将凭证输入框留空，服务端会继续沿用原有的加密值；只有填入新内容时才会覆盖更新。

点击“停用”会立即中止新消息接入，但完整保留规则配置、平台应用关联与历史会话链路；日后需要恢复服务时，只需在“显示已停用”列表中找到该规则并点击“启用”，无需推倒重建。

## 排查没有回复的问题

- **新建规则时找不到目标聊天渠道**：**Control Plane Plugin** 严格属于站点级扩展（对应接口 `/api/v2/site/control-plane-plugins`），仅在全局站点维度可见，不会出现在租户级或单 Agent 级能力库中。请前往站点管理控制台（`/site-admin-console`），在 **Agent 能力库** 顶部将作用域切换为**全局默认值**，打开 **Control Plane Plugins** 标签页启用对应的渠道插件，并按提示重启控制面。
- **机器人在群里收不到消息**：核查外部平台后台的事件订阅开关、接口权限及应用发布生效状态；此外，钉钉与企业微信群聊中必须明确 `@` 提及机器人才能触发推送。
- **企业微信收发异常**：请先对照 [快速开始](../quickstart/#4-连接聊天渠道并创建信号路由规则) 中的企业微信说明排查平台侧硬性限制——常见原因包括机器人并非由超级管理员创建、未配置企业可信 IP 白名单，或用户尚未主动发消息激活会话。
- **规则保存成功但发消息无响应**：确认目标 Agent 处于启用状态、模型档案配置有效，并在路由规则列表中检查该规则本身是否处于正常启用状态。
- **私聊对答正常、群聊毫无反应**：检查当前规则所选的群聊消息模式，并确认已将机器人拉入目标群聊。

各聊天平台所需的具体权限项、订阅事件名与凭证获取方式，均以 [快速开始](../quickstart/#4-连接聊天渠道并创建信号路由规则) 中对应平台的配置步骤为准。

此外，若希望钉钉机器人采用流式打字机卡片回复，需先前往钉钉卡片平台搭建一份 AI 卡片模板，具体步骤见 [快速开始](../quickstart/#4-连接聊天渠道并创建信号路由规则) 钉钉标签页下的高级设置说明。
