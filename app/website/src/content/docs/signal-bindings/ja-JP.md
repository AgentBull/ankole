シグナルルーティングルール（`Signal Binding`）は、受信したメッセージや外部イベントをどの Agent に届けるかを決める設定であり、次の 2 つのモードをサポートします。

- **`ai_colleague` モード：** チャットアプリまたは CloudEvents ソースを特定の AI Colleague 1 体に紐付けます。1 体の AI Colleague に複数のルールを作成し、複数のチャット基盤へ同時に接続することも可能です。
- **`sender_personal_assistant` モード**（Lark / Feishu および Slack で対応、`agent_uid` は `null`）：ワークスペース全体で 1 つの共有 Personal Assistant Bot を公開し、ダイレクトメッセージ（`im_dm`）を照合済みの有効メンバー各自の Personal Assistant（初回利用時に自動作成）へルーティングします。未マッピングの送信者は **手動レビュー** で保留され、ゲストは利用できません。

チャットアダプターは受信メッセージを Conversation に記録したうえで解決先の Agent 向けに Signal を生成します。また、CloudEvents Webhook エンドポイントを使って外部システムからのイベントを受信し、Signal として配信することもできます。

Slack、Microsoft Teams、Lark、Feishu、DingTalk のアプリ設定がまだ済んでいない場合は、先に [Quick start](../quickstart/#chat-channels) の Channel Provider セットアップ手順を完了してください。

## ルーティングルールを作成する

1. Console で **Signal Routing** を開き、**New routing rule** を選択します。
2. Channel Provider アダプターとルーティングモードを選択します。特定の AI Colleague（`ai_colleague` モード）を選ぶか、Lark / Feishu・Slack で **送信者の Personal Assistant**（`sender_personal_assistant` モード）を選択します。
3. `support-slack` や `workspace-pa-lark` のように用途が分かりやすいルール名を入力します。
4. `ai_colleague` ルールではグループメッセージモードを選択します（`sender_personal_assistant` ルールはダイレクトメッセージ専用で、未登録送信者は常に **手動レビュー** となります）。
5. **Pod → Connections**（`Ankole.Connectors`）に登録済みのアプリ接続（`authConfigId`）を選択してディレクトリ同期や SSO ログインとアプリ認証情報を共有するか、認証情報を直接入力して `Ankole.Connectors` に保存し、ルールを保存します。
6. 接続したチャットアプリ上でボットにメッセージを送り、対象の Agent から返信が返ってくることを確認します。

ボットの人格ごとに専用のチャットアプリとルーティングルールを割り当ててください。複数の AI Colleague で別々のボットアカウントを使い分ける場合はボットごとに個別のチャットアプリを用意し、共有 Personal Assistant Bot にも独立したアプリを割り当てます。

このように分離しておくことで、各ボットの Identity とメッセージストリームが混ざらず、認証情報の管理も安全に行えます。

## グループメッセージモードを選択する

Console には、選択した Channel Provider が対応しているモードだけが表示されます。

| モード | Agent 宛て（メンション付き）ではないグループ発言の扱い |
|---|---|
| **Addressed messages only** | Agent は発言を受け取らず、返信も行いません。 |
| **Observe unaddressed messages** | 発言は会話コンテキストに記録されますが、その時点では Agent は起動しません。後から誰かが Agent にメンションした際、それまでのやり取りを文脈として参照できます。 |
| **May intervene** | 会話に割り込んで発言すべきかどうかを Agent 自身が判断し、有益だと判断した場合にのみ返信します。 |

Slack、Microsoft Teams、Lark、Feishu は 3 つのモードすべてに対応しています。一方、DingTalk と WeCom はボットへの明示的なメンションが付いたグループ発言しか受信できない仕様のため、Console 上でも **Addressed messages only** のみが選択できます。特に WeCom にはこれ以外にも多くのプラットフォーム制約（送信取り消し不可、グループ内でのファイル送受信不可、Agent からの会話開始不可）があるため、最初に導入するチャネルとしては推奨しません。詳しくは [Quick start](../quickstart/#chat-channels) の WeCom タブを参照してください。

なお、**May intervene** を選んでも、すべての発言に毎回反応するわけではありません。新着メッセージのバッチごとに 1 回だけ介入要否が判定され、発言すべきときだけ応答します。特定のグループで発言タイミングを細かく指示したい場合は、そのグループ内で直接チャネル常駐指示（例：「CI が赤になったときだけ発言して」）を伝えてください。それでも発言頻度が高すぎる場合は、まず常駐指示または Agent の役割定義を絞り込みます。介入判定の仕組みと常駐指示の詳細については、[アンビエント介入](../ambient-intervention/) を参照してください。

質問されたときだけ応答すれば十分なグループでは、**Addressed messages only** を選んでください。

## 不明な送信者の扱いを選択する

Ankole はまず、送信者の不変のプラットフォームユーザー ID に紐付く有効な Human Principal を照合します。この紐付けはディレクトリ同期、SSO ログイン、または管理者の操作によって作成されます。既定の **手動レビュー** では、チャットプロフィールから取得したメールアドレスや携帯電話番号だけで既存アカウントへ紐付けることはありません。メール OTP（`SiteCredential`）でログインしただけでも、チャットアカウントは紐付きません。

照合できなかった送信者への対応は、**アカウントの自動マッピングに失敗した場合** の設定で選択します。

| オプション | 動作 |
|---|---|
| **手動レビュー**（既定） | 送信者は Console の **アイデンティティ → 保留中のマッピング** に表示されます。管理者が紐付けを完了するまで、Agent 宛てのメッセージには管理者への連絡を求める定型文だけが返されます。発言内容が会話コンテキストに入ったり Brain に学習されたりすることもありません。 |
| **独立アカウントを自動作成** | アカウントを解決または作成し、その場で応答を開始します。社外からも利用できるオープンなチャネルに適しています。その Provider への初回の紐付けでは、確認済みのメールアドレスが、有効な Human 1 人のプロフィールメール、検証済みの個人ログインメール、またはディレクトリの連絡先別名と一致すれば、その Human に紐付けます。ただし、その Human に同じ Provider の紐付けがなく、オフボーディングを完了していないことが条件です。それ以外の場合は、プラットフォーム識別子を使って独立アカウントを作成します。メールの一致先が複数ある場合やアカウント識別子が使用済みの場合は受け入れられないため、管理者が明示的に紐付けてください。 |

手動レビュー待ちの送信者がグループで Agent 宛てではない通常の発言をした場合、その発言は無視されます。

Telegram、Discord、LINE、WhatsApp では、プラットフォーム ID の紐付けがない送信者は未マッピングとして扱われます。既知のユーザーだけを受け入れたい場合は **手動レビュー** を使い、各ユーザーを一度ずつ既存アカウントに紐付けてください。WhatsApp の電話番号だけで既存の Human の携帯電話番号へ自動的に紐付くことはありません。

メールチャネルは、送信元アドレスを独立した `email` 名前空間で照合します。明示的な `email` identity の紐付け、または有効な Human に登録された連絡先メールが一致すれば受け入れます。社員のメールの紐付けはディレクトリ同期や上流 Provider へのログインで作成でき、社外連絡先の紐付けは管理者がこの Console 画面で登録できます。メール OTP のログインアドレスだけでは、メールチャネルの紐付けにはなりません。Lark や Feishu の外部グループに参加する社外テナントのメンバーには社内の従業員 ID がないため、手動の紐付けか独立アカウントのポリシーを使ってください。本人が最初のメッセージを送る前に、メール OTP（`SiteCredential`）ユーザーとチャットアカウントの紐付けなどを同じ画面で登録することもできます。

## チャットの内容が Brain の知識になる仕組み

ルーティングルールはあくまでメッセージの配送先を決めるものであり、知識の公開範囲を設定するものではありません。Brain がチャットのやり取りから知識を学習する際は、会話の種別と判明している参加者の Identity から閲覧範囲（スコープ）が自動的に決まります。

- **グループチャット：** そのチャネルの現在の member group に所属しているメンバーと Agent が、学習された知識を参照できます。member group が紐付いていないグループからは学習を行いません。
- **ダイレクトメッセージ：** 対話相手のユーザー本人と、応答を担当した Agent（バインドされた AI Colleague または送信者の Personal Assistant）だけが学習された知識を参照できます。デフォルトでは他の Agent から参照することはできません。

なお、公開情報であればテナント全体で共有される知識になる場合があり、逆に発言内で明示的に機密扱いが指定された内容は発言者本人のみに制限できます。それ以外の通常の発言は、上記のグループチャットまたはダイレクトメッセージの閲覧範囲をそのまま維持します。必要なモデル設定や検索時の挙動については、[Brain](../brain/) を参照してください。

## ルールを編集、無効化、または有効化する

ルール一覧には、デフォルトで有効なルールだけが表示されます。過去に無効化したルールを確認・復元したい場合は、**無効なルールを表示** をオンにしてください。

**編集** を開くと、機密情報を除く現在の設定値を確認でき、対象の AI Colleague、グループメッセージモード、選択中の `Ankole.Connectors` 接続（`authConfigId`）、またはチャット認証情報を変更できます。`ai_colleague` ルールの対象 Agent を別の Agent に切り替えると、以降に届く新しいメッセージは切り替え先の Agent へルーティングされます。

セキュリティ保護のため、保存済みのトークンやシークレットの値がサーバーからブラウザーへ返されることはありません。認証情報欄を空欄のまま保存すれば、暗号化済みの既存値がそのまま維持されます。値を更新したいときにだけ新しい値を入力してください。

**無効化** を実行すると、ルール設定やチャットアプリとの紐付け、過去の会話履歴を残したまま、新規メッセージの配信だけを停止できます。再開したいときは **無効なルールを表示** から該当ルールを探し、**有効化** を選ぶだけで元に戻せます。ルールを一から作り直す必要はありません。

## Agent が返信しない場合

- **目的の Channel Provider が選択肢にない場合：** **Control Plane Plugins** はサイトスコープ専用（`/api/v2/site/control-plane-plugins`）であり、テナント単位や個別 Agent の Agent Library 画面ではなく、Site Admin Console のグローバルスコープでのみ表示されます。Site Admin Console（`/site-admin-console`）を開き、**Agent Library** のスコープを **グローバル既定値** に合わせたうえで **Control Plane Plugins** タブから該当プラグインを有効化し、案内に従ってコントロールプレーンを再起動してください。
- **ボットがグループメッセージを受信できない場合：** チャット基盤側のイベント購読設定、権限スコープ、アプリの公開（リリース）状態を確認してください。なお、DingTalk と WeCom のグループチャットではボットへの明示的な `@` メンションが必須です。
- **WeCom の挙動が想定と異なる場合：** まず [Quick start](../quickstart/#chat-channels) の WeCom タブにある制約一覧と照らし合わせてください。よくある原因は、ボットがスーパー管理者アカウントで作成されていない、信頼済み IP が未登録、またはユーザー側でまだボットとの会話が有効化されていない、のいずれかです。
- **ルールは保存できたのに返信がない場合：** 対象の Agent が有効になっているか、モデル設定が正常に動作するか、およびルールが有効な一覧に表示されているかを確認してください。
- **ダイレクトメッセージは動くのにグループメッセージだけ動かない場合：** グループメッセージモードの設定と、対象のグループにボットが参加しているかを確認してください。

各チャット基盤固有の権限設定、購読イベント、認証情報の取得手順については、[Quick start](../quickstart/#chat-channels) を参照してください。

なお、DingTalk ルールでストリーミングカード形式の返信を利用するには、DingTalk カードプラットフォーム上で AI カードテンプレートを 1 つ作成しておく必要があります。具体的な作成手順は、[Quick start](../quickstart/#chat-channels) の DingTalk タブ内の詳細セクションで解説しています。
