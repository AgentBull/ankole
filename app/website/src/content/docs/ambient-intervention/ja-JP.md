外部チャネルの[シグナルルーティングルール](../signal-bindings/)でグループメッセージモードを **May intervene** に設定した場合、またはネイティブの **Pod Chat** グループスレッドで参加 Agent の `may_intervene` ポリシーを有効にした場合、Agent は自分宛てのメンションがないグループメッセージも確認し、人間から届いた新着メッセージのバッチごとに処理経路を判定します。基本動作は「沈黙（何もしない）」ですが、状況に応じて短い返信を返したり、新しい作業として引き受けたり、実行中の background job に追加情報を引き継いだりできます。

このモードにおけるグループ内での振る舞いは、Conversation に保存される `standing_orders` と、グループ介入設定（外部チャネルでは Signal Binding の設定、Signal Binding を使わない Pod Chat グループスレッドでは参加 Agent ごとの `may_intervene` ポリシー）の 2 つによって制御されます。

## 各メッセージは一度だけ判断される

各 Agent は Conversation ごとに独立した「判定済みカーソル（判断進度）」を保持します。同じグループ Conversation に複数の Agent が参加している場合、メッセージ履歴と standing orders は共有されますが、どこまで判定したかの進度は Agent ごとに別管理です。また、アンビエント判定を起動するのは**人間**の発言だけであり、Agent の発言によって別の Agent が起動することはありません。各チェックでは前回の判定以降に届いた新着メッセージだけが評価対象となり、それ以前のメッセージは文脈の背景として参照されるだけで再評価はされません。そのため、一度「見送る」と判断されたメッセージに対して、数ラウンド後に突然 Agent が返信し始めるようなことはありません。

すべての判定結果は、選択されたアクション、認可の根拠（authorization source）、判断理由とともに記録されます（background job への引き継ぎ時は引き継ぎ先の対象も記録されます）。Agent の発言が控えめすぎたり積極的すぎたりする場合は、運用者がこれらの記録からどの経路が選ばれたかを確認できます。

## 4 つの処理経路

- **何もしない（`NOOP`）**: 発言せず静かに待機します。雑談や相づち、内容が重複する回答、あるいはすでに他のメンバーが対応を引き受けた話題では、通常この経路が選ばれます。
- **前景返信（`FOREGROUND_REPLY`）**: 質問への回答、確認、調整、進捗報告、またはごく小規模な調査のために、目に見える短いターンを 1 回開始します。この経路から background job を新規作成したり再開したりすることはできません。
- **新しい作業（`NEW_WORK`）**: 独立した実質的なタスクを検出した場合の経路です。人間からの直接の依頼があるか、一致する standing order がある場合にのみ、通常の owner turn へ進みます。人間を起点とするターンは **`Human ∩ Agent` の権限交差**（`interactive_principal = waking_human`）のもとで実行されるため、アクセスする各リソースに対して「きっかけを作った人間」と「Agent」の双方が権限を持っている必要があります。直接の依頼も一致する standing order もない場合、Agent は作業を引き受けるべきか尋ねるだけの確認ターンを実行します（この確認ターンではツールは使えず、ジョブも開始できません）。
- **引き継ぎ（`HANDOFF`）**: 新着メッセージを、現在稼働中の background job のうち条件が明確に一致する 1 件へ静かに転送します。対象となるのは、同じ Agent・owner Session・Conversation（外部チャネル経由の場合はさらに同じ binding）に属するジョブに限られます。候補が絞り込めない場合や曖昧な場合は引き継ぎを行いません。

なお、経路判定器（recognizer）自体が直接 background job を作成することはありません。あくまで処理経路と認可の根拠を選ぶだけであり、その後の通常の owner turn において承認ルールやバックグラウンド実行ルールが適用されます。

## 返信は質問した人に紐付く

Agent が発言すると決めた場合、返信方法は次の 2 パターンに分かれます。

- **誰かが Agent に尋ねている場合** — `@` メンションが付いていなくても、新着メッセージのいずれかが実質的に Agent への質問や呼びかけになっているケースです。この場合、返信はそのメッセージに紐付け（アンカー）されます。対応しているチャネルでは引用返信やスレッド返信として表示されるため、どの発言に対する返答なのかが一目でわかります。
- **自発的な発言** — 特定の誰かから呼びかけられたわけではないものの、今ここで情報を補足すると役に立つと判断したケース（または standing order の条件に一致したケース）です。この場合、返信は通常のグループメッセージとして投稿されます。

質問者への紐付けには厳密な検証が行われます。対象となる質問メッセージは、今回判定したバッチ内に含まれており、人間による投稿であり、かつその投稿者が依然として直近の発言者である必要があります。会話の話題がすでに次へ進んだ後で、過去の質問を掘り起こして返信することはありません（その場合は通常の自発的な返信にフォールバックします）。また、一度紐付けた質問メッセージが後からチャットプラットフォーム側で削除された場合、保存された紐付け状態は `degraded` となってアンカーが解除されますが、判定記録と判定済みカーソル自体はそのまま保持されます。

## channel standing orders

standing orders は Conversation ごとに保存される永続的なポリシーテキストで、その会話に参加するすべての Agent で共有されます。「このチャンネルではどのようなときに自発的に発言すべきか」を自然言語で指示できます。たとえば次のように指定します。

- 「CI が赤になったとき、またはデプロイが失敗したときだけ発言してください。」
- 「18:00 以降に誰かが日報を投稿したら要約してください。それ以外のときは静かにしていてください。」
- 「ここは顧客向けグループです。技術的な質問を直接受けた場合以外は発言しないでください。」

**設定はチャンネル内で Agent に話しかけるだけで行えます。** チャンネルのメンバーが「これからは、CI が赤になったときだけここで発言して」と伝えると、Agent はその内容を該当チャンネルの standing orders として保存し、依頼者も記録します。内容を更新するとテキスト全体が新しい指示で置き換えられ、「このチャンネルの standing orders をクリアして」と伝えれば削除されます。

保存された standing orders は 2 つの場面で参照されます。まず経路判定の段階ではチャンネルの運用ポリシーとして扱われ、条件が明確に一致すれば `NEW_WORK` への遷移を許可する根拠になります。さらに、その後の可視の owner turn でもコンテキストの一部として Agent に渡されます。

利用にあたっては次の 2 点に注意してください。

- **May intervene モードが有効なときにのみ機能します。** May intervene がオフの場合（外部チャネルで別の binding モードになっている場合や、Pod Chat グループスレッドで参加 Agent の `may_intervene` が無効な場合）でもテキスト自体は Conversation の `standing_orders` に保存されますが、そのままでは動作せず、Agent も保存時に「現在は非アクティブである」旨を返信します。後から May intervene を有効にすれば、追加操作なしでそのまま適用されます。
- 1 つの standing orders テキストの上限は 4,000 文字です。

Console API から standing orders を直接読み書きすることも可能です。詳しくは [Console API reference](../console-api/) の `/api/v2/conversations/:conversation_id/standing-orders` エンドポイントを参照してください。

## それでも発言しすぎる、または少なすぎる場合

- **発言が多すぎる場合:** まず standing orders の条件を絞り込むか一度クリアし、それでも多ければ Agent 自体のロール指示を調整してください。呼ばれたときだけ答える一問一答の動きで十分なグループでは、外部チャネルの binding を **Addressed messages only** に戻すか、Pod Chat グループスレッドで該当 Agent の `may_intervene` を無効にします。
- **発言が少なすぎる場合:** May intervene が有効になっているか（外部チャネルの Signal Binding 設定、または Pod Chat グループスレッドでの参加 Agent の `may_intervene` 設定）を確認したうえで、Conversation に具体的な standing order を 1 つ設定してください。アンビエント判定は既定で控えめに振る舞うよう設計されているため、明示的な指示がない限り、本当に必要な場面でしか発言しません。
- **orders を保存しても挙動が変わらない場合:** 保存直後に Agent が返した応答メッセージを確認してください。現在その standing orders が有効かどうかが記載されています。非アクティブと表示されている場合は、外部チャネルの binding モードが May intervene になっていないか、Pod Chat グループスレッドで対象 Agent の `may_intervene` がオフになっています。
