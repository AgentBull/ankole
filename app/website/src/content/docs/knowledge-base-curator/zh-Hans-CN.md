一个知识库策展人 agent 保持 Brain 知识准确和最新——复核 dreaming 提案、识别重复或矛盾的条目、退役陈旧知识、提议合并。这是 [Brain 复核](../brain-review-ops/)的维护面，自动化成一项周期任务。本指南是那个 agent 的实际形态。

先把决定性的性质说清楚：agent **提议变更，不静默应用**。每个策展动作——合并、退役、更新——是经 Brain 审计轨迹由人复核的提案。价值在于做人会跳过的繁琐比较工作（找重复、查陈旧），不在于绕过人工复核。

## 需要什么

- **绑定 `primary` 和 `embedding` profile**——比较知识条目需要推理和召回。
- **一个 signal binding** 到策展提案发帖的频道。
- **一个调度**——每周是策展的好节奏。见 [Cron 调度](../cron-schedules-ops/)。
- **有一定历史的 Brain 知识**——策展在知识库随时间积累条目后最有价值。

## 策展任务

1. **复核 dreaming 提案**——检查 `GET /brain/audit-log` 中带 `dreaming` 权限的条目。每个按准确性和相关性提议批准或拒绝。
2. **找重复**——通过 `memory_search` 召回相似条目；若两个条目用不同话说同一件事，提议合并。
3. **找矛盾**——若两个条目不一致（一个说"API 返回 XML"另一个说"JSON"），标记冲突供人解决。
4. **退役陈旧条目**——若条目引用已不存在的服务、配置或流程，提议退役。
5. **报告**——结构化提案：批准什么、拒绝什么、合并什么、退役什么，各附证据。

## 提案格式

```text
**每周策展提案 — <日期>**
**批准**（看起来对的 dreaming 提案）：
- <条目>：<为什么准确>
**拒绝**（看起来错的 dreaming 提案）：
- <条目>：<为什么错>
**合并**（重复）：
- <条目 A> + <条目 B>：<说的是同一件事；合并为一个>
**退役**（陈旧）：
- <条目>：<引用已被替换的旧 auth 服务>
**矛盾**（需人解决）：
- <条目 A> 说 X；<条目 B> 说 Y。哪个是当前的？
```

人复核提案并通过 `POST /brain/entry-operations` 或还原路由应用变更。

## 人设控制什么

- **策展范围**——"复核 dreaming 提案、找重复、退役引用已废弃服务的超过 6 个月的条目。"
- **陈旧规则**——"条目引用不在当前服务图里的服务、或最后更新超过 90 天且话题变化快的，视为陈旧。"
- **合并策略**——"只在条目真正冗余时提议合并，非在它们覆盖相关但不同的话题时。"
- **不做什么**——"不直接应用变更。只提议。不删除条目——提议退役。"

## 一个完整示例

设置一个每周知识策展人：

1. 创建 agent，绑 `primary`/`embedding`。
2. 撰写 `MISSION.md`："每周一，复核 Brain 知识。检查审计日志找未复核的 dreaming 提案。搜索重复。标记引用已废弃服务的条目。提议：批准、拒绝、合并、退役。把提案发到频道。不应用变更。"
3. 加一条每周调度：`cron: "0 8 * * 1"`。
4. agent 读审计日志、搜重复、查陈旧、发提案。
5. 人复核提案并通过 Brain 复核界面应用变更。

## 本指南不是什么

它不是自动编辑器——agent 提议；人应用。它不是知识库迁移工具——策展清理现有条目；系统间迁移是不同任务。它也不是 [Brain 复核](../brain-review-ops/)界面的替代——它提议通过那个界面应用的变更。
