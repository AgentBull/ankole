随着对话轮次不断累加，任何长会话迟早都会触及大模型的上下文窗口上限。为此，AIGateway 会自动对单轮请求可见的历史上下文执行压缩（Compaction），让长会话得以跨越单次窗口限制持续推进。本页对照 `ai_gateway/compaction*.ex` 的实际源码说明这套机制。

先明确最核心的设计取舍：**Compaction 是刻意有损的，但绝非暗中静默丢弃。**每次执行压缩时，网关会用一份结构化摘要替换早期旧回合、原封不动保留最近几个回合，并将压缩结果本身保存为会话历史指向的一份持久化产物（Artifact）。此后早期原始回合不再进入模型上下文，而这份摘要则作为后续推理的新基准参考状态。换言之，Compaction 并不是一层可逆解压回原文的无损缓存。

## AIGateway 历史 compaction

有状态 Responses 会话的自动历史压缩由 AIGateway 全权托管，从何时触发、如何生成摘要到哪些内容原样保留，核心逻辑全部收敛在 `Ankole.AIGateway.Compaction` 模块中。

### 触发

当会话累计消耗的上下文 Token 数越过设定阈值时，系统便会触发压缩。触发判定直接读取当前可见历史中**最近一次上游 Provider 报告的实际用量**——由于每次响应返回的输入用量本身就是截至当轮的完整快照（而非增量差值），AIGateway 无需在本地按字符粗略估算 Token 数，而是直接以上游返回的权威计量为准。

压缩阈值通过站点级 `AppConfigure` 配置键 `ai_gateway.compaction` 统一调控：

| 参数 | 默认值 | 含义 |
|---|---|---|
| `threshold` | `0.50` | 触发压缩的模型输入上下文窗口占比阈值 |
| `max_threshold_tokens` | `120,000` | 计算出触发阈值后的绝对 Token 上限，避免超大窗口模型攒出过长历史 |
| `tail_rows` | `2` | 紧挨在摘要之后逐字完整保留的最近回合数 |
| `user_message_budget_tokens` | `20,000` | 从被压缩区间内挑选用户原始提问逐字重放的 Token 预算 |

未获取到模型窗口大小时默认按 `256k` 计算。设置 `max_threshold_tokens` 硬上限，是为了防止百万级超大窗口模型一路攒下过于庞大的历史，导致单次压缩调用本身变得极其昂贵缓慢；而针对窗口较小的小模型，系统则会通过 `small_context_trigger_ratio`（`0.85`）按更高占比充分利用有限窗口。

### 摘要器做什么

一旦用量越过阈值，AIGateway 会调用摘要模型将早期回合提炼为一份结构化摘要。压缩提示词明确将这份摘要界定为**静态参考状态而非待执行指令**：“切勿继续推进对话，切勿回答任何问题，仅输出结构化摘要。”摘要会重点归纳任务初衷、关键决策、踩过的报错及修复方案，同时**逐字原样保留**所有文件路径、函数名、报错原文、终端命令与业务 ID——因为一旦路径或错误码被同义改写，后续工具调用就会变成彻底失效的死引用。

生成后的摘要将作为会话历史中承上启下的基准记录注入上下文，模型在后续轮次中会将其视作既有背景状态，而不会误当作一轮需要接话的未完对话。

### 什么逐字存活

除了旧回合的结构化摘要，还有两类关键内容会逐字原样保留在后续上下文中：

- **最近的完整回合**（`tail_rows`，默认为 `2`）：紧挨当前时刻的最后几个回合完整保留，确保模型手头始终握有连贯的即时上下文与最近的工具输出。
- **被压缩区间内的用户原文**：`CompactionRetention` 会在 `user_message_budget_tokens` 预算上限内，从已被折叠进摘要的历史区段中提取人类用户的原始消息并逐字重放。正因如此，哪怕早期冗长的助手推理与工具输出已被压缩折叠，模型依然能准确看到用户最初交代的原始原话与约束细节。

依靠“早期助手工作摘要 + 逐字保留的用户原话 + 逐字保留的最近完整回合”这三者组合，超长会话即便历经多轮压缩也不会跑偏失焦。

### compaction 产物

每次压缩都会产出一份持久化的 `CompactionArtifact` 记录并由 AIGateway 落盘保存。此后该会话的历史链会将最近一次压缩产物作为新的起点锚点，后续回合直接从该锚点向后续接。

## 调优

管理员可根据实际业务形态在 Console 中微调以下参数：

- **业务以短平快对话为主、觉得压缩触发太频繁时，适当调高 `threshold`**：默认的 `0.50` 偏向稳健保守，可根据成本与延迟权衡上调。
- **发现压缩后模型容易丢掉刚做完的上一步细节时，适当调高 `tail_rows`**：保留更多完整的近期回合，代价是留给后续增长的缓冲空间相应变小。
- **长对话中用户前期交代的大量需求细节被截断遗漏时，适当调高 `user_message_budget_tokens`**：为逐字重放用户原始消息留出更充裕的预算。

上述三个参数均位于 Console 的 `AppConfigure` 系统配置页，修改保存后将在**下一次触发压缩时**生效，不会影响正在执行中的当前回合。

## 本指南不是什么

本页讨论的并非上游厂商的前缀提示词缓存（Prompt Caching）——AIGateway 不在这一层自行实现厂商侧的 KV Cache 机制，前缀缓存由各上游 Provider 原生负责（在支持该特性的 Provider 上可通过配置 `promptCacheKey` 提升缓存命中率）。同时，Compaction 也绝非无损归档：早期原始回合确实会从发往模型的活动上下文中移除。最后，自动压缩也不能替代合理的任务拆分——它能兜底保障长会话不因窗口溢出而中断，但如果某个会话每隔寥寥几轮就频繁触发压缩，更合理的做法是引导开启新会话，或将重度长线工作委派给独立的[后台 Agent 任务](../background-jobs/)。
