一个设计评审 agent 读一份设计文档或架构提案——ADR、设计文档、提案——评审其缺口、风险、未考虑的替代方案、和需验证的假设。本指南是那个 agent 的实际形态。

先把决定性的性质说清楚：agent **评审文档，不批准设计**。它提出问题和识别缺口；团队解决它们。价值在于第二双眼睛抓住作者遗漏的东西，不在于批准的权威。

## 需要什么

- **绑定 `primary` profile**——设计评审需要深度推理。
- **绑定 `embedding` profile**——Brain 召回过往决定、现有架构约束、和项目的设计优先级。
- **一个 signal binding** 到评审反馈发帖的频道。
- **交付的设计文档**——粘贴文本、上传文件、或 URL。

## 工作流

1. **设计文档到达**——粘贴在频道、上传、或链接。
2. **agent 读文档**——提议的设计、其上下文、其假设。
3. **agent 召回上下文**——Brain 知识找过往决定、项目架构约束、和设计优先级（来自 `AGENTS.md` 或项目的设计文档）。
4. **agent 评审**——识别：遗漏的考虑、未声明的假设、未处理的风险、未评估的替代方案、和与现有架构的不一致。
5. **agent 发反馈**——结构化的问题，不是判决。

## 评审格式

```text
**设计评审 — <文档标题>**

**优点**：<设计做对了什么>
**问题**（团队应回答）：
- <问题 1>：<为什么重要>
- <问题 2>：<为什么重要>
**风险**（文档中未处理）：
- <风险 1>：<可能出什么问题>
**替代方案**（未评估）：
- <替代>：<为什么值得考虑>
**一致性**：<设计是否与项目现有架构和约束一致？>
```

格式是问题不是答案。agent 提出作者该处理的；团队决定怎么处理。

## 人设控制什么

- **评审深度**——"高层：遗漏的考虑和风险"vs"详细：逐行一致性检查"。
- **上下文召回**——"把设计与 Brain 的架构决定和项目设计优先级对照。"
- **语气**——"建设性。提问题不否定。每个问题应可回答。"
- **不做什么**——"不批准或拒绝设计。不重写文档。只提问题。"

## 一个完整示例

为工程团队设置设计评审 agent：

1. 创建 agent，绑 `primary`/`heavy`/`embedding`。
2. 撰写 `MISSION.md`："分享设计文档时读它。召回 Brain 的架构决定和项目设计优先级。评审：遗漏的考虑、未声明的假设、未处理的风险、未评估的替代方案、与现有架构的不一致。发结构化反馈：优点、问题、风险、替代方案、一致性。不批准或拒绝。只提问题。"
3. 策展 Brain 知识：过往 ADR、架构约束、项目设计优先级。
4. 在频道里："评审新通知服务的设计：<链接或粘贴>。"
5. agent 读、召回、评审、发结构化反馈。

## 本指南不是什么

它不是架构审批人——agent 提问题；团队批准。它不是代码审查员——它评审设计文档不评审代码。它也不是橡皮图章——不提问题只说"看起来不错"的设计评审没有价值。价值在于问题，不在于批准。
