## Ankole 的部署结构

一套 Ankole 私有化部署实例由一个逻辑控制面，以及每位 Agent 各自独占的一个 Agent Computer Worker 组成。控制面持有持久领域状态与监督权，负责全局管理与调度；Worker 则负责承载 Agent 的实际运行，相当于每位 Agent 专属的工作电脑。

不同 Agent 之间绝不共用 Worker，正如团队中每位同事都有各自独立的工作电脑。创建 Agent 时，控制面会同步为其创建专属 Worker，并在后续运行中自动负责该 Worker 的停止、升级替换与销毁回收。

  text="Worker 所在的容器或 Pod 就是它唯一的隔离边界：Agent 的命令行执行、Automation 脚本与无头浏览器均直接在其中运行，不设内层沙盒，容器本身也无需任何额外内核特权。Agent 可以在自己的 Worker 上自由安装软件甚至把环境弄坏，但绝无法冒充其他 Agent；一旦某个 Worker 未能按时就绪，控制面会自动将其重建。"

每套部署实例均需要 PostgreSQL 数据库、控制面云盘文件存储，以及每位 Agent 的持久 Home 存储。官方 Kubernetes Helm Chart 默认采用共享的 ReadWriteMany Home PVC 搭配独立的 ReadWriteOnce 缓存 PVC——其中持久 Home 必须纳入定期备份，缓存卷则无需备份。

单个站点可以容纳多个逻辑隔离的租户：站点管理员负责维护底层共享基础设施，各租户各自拥有独立的人员主体、Agent、Brain 知识库与外部平台连接。站点管理台默认位于 `/site-admin-console`；如需修改路径，请在启动前设置环境变量 `ANKOLE_SITE_ADMIN_CONSOLE_PATH`（Helm 部署对应配置 `controlPlane.siteAdminConsolePath`）。

### 术语表

以下术语表是 Ankole 用户文档与控制台界面的统一用语规范。括号内保留英文原名以便对照第三方平台后台、配置字段与 API；后文统一使用简称。

| 统一名称 | 含义 | 后文简称 |
|---|---|---|
| **站点（Site）** | 一套共享底层基础设施、由站点管理员统一运维的完整 Ankole 部署实例 | 站点 |
| **租户（Tenant）** | 站点内单个组织的人员、Agent、Brain、外部平台连接及业务数据边界 | 租户 |
| **主体（Principal）** | Ankole 中可拥有身份标识与访问权限的自然人、Agent 或系统服务 | 主体 |
| **身份源提供商（Identity Provider，IdP）** | 为 Console 提供企业单点登录，并向 Ankole 同步员工、通讯录与组织架构的外部身份源 | IdP |
| **聊天平台** | Slack、Teams、飞书 / Lark、钉钉、企业微信、Telegram、Discord、LINE、WhatsApp 或电子邮箱等承载对话的外部平台 | 平台 |
| **聊天渠道（Channel Provider）** | 接入 Ankole 的一套外部聊天应用或机器人凭证配置，用于收取消息并发回 Agent 回复 | 聊天渠道 |
| **对话（Conversation）** | 人与 Agent 共同参与的交流空间；原生对话发言以 Ankole 为准，外部平台对话发言以宿主平台为准 | 对话 |
| **消息（Message）** | 在对话中正式提交、对参与者可见的发言记录 | 消息 |
| **信号（Signal）** | 由对话发言、定时触发、外部事件或子任务完成所生成并持久接纳的输入刺激 | 信号 |
| **执行会话（Session）** | 持有专属信号队列与可恢复执行进度的运行上下文，严格限定在单个对话内 | 执行会话 |
| **投递（Delivery）** | 向外部对话发送回复时的持久化投递意图、尝试记录与最终回执 | 投递 |
| **信号路由规则（Signal Binding）** | 定义将哪个信号源收到的消息或事件转交给哪位 Agent 处理的绑定规则 | 路由规则 |
| **大语言模型提供商（LLM Provider）** | 保存模型接口地址、访问凭证及可用模型列表的配置 | 模型提供商 |
| **后台 Agent 任务档案（内部键：`coding`）** | 指定后台 Agent 任务所使用的 AIGateway 提供商与模型 | 后台 Agent 任务 |

## 1. 部署 Ankole

单机部署推荐使用 Docker Compose，企业级集群环境推荐使用 Kubernetes；源码安装仅用于本地功能开发与故障调试。

## 2. 先设置登录与身份源

Ankole 专为企业私有化部署设计。一套站点可承载多个租户；各租户内的 Agent、员工与系统服务均统一建模为主体（Principal），并由权限模块（AuthZ）集中鉴权。完成 `/setup` 初始化后，首位登录的管理员会同时获得站点级 `siteadmin`（可访问 `/site-admin-console` 站点管理台）与默认 Pod 的 `pod_admin` 权限。进入控制台调整租户级设置前，请先在左上角切换至目标租户。

在 `/setup` 初始化向导中，你既可以选择免密**邮箱验证码（Email OTP，`email_otp`）**（通过自有 SMTP 服务器发送 6 位验证码），也可以接入**企业 SSO 身份源提供商（IdP）**来同步员工名册、通讯录与部门架构。请务必先完成登录与身份初始化，再去配置外部聊天渠道。

| 设置项 | 负责什么 | 在哪里设置 |
|---|---|---|
| **邮箱验证码（`email_otp`）** | 免密 6 位邮箱验证码登录（`authn.email.mail` SMTP 发信与 `SiteCredential` 绑定）及邮件邀请成员 | `/setup`（**邮箱验证码**），或命令行 `mix ankole.authn.mail.put` |
| **IdP** | 企业 SSO 单点登录，以及员工、通讯录、组织架构与权限组的同步 | 首次在 `/setup` 配置，后续在 **Console → 身份源提供商** 管理 |
| **聊天渠道** | 收取外部 IM 消息并发回 Agent 的回复 | 在 **Console → 信号路由** 中配置 |

登录认证方式与日常对话所用的聊天渠道完全解耦，可以来自不同平台：例如用邮箱验证码或 Google Workspace 登录后台，而在 Slack 中与 Agent 对话；或者用 Microsoft Entra ID 登录后台，而将 Agent 接入飞书、Slack、钉钉、Teams 或企业微信。

### 按所选登录方式完成首次设置

在下方切换至**邮箱验证码**或企业实际使用的身份源，按对应标签页的步骤依次操作。每个企业 SSO 标签页均从第三方管理后台创建应用讲起，直至完成首次登录与通讯录全量同步。

若对应的企业平台适配器是在本次操作中刚刚启用的，请在完成首次登录后按当前部署方式重启一次控制面进程，以便通讯录长连接或 Microsoft Graph 订阅等插件后台任务完整启动。

## 3. 添加模型提供商，并创建 Agent

Agent 的模型档案只保存模型引用，因此必须先添加模型提供商。登录 Console 后打开 **模型提供商 → 新增提供商**，选择提供商类型，填写固定的 Provider ID、接口地址与访问凭证并保存。

控制面会对所有提供商凭证进行加密存储，切勿将模型 API 密钥写入部署环境变量或 Agent 工作区文件中。

随后打开 **Agents → New Agent**，填写唯一标识（handle）和显示名称，选择运行所需的 WorkerProvider，并在职责说明（mission）中写清工作范围与交付要求；Agent 的全局 UID 由 Ankole 自动生成。

接着为该 Agent 配置三个核心模型档案（Model Profile）：

| Profile | 建议用途 |
|---|---|
| `primary` | 日常绝大多数对话与工具调用使用的主模型 |
| `light` | 简单、高频的轻量推理与维护任务 |
| `heavy` | 高复杂度深度推理任务 |

以上三个核心档案缺一不可。首次跑通链路时，可以先让三者共用同一个已验证可用的提供商和模型；待确认 IM 收发对话顺畅后，再按实际负载拆分为不同档位的模型。

## 4. 连接聊天渠道并创建信号路由规则

请先在 Console 中确认目标聊天平台对应的控制面插件（Control Plane Plugin）已启用，再前往该平台后台创建机器人或应用。即便企业的身份源（IdP）与聊天渠道同属一个平台，生产环境仍建议分别创建独立应用，将登录及通讯录权限与机器人消息权限隔离，后续轮换密钥或发布应用版本时也互不干扰。

一套聊天应用通常对应一个独立的机器人身份；若多位 Agent 需要展示各自不同的机器人名称、头像或权限范围，请在同一聊天平台分别创建多套应用。应用准备就绪后，回到 Console 创建信号路由规则，将该聊天渠道绑定到目标 Agent。

在账号映射机制上，Slack、Teams、飞书 / Lark、钉钉与企业微信属于企业办公平台，发信人直接对应 IdP 同步的企业通讯录成员；Telegram、Discord、LINE 与 WhatsApp 则属于个人消费级 IM，发信人没有企业员工档案，默认需由管理员先在**身份 → 待绑定账号**中将每位新发信人关联至已有账号后，Agent 才会为其提供服务（WhatsApp 若检测到发信手机号已归属某个已知主体，则会自动完成映射）；电子邮件渠道接入的是单个专用邮箱，仅识别命中显式邮箱身份绑定的发件人。

### 在 Console 中完成连接

每条信号路由规则负责把一个外部聊天渠道连接到一位目标 Agent，记录所用平台适配器、应用凭证、应答 Agent 以及群聊消息处理模式；接入多个机器人时，请分别创建对应的路由规则。

打开 **Console → 信号路由 → 新增路由规则**，依次填写：

| 字段 | 如何选择 |
|---|---|
| **Target Agent** | 选择第 3 步创建的 Agent |
| **Adapter** | 选择 Slack、Teams、飞书 / Lark、钉钉、企业微信、Telegram、Discord、LINE、WhatsApp 或 Email |
| **规则名称** | 填写稳定的标识名称，例如 `slack-main` 或 `lark-main` |
| **Group message mode** | 首次联调测试请选择 `addressed_only` |
| **聊天渠道配置** | 填入上方对应平台标签页中准备好的各项凭证与参数 |

保存后，确认该规则在列表中显示为启用状态。若保存时提示凭证校验有误，请先修正凭证再去聊天软件测试——在凭证通过检查前，平台适配器不会建立连接。

## 5. 在 IM 中与 Agent 对话

将配置好的机器人拉入测试会话。首次在群聊中测试时，请明确 @ 提及它：

> @Ankole 你能做什么？你现在服务哪个团队？

### Agent 没有回复时

若迟迟未收到回复，请按以下顺序逐项排查：

1. 聊天平台后台中的应用已发布最新版本，且当前测试账号在应用可用范围内。
2. 机器人已被邀请加入测试所在的频道、团队或群聊会话。
3. 平台要求的消息接收事件与接口权限均已审批生效。
4. 信号路由规则处于启用状态，且指向正确的目标 Agent。
5. 目标 Agent 已配齐 `primary`、`light` 与 `heavy` 三个核心模型档案。
6. 模型提供商的 API 凭证与模型名称真实有效。
7. 在 **Console → 工作节点** 中，该 Agent 对应的 Worker 状态显示为“就绪”；若未就绪，页面会直接展示底层平台返回的具体原因。

使用 Docker Compose 部署时，可运行 `docker compose logs -f control-plane` 查看控制面实时日志；如需查看 Worker 日志，先运行 `docker ps -a --filter label=ankole.installation=ankole` 列出 Worker 容器，再执行 `docker logs CONTAINER_NAME` 查看目标容器。使用 Kubernetes 部署时，分别查看控制面 Pod 与对应 Worker Pod 的日志即可。排查问题时请仅截取相关报错行，切勿打印环境变量或任何敏感密钥。

跑通首条回复后，可继续阅读 [Agent](../agents/)、[信号路由规则](../signal-bindings/)或 [后台 Agent 任务](../background-jobs/)。
