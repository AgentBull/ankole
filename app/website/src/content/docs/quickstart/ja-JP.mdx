## Ankole のデプロイ方法

プライベートな Ankole デプロイメントインスタンスは、1 つの control plane と、Agent ごとに 1 つ割り当てられる Agent Computer Worker で構成されます。control plane は永続的なドメイン状態とプロセス監視を担う管理基盤であり、Worker は各 Agent 専用の仕事用コンピュータとして実行環境を提供します。

人間が一人ひとり自分の業務用 PC を持つのと同じように、複数の Agent が 1 つの Worker を共有することはありません。Agent を作成すると、control plane がその Agent 専用の Worker を自動でプロビジョニングし、停止・置き換え・削除まで一貫して管理します。

<DocsKnowledgeNote
  label="💡 知っていましたか？"
  text="Worker のコンテナ（または Pod）そのものが唯一の分離境界です。Agent が実行するコマンド、Automation スクリプト、ブラウザ操作は内側の追加サンドボックスなしでそのコンテナ内で直接動作し、特権的なカーネル権限も必要としません。Agent が自分の Worker 内にソフトウェアを入れたり環境を壊したりすることはあっても、別の Agent になりすますことはできません。また、規定時間内に準備完了にならない Worker は control plane が自動的に再構築します。"
/>

すべてのデプロイメントには、PostgreSQL、ドライブ用のファイルストア、および Agent ごとの永続 Home ストレージが必要です。Kubernetes の既定 Helm chart では、共有の ReadWriteMany Home PVC と、それとは別の ReadWriteOnce キャッシュ PVC を使用します（Home はバックアップ必須ですが、キャッシュは再構築可能なためバックアップ不要です）。

また、1 つのサイト内に複数のテナントを収容できます。サイト管理者が共有インフラを管理し、各テナントがその配下でメンバー、Agent、Brain、外部接続をそれぞれ保有します。Site Admin Console の既定パスは `/site-admin-console` ですが、起動前に `ANKOLE_SITE_ADMIN_CONSOLE_PATH`（Helm では `controlPlane.siteAdminConsolePath`）で変更できます。

### このガイドで使用する用語

以下の表は、Ankole のドキュメントおよび管理画面で使われる用語の定義です。括弧内の名称は外部プラットフォームや設定フィールド、API 上の表記に対応しています。以降のセクションでは右列の短縮形を使用します。

| 正式用語 | 意味 | 短縮形 |
|---|---|---|
| **Site** | 共有インフラとサイト管理者を持つ Ankole デプロイメント全体 | Site |
| **Tenant** | サイト内の 1 組織に属するメンバー、Agent、Brain、外部接続、および業務データ | Tenant |
| **Principal** | Ankole 上で ID と権限を持つ人間、Agent、またはシステムサービス | Principal |
| **Identity Provider (IdP)** | Console の SSO を提供し、社員・連絡先・組織構造を同期する外部の認証基盤 | IdP |
| **Chat platform** | Slack、Teams、Lark/Feishu、DingTalk、WeCom、Telegram、Discord、LINE、WhatsApp、メールなどの外部会話サービス | Platform |
| **Channel Provider** | メッセージを受信して Agent の返信を送り出す個別のチャットアプリまたは bot 設定 | Channel Provider |
| **Conversation** | 人と Agent がやり取りする共有の会話空間。ネイティブ会話は Ankole が、外部チャット会話は外部プラットフォーム側が正本を持ちます | Conversation |
| **Message** | 会話の参加者に表示される確定済みの発言レコード | Message |
| **Signal** | メッセージ、スケジュール時刻、外部イベント、またはタスク完了から生成される永続的なトリガー信号 | Signal |
| **Session** | Signal キューと復旧可能な作業状態を持つ実行コンテキスト（複数の Conversation をまたぐことはありません） | Session |
| **Delivery** | 外部の会話へメッセージを送出する際の永続的な送信意図・試行・結果の記録 | Delivery |
| **Signal Routing Rule (Signal Binding)** | Signal の発生元から対象の Agent へメッセージやイベントを振り分けるルール | Routing rule |
| **LLM Provider** | モデルサービスの接続先エンドポイント、認証情報、利用可能なモデル一覧を保持する設定 | LLM Provider |
| **Background Agent Jobs profile (内部キー: `coding`)** | Background Agent Jobs で使用する AIGateway provider とモデルを指定するプロファイル | Background Agent Jobs |

## 2. サインインと identity を最初にセットアップする

Ankole は組織内のプライベートデプロイメント向けに設計されており、1 つのサイト内に複数のテナントを構成できます。各テナントの社員、Agent、システムサービスはすべて Principal として表現され、AuthZ が権限を一元管理します。`/setup` を完了すると、最初の管理者に `siteadmin`（`/site-admin-console` の Site Admin Console 権限）と既定 Pod の `pod_admin` の両方が付与されます。テナント単位の設定を行う際は、Console 上で対象テナントを選択してから操作してください。

`/setup` では、パスワードレスの **メール認証（Email OTP）**（`email_otp`：SMTP サーバーと 6 桁の確認コードを使用）または、社員・連絡先・組織構造のディレクトリ同期も兼ねる **エンタープライズ SSO Identity Provider（IdP）** のどちらかを選択します。チャットチャンネルを接続する前に、まずこのサインイン基盤を完了させてください。

| 設定 | 役割 | 設定場所 |
|---|---|---|
| **メール認証（`email_otp`）** | パスワード不要の 6 桁メール確認コード認証（`authn.email.mail` の SMTP 設定と `SiteCredential` 紐付け）およびメール招待 | `/setup`（**メール認証**）、または CLI `mix ankole.authn.mail.put` |
| **Identity Provider (IdP)** | エンタープライズ SSO、および組織ディレクトリからの社員・連絡先・部署・権限グループの同期 | 初回は `/setup`、以降は **Console → Identity Providers** |
| **Channel Provider** | チャットメッセージの受信と Agent からの返信送信を担う IM アプリまたは bot | **Console → Signal Routing** |

なお、サインイン方式とチャットチャンネルを同じプラットフォームに揃える必要はありません。たとえばメール認証や Google Workspace でサインインを構成しつつ Slack で Agent と会話したり、Entra ID で SSO と組織同期を行いながら Lark・Slack・DingTalk・Teams・WeCom をチャット窓口として使ったりできます。

### お使いのサインイン方式のセットアップを完了する

## 3. LLM Provider を追加して Agent を作成する

Agent のモデルプロファイルは登録済みの LLM Provider を参照するため、先に LLM Provider を追加します。Console にサインインし、**Providers → New provider** を開いて provider の種類を選択し、安定した Provider ID、エンドポイント、および認証情報を入力して保存してください。

登録した認証情報は control plane 内で暗号化して保管されます。デプロイ用の環境変数ファイルや Agent のファイル内に API key を書き込まないでください。

続いて **Agents → New Agent** を開き、handle、表示名、Worker provider、および担当業務と完了条件を記した mission を設定します（不透明な Agent UID は Ankole が自動生成します）。

Agent を作成したら、以下の 3 つのモデルプロファイルを設定します。

| プロファイル | 初回実行での用途 |
|---|---|
| `primary` | メインの対話・推論モデル |
| `light` | 軽量かつ高頻度な処理用モデル |
| `heavy` | 高度な統合・深い推論用モデル |

Agent を動かすにはこの 3 つすべてが必須です。最初の疎通確認では、動作実績のある同じ provider とモデルを 3 つすべてに割り当てて構いません。一通りの会話が通ることを確認してから、用途別にモデルを分けてください。

## 4. チャットチャンネルを接続して signal routing ルールを作成する

Console で対象チャットプラットフォームの Control Plane Plugin を有効化し、プラットフォーム側で bot またはアプリケーションを作成します。サインイン（IdP）と同じプラットフォームを使う場合でも、IdP 用とチャット用でアプリは分けて作成してください。アプリを分離しておくことで、サインイン・ディレクトリ権限と bot 権限を最小限に保てるほか、認証情報のローテーションやアプリのバージョン公開も互いに影響せず行えます。

通常、1 つのチャットアプリは 1 つの bot アカウントに対応します。複数の Agent で別々の bot 名・アイコン・権限を使い分けたい場合は、プラットフォーム側で Agent ごとにアプリを作成してください。アプリの準備ができたら、Console でルーティングルールを作成して対象の Agent に接続します。

なお、Slack・Teams・Lark/Feishu・DingTalk・WeCom はエンタープライズ向けプラットフォームであり、発言者は IdP が同期した社員ディレクトリと照合されます。一方、Telegram・Discord・LINE・WhatsApp はコンシューマー向け IM のため社員レコードが存在せず、新しい送信者が話しかけた際は管理者が **アイデンティティ → 保留中のマッピング** で既存アカウントへ紐付けてから Agent の応答が始まります（WhatsApp のみ、携帯電話番号が既存アカウントと一致すれば自動マッピングされます）。また、Email では専用メールボックスを接続し、明示的に email identity が紐付けられた送信者からのメールのみを受け付けます。

### Console で接続を完了する

ルーティングルールは、1 つの Channel Provider と 1 つの Agent を結び付け、使用するアダプター・アプリ認証情報・宛先 Agent・グループメッセージの扱い方を定義します。bot ごとに個別のルールを作成してください。

| フィールド | 設定内容 |
|---|---|
| **Target Agent** | ステップ 3 で作成した Agent |
| **Adapter** | Slack、Teams、Lark/Feishu、DingTalk、WeCom、Telegram、Discord、LINE、WhatsApp、または Email |

| **Channel settings** | 上のチャンネルタブで控えた認証情報と設定値を入力 |

### Agent が返信しない場合

以下の順番で、上流から 1 つずつ境界を確認してください。

1. 外部プロバイダー側でアプリの最新バージョンが公開されており、テストユーザーが公開範囲に含まれていること。
2. 対象のチャンネル、チーム、または会話に bot が招待・インストールされていること。
3. 必要なメッセージ受信イベントと権限スコープがすべて有効になっていること。
4. ルーティングルールが有効（enabled）で、意図した Agent を指していること。
5. Agent に `primary`・`light`・`heavy` の 3 つのモデルプロファイルが設定されていること。
6. LLM Provider の認証情報とモデル指定が有効であること。
7. **Console → Workers** で対象 Agent の Worker が準備完了になっていること（未完了の場合は、同じ画面にバックエンドからのエラー理由が表示されます）。

Docker Compose 環境では、`docker compose logs -f control-plane` で control plane のログを確認し、`docker ps -a --filter label=ankole.installation=ankole` で Worker コンテナを特定して `docker logs CONTAINER_NAME` でログを確認します。Kubernetes 環境では、control plane と Worker の各 Pod ログを確認してください。その際、該当するエラー出力だけを確認し、環境変数一覧や secret をターミナルやチャットに出力しないよう注意してください。

最初の返信を確認できたら、次は [Agents](../agents/)、[Signal Routing ルール](../signal-bindings/)、または [Background Agent Jobs](../background-jobs/) に進んでください。
