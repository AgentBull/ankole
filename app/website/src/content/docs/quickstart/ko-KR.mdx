## Ankole 배포 방식

프라이빗 Ankole 배포 인스턴스는 하나의 컨트롤 플레인과, Agent마다 하나씩 할당되는 Agent Computer Worker로 구성됩니다. 컨트롤 플레인은 영속적인 도메인 상태와 감독을 총괄하는 관리 플랫폼이고, Worker는 각 Agent의 전용 작업 컴퓨터 역할을 하는 실행 환경입니다.

동료마다 각자의 업무용 컴퓨터를 쓰듯 Agent끼리도 Worker를 공유하지 않습니다. Agent가 생성되면 컨트롤 플레인이 전용 Worker를 직접 생성하며, 중지·교체·삭제까지 모두 관리합니다.

<DocsKnowledgeNote
  label="💡 알고 계셨나요?"
  text="Worker의 컨테이너 또는 Pod 자체가 유일한 격리 경계입니다. Agent가 실행하는 명령, Automation 스크립트, 브라우저는 별도의 내부 샌드박스 없이 그 안에서 바로 실행되며 컨테이너에 추가 커널 권한도 필요하지 않습니다. 설령 Agent가 자기 Worker에 소프트웨어를 설치하거나 환경을 망가뜨리더라도 다른 Agent 신원으로 행동할 수는 없으며, 준비 상태를 제때 회복하지 못하는 Worker는 컨트롤 플레인이 새로 교체합니다."
/>

모든 배포 환경에는 PostgreSQL, 드라이브 파일 스토리지, Agent별 영구 Home 볼륨이 필요합니다. 기본 Kubernetes 차트는 공유 `ReadWriteMany` Home PVC와 별도의 `ReadWriteOnce` 캐시 PVC를 사용합니다. Home 볼륨은 반드시 백업해야 하지만 캐시 볼륨은 백업하지 않아도 됩니다.

하나의 사이트 안에 여러 테넌트를 둘 수 있습니다. 사이트 관리자는 공유 인프라를 운영하고, 각 테넌트는 소속 사용자·Agent·Brain·외부 연동을 독립적으로 소유합니다. 사이트 관리 콘솔의 기본 경로는 `/site-admin-console`이며, 최초 기동 전에 `ANKOLE_SITE_ADMIN_CONSOLE_PATH`(Helm: `controlPlane.siteAdminConsolePath`)로 변경할 수 있습니다.

### 이 가이드에서 사용하는 용어

다음 표는 Ankole 문서와 화면 전반에서 사용하는 핵심 용어를 정리한 것입니다. 괄호 안의 표기는 외부 플랫폼이나 설정 필드, API 명칭에 대응하며, 이후 본문에서는 짧은 형식을 주로 사용합니다.

| 정식 용어 | 의미 | 짧은 형식 |
|---|---|---|
| **Site** | 공유 인프라와 사이트 관리자를 갖춘 하나의 전체 Ankole 배포 단위 | Site |
| **Tenant** | 사이트 내 개별 조직의 사용자, Agent, Brain, 외부 연결 및 작업 공간 | Tenant |
| **Principal** | Ankole 안에서 신원과 권한을 부여받는 주체(사람, Agent, 시스템 서비스) | Principal |
| **Identity Provider (IdP)** | Console SSO 로그인을 제공하고 구성원·연락처·조직도를 동기화하는 외부 신원 소스 | IdP |
| **Chat platform** | Slack, Teams, Lark/Feishu, DingTalk, WeCom, Telegram, Discord, LINE, WhatsApp, 이메일 메일함 등 외부 대화 플랫폼 | Platform |
| **Channel Provider** | 메시지를 수신하고 Agent 답변을 발송하는 개별 채팅 앱 또는 봇 설정 | Channel Provider |
| **Conversation** | 사람과 Agent가 함께 참여하는 대화 공간. 네이티브 메시지는 Ankole을, 외부 메시지는 해당 플랫폼을 정본으로 삼습니다 | Conversation |
| **Message** | 대화 참여자에게 표시되는 확정된 메시지 기록 | Message |
| **Signal** | 메시지 도착, 예약 시각 도래, 외부 이벤트, 작업 완료 등으로 발생하는 영속적 트리거 | Signal |
| **Session** | 시그널 큐와 복구 가능한 작업 상태를 지닌 실행 컨텍스트(대화 간 경계를 넘지 않음) | Session |
| **Delivery** | 외부 대화 채널로 내보내는 메시지의 영속적인 전송 의도, 시도 이력 및 최종 결과 | Delivery |
| **Signal Routing Rule (Signal Binding)** | 시그널 소스의 메시지나 이벤트를 대상 Agent로 연결하는 라우팅 규칙 | Routing rule |
| **LLM Provider** | 모델 서비스 엔드포인트, 자격 증명, 사용 가능 모델 목록을 담는 설정 | LLM Provider |
| **Background Agent Jobs profile (internal key: `coding`)** | Background Agent Jobs 실행에 사용할 AIGateway Provider와 모델을 지정하는 프로필 | Background Agent Jobs |

## 2. 로그인과 identity를 먼저 설정

Ankole은 조직 내부의 프라이빗 배포를 전제로 설계되었습니다. 한 사이트에 여러 테넌트를 둘 수 있으며, 각 테넌트의 구성원·Agent·시스템 서비스는 모두 Principal로 표현되고 권한은 AuthZ가 관리합니다. `/setup`을 완료하면 첫 관리자에게 사이트 관리 콘솔(`/site-admin-console`)용 `siteadmin` 권한과 기본 Pod의 `pod_admin` 권한이 함께 부여됩니다. 테넌트 단위 설정을 변경하기 전에는 Console에서 대상 테넌트가 선택되어 있는지 먼저 확인하세요.

`/setup`에서는 비밀번호 없이 6자리 인증 코드를 이메일로 받는 **이메일 인증(Email OTP)**(`email_otp`, SMTP 서버 사용)과, 직원·연락처·조직도까지 함께 동기화하는 **엔터프라이즈 SSO Identity Provider(IdP)** 가운데 하나를 선택합니다. 채팅 채널을 연결하기 전에 로그인 방식부터 먼저 설정하세요.

| 설정 항목 | 담당 역할 | 설정 위치 |
|---|---|---|
| **이메일 인증 (`email_otp`)** | 비밀번호 없는 6자리 이메일 인증 코드 로그인(`authn.email.mail` SMTP 발송 및 `SiteCredential` 바인딩)과 이메일 초대 | `/setup` (**이메일 인증**), 또는 CLI `mix ankole.authn.mail.put` |
| **Identity Provider (IdP)** | 엔터프라이즈 SSO 로그인 및 사내 디렉터리의 직원·연락처·조직도·권한 그룹 동기화 | 초기 `/setup` 완료 후 **Console → Identity Providers** |
| **Channel Provider** | 사용자 메시지를 받고 Agent 답변을 보내는 메신저 앱 또는 봇 | **Console → Signal Routing** |

로그인 수단과 채팅 채널이 꼭 같은 플랫폼일 필요는 없습니다. 예를 들어 이메일 인증이나 Google Workspace로 로그인을 구성하고 Slack에서 Agent와 대화할 수 있으며, Entra ID로 신원 인증을 처리하면서 대화 채널로는 Lark, Slack, DingTalk, Teams, WeCom을 연결할 수도 있습니다.

### 선택한 로그인 방식 설정 완료

## 3. LLM Provider 추가 및 Agent 생성

Agent의 모델 프로필은 등록된 Provider의 모델을 참조하므로 먼저 LLM Provider를 추가해야 합니다. Console에 로그인한 뒤 **Providers → New provider**를 열고 Provider 유형을 선택한 다음, 고정된 Provider ID와 엔드포인트·자격 증명을 입력해 저장하세요.

Provider 자격 증명은 컨트롤 플레인 내부에 암호화되어 저장됩니다. 배포 환경 변수 파일이나 Agent 작업 공간 파일에는 절대 기록하지 마세요.

이어서 **Agents → New Agent**를 열고 핸들(handle), 표시 이름, Worker Provider, 그리고 담당 역할과 완료 기준을 담은 미션(mission)을 입력합니다. 고유 불투명 UID는 Ankole이 자동 생성합니다.

마지막으로 세 가지 필수 모델 프로필을 지정합니다:

| 프로필 | 기본 역할 |
|---|---|
| `primary` | 주 추론 및 대화 응답 모델 |
| `light` | 짧고 빈번한 경량 보조 작업 |
| `heavy` | 깊이 있는 분석 및 종합 추론 |

Agent가 정상 실행되려면 세 프로필이 모두 지정되어 있어야 합니다. 첫 대화를 테스트할 때는 검증된 동일한 Provider·모델을 세 프로필에 모두 연결해도 충분하며, 전체 경로가 정상 동작하는 것을 확인한 뒤에 역할별로 모델을 분리하세요.

## 4. 채팅 채널 연결 및 시그널 라우팅 규칙 생성

Console에서 사용할 채팅 플랫폼의 Control Plane Plugin을 활성화한 다음 해당 플랫폼에서 봇 또는 앱을 생성하세요. 로그인(IdP)과 채팅에 같은 플랫폼을 쓰더라도 앱은 각각 따로 만드는 것을 권장합니다. 이렇게 앱을 분리해 두면 로그인·디렉터리 권한과 봇 권한을 독립적으로 관리할 수 있고, 자격 증명 교체나 앱 버전 배포도 서로 영향을 주지 않습니다.

채팅 앱 하나는 일반적으로 봇 신원 하나에 대응합니다. 여러 Agent마다 서로 다른 봇 이름, 프로필 이미지, 권한이 필요하다면 플랫폼에서 앱을 각각 생성하세요. 앱 준비가 끝나면 Console에서 라우팅 규칙을 만들어 대상 Agent에 연결합니다.

Slack, Teams, Lark/Feishu, DingTalk, WeCom은 엔터프라이즈 플랫폼이므로 IdP에서 동기화한 디렉터리 구성원이 곧바로 사용자로 연결됩니다. 반면 Telegram, Discord, LINE, WhatsApp은 일반 소비자용 메신저여서 사내 직원 레코드가 없으므로, 새로운 발신자가 처음 메시지를 보내면 관리자가 **아이덴티티 → 대기 중인 매핑**에서 기존 계정에 연결한 뒤부터 Agent가 응답합니다. 단, WhatsApp에서는 발신자 전화번호가 이미 등록된 계정에 연결되어 있으면 별도 승인 없이 자동으로 매핑됩니다. Email 채널은 전용 메일함을 연결하며, 명시적인 이메일 신원 바인딩이 등록된 발신자만 인식합니다.

### Console에서 연결 완료

라우팅 규칙 하나는 단일 Channel Provider를 단일 Agent에 연결하며 어댑터 종류, 앱 자격 증명, 대상 Agent, 그룹 메시지 동작 모드를 담습니다. 봇마다 별도의 라우팅 규칙을 만드세요.

Console에서 **Signal Routing → New routing rule**을 열고 아래 항목을 입력합니다:

| 필드 | 입력할 값 |
|---|---|
| **Target Agent** | 3단계에서 생성한 Agent |
| **Adapter** | Slack, Teams, Lark/Feishu, DingTalk, WeCom, Telegram, Discord, LINE, WhatsApp 또는 Email |
| **Rule name** | `slack-main`, `lark-main`처럼 식별하기 쉬운 고정 이름 |
| **Group message mode** | 처음에는 `addressed_only`로 시작 |
| **Channel settings** | 위 채널 탭에서 준비한 자격 증명 및 설정값 붙여 넣기 |

규칙을 저장하면 목록에 활성(active) 상태로 표시되어야 합니다. 자격 증명 검증 오류가 표시되면 어댑터 연결이 아직 열리지 않은 상태이므로, 메신저에서 테스트하기 전에 오류부터 해결하세요.

## 5. IM에서 Agent와 대화

테스트용 대화방에 봇을 초대한 뒤 메시지를 보내 보세요. 그룹 채팅에서는 아래처럼 명시적인 `@멘션`으로 대화를 시작합니다:

> @Ankole 어떤 일을 할 수 있고, 어느 팀을 지원하고 있나요?

실제 모델 응답이 돌아오는 것을 확인한 다음, 팀의 운영 방식에 맞춰 Agent 미션과 모델 프로필, 그룹 채팅 응답 정책을 세밀하게 조정하세요.

### Agent가 응답하지 않으면

경계를 하나씩 좁혀 가며 다음 순서대로 점검하세요:

1. 외부 플랫폼에서 최신 앱 버전이 게시되었고 테스트 사용자가 가용 범위에 포함되어 있는지 확인합니다.
2. 대상 채널, 팀 또는 대화방에 봇이 정상 설치·초대되었는지 확인합니다.
3. 필수 메시지 이벤트 구독과 권한 scope가 모두 켜져 있는지 확인합니다.
4. 라우팅 규칙이 활성 상태이며 의도한 대상 Agent를 가리키는지 확인합니다.
5. 대상 Agent에 `primary`, `light`, `heavy` 세 모델 프로필이 모두 설정되어 있는지 확인합니다.
6. LLM Provider 자격 증명과 모델 식별자가 유효한지 확인합니다.
7. **Console → Workers**에서 해당 Agent의 Worker가 준비(ready) 상태인지 확인합니다. 준비 상태가 아니라면 같은 화면에서 백엔드가 보고한 원인을 확인할 수 있습니다.

Docker Compose 환경에서는 `docker compose logs -f control-plane`으로 컨트롤 플레인 로그를 확인하고, `docker ps -a --filter label=ankole.installation=ankole`로 Worker 컨테이너 목록을 조회한 뒤 `docker logs CONTAINER_NAME`으로 개별 컨테이너 로그를 살펴보세요. Kubernetes 환경에서는 컨트롤 플레인 Pod와 Worker Pod 로그를 확인합니다. 로그를 점검할 때는 오류 메시지만 확인하고 환경 변수나 시크릿 값은 외부에 출력하지 마세요.

첫 응답까지 확인했다면 이어서 [Agents](../agents/), [Signal 라우팅 규칙](../signal-bindings/), [Background Agent Jobs](../background-jobs/) 가이드를 살펴보세요.
