一个事故复盘 agent 读事故的原材料——频道时间线、结构化日志、Brain 审计轨迹——起草一份无指责的复盘：时间线、影响、根因、促成因素、和行动项。本指南是那个 agent 的实际形态。

先把决定性的性质说清楚：agent **起草，不下结论**。它把原材料组装成结构化文档，但根因分析和行动项是供团队确认的提案。价值在于快速组装时间线和证据——复盘的前 80% 是纯数据收集——不在于最终判断。

## 需要什么

- **绑定 `primary` profile**——综合时间线和起草分析需要推理。
- **绑定 `embedding` profile**——Brain 召回找有类似模式的过往事故。
- **一个 signal binding** 到复盘草稿发帖的频道。
- **事故的原材料**——频道讨论（`may_intervene` 观察或粘贴的）、结构化日志（文件或抓取的批量）、Brain 审计轨迹。

## 复盘模板

agent 起草的无指责复盘：

```text
**复盘 — <事故> — <日期>**
**摘要**：<一段话发生了什么>
**影响**：<受影响用户、持续时间、严重度>
**时间线**：
- <时间>：<发生了什么>
- <时间>：<检测>
- <时间>：<响应开始>
- <时间>：<缓解>
- <时间>：<解决>
**根因**（提议）：<agent 的分析>
**促成因素**：<什么让它更糟或更难发现>
**做得好的**：<响应中有效的>
**行动项**（提议）：
- [ ] <预防行动> — 负责人：待定
- [ ] <检测改进> — 负责人：待定
- [ ] <响应改进> — 负责人：待定
```

"提议"标记是关键——agent 组装证据并提议分析，但团队确认根因并分配行动项。

## 工作流

1. **事故已解决**（或人在事故中请求草稿）。
2. **agent 读时间线**——从频道讨论、结构化日志、Brain 审计轨迹。
3. **agent 组装**——构建按时间顺序的时间线、识别检测到解决的差距、提取每步发生了什么。
4. **agent 提议**——根因（从证据和 Brain 的过往事故模式）、促成因素、做得好的、行动项。
5. **agent 发草稿**——带"提议"标记，请求团队复核和确认。

## 人设控制什么

- **语气**——"无指责。聚焦系统和流程，不聚焦个人。'出了什么问题'部分不写名字。"
- **深度**——"带时间戳的完整时间线"vs"只含关键里程碑的摘要时间线"。
- **行动项**——"提议预防、检测、响应改进。不分配负责人——团队做。"
- **召回**——"查 Brain 找有类似模式的过往事故。若这是复发，标记。"

## 一个完整示例

为团队事故频道设置复盘 agent：

1. 创建 agent，绑 `primary`/`heavy`/`embedding`。
2. 把 binding 的策略设为 `may_intervene`（让它观察事故展开）。
3. 撰写 `MISSION.md`："事故解决后，从频道时间线和日志起草无指责复盘。结构：摘要、影响、时间线、根因（提议）、促成因素、做得好的、行动项（提议）。查 Brain 找类似过往事故——复发则标记。发草稿请求复核。"
4. 事故解决时 @ agent："为今天的数据库宕机起草复盘。"
5. agent 读时间线、组装、提议、发草稿。

## 本指南不是什么

它不是根因权威——agent 提议；团队确认。它不是行动项跟踪器——agent 提议项；团队的任务系统分配。它也不是人工复盘的替代——草稿是起点；团队加只有人才有的上下文。
