在 Ankole Agent Harness 中，Agent 是能够持续自主开展工作的数字主体。每个 Agent 都拥有独立的职责使命、人工负责人、权限边界、可用工具、模型档案与专属文件空间，可在权限允许的范围内调取公司大脑（Brain）中的知识，并通过信号路由规则接收来自各渠道的消息与事件。

## 创建 Agent

1. 打开 **Console → 智能体**，点击「新增智能体」。
2. 输入显示名称，并核对自动生成的标识名（handle）。标识名后续仍可修改；点击保存时，Ankole 会自动分配一个全局唯一的不透明 UID。
3. 填写角色定位、可选头像 URL，并选择 Worker Provider。
4. 选择一名人员主体（Principal）担任 Agent 负责人，再选择群聊记忆披露模式。
5. 保存 Agent。页面随后会展开长期设定文档、模型档案与 Agent 专用环境变量的配置区域。

「角色」字段用于简要概括 Agent 承担的岗位职责（例如「研究分析师」或「客户支持」），而具体的职责边界、行事准则、视觉规范与保密要求，则由下文的四份长期设定文档分别管理。

「Worker Provider」决定该 Agent 归属的 [WorkerPool](../worker-management/)：创建请求未显式指定时默认使用站点默认资源池；若站点未配置默认池，创建将直接失败。此项绑定保存后不可更改。同一资源池内的不同 Agent 仍各自拥有独立的 Worker 实例与持久化 Home 目录；保存 Agent 配置不会立即启动实例，等到实际需要执行电脑环境工作时才由控制面按需拉起。

## 设置负责人和群聊披露模式

每个 Agent 都必须指定一名人工负责人。负责人有权查看由该 Agent 编写、持有，或将该 Agent 列为可见对象的 Brain 知识；但如果某条知识限定了特定权限组（Group）可见，而负责人本人不属于该权限组，负责人身份并不能绕过该权限组的访问限制。

群聊记忆披露模式决定了 Agent 在多人可见的对话中可以引用哪些记忆：

- **严格**：群聊中的每一位参与者都必须处于该条记忆的可见范围内，Agent 才能在群内引用。
- **宽松**：系统仅校验当前提问者的访问权限，群内其他参与者不影响可见知识范围。

在单人私聊中，两种模式的行为一致。建议仅在群组成员明确接受宽松共享规则时选择「宽松」，其余场景一律选择「严格」。完整的知识权限与披露模型请参阅 [Brain](../brain/)。

## 设置长期文档

打开 Agent 编辑页中的 **MISSION / SOUL / DESIGN / CONFIDENTIALITY POLICY** 标签页：

| 文档 | 填写内容 |
|---|---|
| `MISSION.md` | Agent 存在的目的、负责的具体工作，以及交付完成的判定标准 |
| `SOUL.md` | 沟通方式、判断原则，以及面对信息不全或不确定情况时的行动准则 |
| `DESIGN.md` | Agent 制作网页、幻灯片、文档、图表等视觉内容时遵循的设计系统 |
| `ConfidentialityPolicy.md` | Agent 主动向 Brain 写入知识时如何选择受众可见范围 |

`DESIGN.md` 遵循标准的 <a href="https://www.designmd.co/about" target="_blank" rel="noreferrer">DESIGN.md 格式</a>：YAML frontmatter 保存颜色、字体、间距、圆角和组件等设计令牌（Design Tokens），Markdown 正文说明视觉原则与排版用法。Ankole 内置了一套默认设计系统，管理员也可在 **Console → 智能体 → DESIGN** 中将其替换为企业自身的品牌规范。

请勿将业务流程、权限边界或行为准则写入 `DESIGN.md`——这些内容应分别归入 `MISSION.md`、`SOUL.md`、`ConfidentialityPolicy.md` 或具体的 Skill。此外，`ConfidentialityPolicy.md` 仅指导 Agent 主动向 Brain 写入知识时的范围判定；系统从日常聊天中自动提炼记忆时，可见范围固定由对话参与者决定。初次编写长期文档时应尽量简明扼要，待实际工作中暴露具体问题后，再按需补充对应规则。

文档保存后将从后续新开启的对话起生效，当前正在执行的工作仍继续使用启动时读取的版本。

## 配置模型

在同一编辑页的「模型档案」区域，至少需要配置 `primary`、`light` 和 `heavy` 三个核心档案，分别用于日常对话、轻量任务与复杂深度推理。初次接入时，可以先为这三个档案选择同一个已验证可用的模型。

其余档案按实际业务需求选配：

- 需要识别和读取图片时，配置 `vision_fallback`。
- 需要搜索互联网或读取公开网页时，配置 `web_search` 和 `web_fetch`。
- 需要生成图片时，配置 `image_generate`。
- 后台 Agent 任务需要使用独立的模型提供商或特定模型时，配置「后台 Agent 任务」（ChatGPT 订阅额度同样通过 [ChatGPT 订阅 Provider](../chatgpt-subscription-provider/) 在此处选择）。

配置档案时，先选择模型提供商，再选择或手动输入模型名称。选定提供商后，表单会显示「上下文长度」字段；留空时自动采用该提供商与模型的默认值。

「高级设置」仅展示当前所选提供商声明支持的选项：其中「推理摘要」仅适用于 Responses API，「回答详略」设置输出的默认详略程度，「服务等级」用于覆盖当前模型档案请求的服务等级。各选项的可用值取决于上游提供商、账号权限与具体模型；字段留空时一律沿用提供商默认值。

有关模型提供商接入与首次配模的完整步骤，请参阅 [快速开始](../quickstart/#3-添加模型提供商并创建-agent)。

## 设置 token 额度

模型档案旁的 **Token 额度**区域用于限制该 Agent 在单个循环周期内允许消耗的 Token 总量。启用时需设定周期长度（天）、周期起始时间和 Token 上限；未设置额度的 Agent 不受此限制。

配置后，面板会以进度条展示当前已用 Token 数、占上限的比例以及当前周期的起止时间。Ankole 按上游提供商为该 Agent 每次模型调用报告的输入 Token 与输出 Token 之和进行统计，涵盖计划任务回合、Workflow、后台 Agent 任务，以及由这些调用触发的上下文压缩；但 Brain 内部模型调用、向量嵌入（Embedding）、网页工具、图片生成，以及人类成员使用个人凭证发起的请求均不计入。

一旦消耗达到上限，该 Agent 收到新的聊天消息后将不再正常作答，而是自动回复一条说明已用 Token、配额上限及本周期结束时间的提示；与此同时，该 Agent 名下的后台 Agent 任务会直接失败，不会挂起等待下一个周期。由于配额检查在每次模型调用发起前执行，触发阈值的最后一次调用可能会因当次消耗而略微超出上限。被拦截的聊天消息不会自动重放，待周期结束后由用户重新发送即可。

点击**重置周期**会立即开启一个新周期，让 Agent 不必等到原周期结束即可恢复工作；点击**取消额度**则会移除配额限制。无论执行哪种操作，历史用量记录都会保留以备审计。更多成本管控手段请参阅 [成本管理](../cost-management/)。

## 配置能力和环境变量

新建的 Agent 默认继承当前租户启用的 Agent Plugin 和 Skill。需要调整时，可打开 **Console → Agent 能力库**修改租户默认设置，或为该 Agent 单独设置覆盖开关，具体方法见 [Agent 能力库](../skills/)。

如果某项 Skill、命令行工具或 MCP 服务需要外部 API 密钥，可在 Agent 编辑页的「环境变量」中添加。此处添加的专属变量仅对当前 Agent 可见，优先级高于同名的租户变量（租户未设置时则覆盖同名站点变量），具体方法见 [环境变量](../worker-env/)。

## 接入聊天渠道

在内置的 **Pod Chat** 中，工作区成员可以直接与启用状态的 Agent 发起私聊（`dm`），或将其拉入群组会话（`group`），无需配置信号路由规则（Signal Binding）。

信号路由规则专用于管理外部 IM 渠道与专用邮箱。如需让该 Agent 接收来自 Slack、Microsoft Teams、飞书（Lark）、钉钉、企业微信、Telegram、Discord、LINE、WhatsApp 或专用邮箱的消息，请打开 **Console → 信号路由**，选择聊天应用与目标 Agent 建立绑定。一个聊天应用可以配置多条路由规则分发给不同 Agent，也可以为不同 Agent 分别创建独立的机器人应用，详见 [信号路由规则](../signal-bindings/)。

## 修改或停用

Agent 的显示名称、角色定位、长期设定、模型档案与可用能力均可随时修改；而 UID 是其他配置引用该 Agent 的唯一稳定标识，创建后不可修改。

停用 Agent 后，它将停止接收新工作，并在智能体列表中显示为「已停用」状态；已停用的 Agent 可随时重新启用。只有处于「已停用」状态的 Agent 才允许永久删除，且永久删除会一并清除关联的会话、任务与历史记录。如果只是想暂停某个外部聊天入口，停用对应的信号路由规则即可。

## Agent 没有回复时

若发送消息后未收到回复，请按以下顺序逐项排查：

1. 确认该 Agent 处于「已启用」状态。
2. 确认 `primary`、`light`、`heavy` 三个核心模型档案均已配置，且关联的 LLM Provider 可用。
3. 若从外部渠道发信，确认信号路由规则已指向当前 Agent。
4. 打开 **Console → 工作节点**，检查该 Agent 的 Worker 是否处于「就绪」状态，或正在正常启动且无失败原因。
5. 打开 **Console → 会话**，确认刚才的消息是否已进入会话列表。
6. 检查页面是否显示了具体的报错信息。

针对特定外部聊天渠道的排查方法，请参阅 [快速开始的故障排查部分](../quickstart/#agent-没有回复时)。
