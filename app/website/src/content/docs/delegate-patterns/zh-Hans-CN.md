agent 会委派之后，问题就从*怎么委派*变成*用哪种形态*。本指南编目后台任务工具支持的委派模式，并说明各自适合什么。它建立在[后台研究任务](../background-research-job/) walkthrough 之上——那一篇端到端覆盖一种模式；这里把它们全部命名。

先把决定性的性质说清楚：委派是 agent 的决定，在回合里用自己的工具做。你不在 Console 里派生任务。你的活是把请求范围说清，让 agent 选对模式；agent 的活是把它翻译成正确的工具调用。

## agent 的委派工具

六个工具，各自一个独立动作：

| 工具 | 做什么 |
|---|---|
| `create_background_job` | 派生一个新任务（`title`、`task`、可选 `workspace_template_id`） |
| `list_background_jobs` | 列出任务，可选按 `status` 过滤 |
| `show_background_job_details` | 读取一个任务的详情和近期轨迹 |
| `send_message_to_background_job` | 向运行中或等待中的任务发消息（`wait_reply` 控制是否阻塞等回复） |
| `respawn_background_job` | 从一个终态任务创建新任务继续（`source_job_id`、`message`） |
| `stop_background_job` | 取消一个任务 |

agent 决定调哪个、何时调。下面的模式是这个决定所取的形态。

## 模式 1：发后即忘

agent 派生一个任务，不等它。用于人要的东西耗时，而一句即时确认就够。

- **形态**：`create_background_job`，频道里一句短回复（"在做了，完成了发"），回合结束。
- **任务回报**，当它完成（`background_agent_job.completed`）、失败（`…failed`）或需要输入（`…waiting`）时。
- **适合**：研究、摘要，任何人不需看着工作发生的场景。

这是[后台研究任务](../background-research-job/)的模式。它是默认；当它不合身时才伸手拿其它。

## 模式 2：问后等

agent 派生一个任务，然后在同一回合里向它发消息并阻塞等回复。用于 agent 需要任务的中间输出来回答人。

- **形态**：`create_background_job`，然后 `send_message_to_background_job`，`wait_reply: true`。
- **回合保持开启**，直到任务回复，于是人看到的是一个答案，不是一次交接。
- **适合**："总结这个 thread，然后把摘要翻译"——翻译需要摘要先有。

风险是把回合长时间开着；任务慢的话，偏向发后即忘，让任务自己发结果。

## 模式 3：从已完成的任务继续

一个任务完成了——成功或失败——而人想把它往前推，而不重述整个任务。agent 从终态任务重生，带着它的上下文。

- **形态**：`respawn_background_job`，带旧任务 id 和描述下一步的短 `message`。
- **新任务**继续源任务的工作空间和轨迹；人不必重新解释。
- **适合**："你昨天研究了 X——现在对 Y 做同样的事"，或"那次失败的运行，带着这个改动重试"。

这正是为什么任务是持久的、不是子进程：一个终态任务仍是有效的起点。

## 模式 4：观察并引导

人观察任务进度，并在中途引导——回答问题、改方向、收窄范围。

- **形态**：任务移到 `waiting_on_user` 并发一个问题；人在频道里回答；agent 用答案调 `send_message_to_background_job`（或拥有它的回合续接它）；任务继续。
- **重复**，按任务需要决策的次数。
- **适合**：方向事先未知的探索性工作，或人的判断比 agent 的猜测更便宜时。

杠杆是人设：问得太勤的任务烦人；从不问的会漂。在 mission 里告诉 agent 何时问、何时自己决定。

## 模式 5：限定范围的工作空间

有些工作需要预备好的工作空间——一个 checkout 的仓库、一个文档模板、一条配好的工具链。当工作需要时，agent 在 `create_background_job` 上挑一个 `workspace_template_id`。

- **形态**：`create_background_job`，带 `workspace_template_id: "<template-id>"`。
- **模板**是 plugin 声明的工作空间；agent 看得到有哪些模板、各自做什么。
- **适合**：对着真实 checkout 的编码任务、对着模板的文档生成，任何"从零开始"会浪费头十次工具调用的事。

若没有模板合身，agent 省略该字段，任务不带模板跑。模板是一种能力，不是要求。

## 选一个模式

一份简短决策指南，按 agent 实际做决定的顺序：

1. **人现在就需要答案吗？** 是且短，别委派——在回合里答。是且长，用问后等，并留意回合长度。
2. **工作需要预备好的工作空间吗？** 是，挑对的 `workspace_template_id`。
3. **工作途中会需要人的判断吗？** 会，为观察并引导做准备；把"何时问"的规则写进人设。
4. **工作是某个已跑过的东西的延续吗？** 是，从源任务重生。
5. **否则**——发后即忘，让任务自己回报。

## 委派不是什么

它不是让 agent 更快的途径——工作该花多久就花多久，一个跑一小时的任务，无论你看着不看着，都花一小时。它不是第二个 agent；任务作为派生它的那个 agent 运行，在那个 agent 的权限和凭证下。它也不是好的范围界定的替代；一个范围糟糕的任务就是范围糟糕的任务，上面的模式不修这一点——请求才修。
