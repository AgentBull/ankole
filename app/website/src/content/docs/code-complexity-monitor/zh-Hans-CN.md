一个代码复杂度监控 agent 对代码库跑复杂度分析器、跟踪哪些函数和模块随时间变得更复杂、在变得不可维护前报告趋势热点。本指南是那个 agent 的实际形态。

先把决定性的性质说清楚：agent **跟踪趋势不是快照**。单次复杂度测量什么都说不；趋势告诉你"这个函数六个月前圈复杂度 15，现在是 28"。价值在于检测轨迹——正在变糟的代码，不是已经糟的代码。

## 需要什么

- **WorkerEnv 里的 git 凭证**（`GIT_TOKEN`）。见 [Git 集成](../git-integration/)。
- **绑定 `primary` profile**——识别哪些复杂度热点要紧需要推理。
- **一个 signal binding** 到复杂度报告发帖的频道。
- **一个复杂度工具**——语言的复杂度分析器（见下）。

## 复杂度工具

| 语言 | 工具 | 测量什么 |
|---|---|---|
| TypeScript/JavaScript | `complexity-report`、`typhon-cli` | 每函数圈复杂度 |
| Python | `radon cc`、`mccabe` | 每函数圈复杂度 |
| Elixir | `cyclomatic` hex 包 | 每函数圈复杂度 |
| Rust | `cargo clippy` 警告 | 认知复杂度提示 |

agent 跑工具、读输出、与上次运行的基线比较（存在 Brain 或文件中）。

## 工作流

1. **复杂度检查触发**——每周或大变更后。
2. **agent 跑复杂度分析器**——每个函数：圈复杂度、代码行数、参数数。
3. **agent 与基线比较**——哪些函数自上次检查以来复杂度增加了？
4. **agent 识别趋势热点**——复杂度增加超过阈值的函数。
5. **agent 报告**——趋势热点、增量、和建议的简化目标。

## 趋势报告

```text
**复杂度趋势 — <日期>**

**趋势上升**（自上次检查复杂度增加）：
- `src/payments.ts` 的 `processPayment()`：18 → 24（+6）。建议：提取验证块。
- `src/webhooks.ts` 的 `handleWebhook()`：12 → 17（+5）。建议：拆分 provider switch。

**高但稳定**（复杂，但没变糟）：
- `src/reports.ts` 的 `generateReport()`：31（3 次检查稳定）。非趋势——低优先级。

**已改善**（复杂度降低）：
- `src/auth.ts` 的 `authenticate()`：22 → 16（-6）。最近的重构有效。
```

"趋势上升"部分是可行动的——这些是正在变糟、需要在越过可维护性阈值之前关注的函数。

## 人设控制什么

- **阈值**——"报告圈复杂度 > 15 的函数，或自上次检查增加 > 3 的任何函数。"
- **基线**——"把基线作为知识条目存在 Brain 里。与上一个已知基线比较，不是与固定目标比较。"
- **范围**——"所有源文件"vs"仅自上次检查以来修改的文件"。
- **不做什么**——"不重构。报告趋势和建议目标。不改代码。"

## 一个完整示例

为 TypeScript repo 设置每周复杂度监控：

1. 在 WorkerEnv 存 `GIT_TOKEN`。
2. 创建 agent，绑 `primary`/`coding` + `embedding`（基线召回）。
3. 撰写 `MISSION.md`："用 `npx typhon-cli src/` 跑复杂度分析。与上周基线（存在 Brain）比较。报告趋势上升（增加 > 3）的函数。每个趋势函数建议一个简化目标。不重构。发报告。"
4. 加一条每周调度：`cron: "0 7 * * 1"`。
5. agent 跑、比较、识别趋势、发报告。

## 本指南不是什么

它不是重构工具——agent 报告趋势；人重构。重构见[重构助手](../refactoring-assistant/)。它不是代码质量评分——复杂度是一个维度；可读性、可测试性、和正确性更重要。它也不是门控——它报告；团队决定行动什么。
