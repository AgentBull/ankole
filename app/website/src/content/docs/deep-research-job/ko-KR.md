Deep Research는 문헌 검토, 경쟁사 조사, 다중 소스 팩트 체크, 여러 가설을 비교해야 하는 예측, 그리고 실제 결과가 나온 뒤 과거 예측을 복기하는 작업을 위해 설계되었습니다. 이처럼 반복적인 검색과 독해, 교차 검증이 필요한 작업을 만나면 Agent는 이를 [Background Agent Job](../background-jobs/)으로 넘기고 현재 대화에서는 사용자의 다른 요청을 계속 처리합니다.

단순히 웹 페이지 몇 곳을 검색해 요약하는 것과는 방식이 다릅니다. 각 Job은 독립된 영속 워크스페이스에서 단계별로 진행됩니다. 먼저 조사 계획을 세우고, 병렬로 자료를 모아 출처 노트로 기록한 뒤, 확보된 근거로부터 결론을 도출하고, 연구 과정을 전혀 보지 못한 독립 검증자(verifier)에게 보고서를 넘겨 검토받으며, 마지막으로 모든 성공 기준을 충족했는지 대조(audit)합니다. 깊이 있는 연구에는 보통 30~90분이 걸리므로, 빠른 답변만 필요할 때는 Deep Research 대신 일반 대화로 바로 질문하세요.

## 시작하기 전에

먼저 [Quick start](../quickstart/)를 마치고 Agent가 채팅 채널에서 정상 응답하는지 확인하세요. 공개 웹 페이지를 검색하고 읽어야 한다면 `web_search`와 `web_fetch` 모델 프로필도 함께 연결해 두어야 합니다.

Deep Research Job은 항상 AIGateway를 통해 모델을 호출합니다. ChatGPT 구독 용량을 활용하려면 [ChatGPT subscription provider](../chatgpt-subscription-provider/)를 등록한 뒤 **Console → Agents → Background Agent Jobs**에서 선택하세요.

또한 해당 Agent에 활성화되어 있고 Background Agent Jobs 사용이 허용된 모든 Skill은 Job에도 자동으로 제공됩니다. 예를 들어 금융 데이터 인터페이스나 사내 시스템 연동 같은 데이터 소스 Skill이 켜져 있다면, 별도로 승인할 필요 없이 Job이 공개 웹 검색에 앞서 해당 데이터 소스를 먼저 활용합니다.

## 연구 시작하기

조사 주제, 시간 범위, 근거 규칙, 원하는 결과물 형식을 명시해 백그라운드 실행을 요청하세요.

```text
Run this as a Deep Research Background Agent Job.
Compare the pricing and product updates from these three vendors over the last
two quarters. Cite primary sources, separate facts from inference, and return
a report with links. Ask me before you expand the scope or use paid data.
```

### 생성 전 명확화

한 줄짜리 요청만 받고 곧바로 Job을 시작하지는 않습니다. Agent는 Job을 생성하기 전에 연구 목표와 활용처, 성공 기준, 조사 범위와 시간 경계, 근거 규칙, 결과물 형식 등 아직 확정되지 않은 사항을 하나씩 질문하며 추천 선택지를 함께 제시합니다. 이때 시스템 환경에서 스스로 확인할 수 있는 사실은 직접 조회하고, 사람의 의사결정이 꼭 필요한 항목만 사용자에게 묻습니다. Job은 사용자의 확인을 거친 뒤에 생성됩니다.

이 짧은 확인 과정은 충분한 가치가 있습니다. 연구 방향을 잘못 잡으면 이후 60분 동안의 자료 수집과 분석을 통째로 허비하게 되지만, 사전 질문 하나는 한 문장만으로도 바로잡을 수 있기 때문입니다.

만약 사전 문답을 건너뛰고 싶다면 “질문하지 말고 바로 Job을 생성하고, 나머지는 알아서 판단해 주세요”라고 말하세요. 그러면 Agent가 어떤 가정을 세웠고 어떤 선택을 Job에 위임했는지 밝힌 뒤 곧바로 Job을 생성합니다.

### 좋은 요청이 담아야 할 것

막연히 “깊이 조사해 줘”라고 하기보다 범위를 구체적으로 짚어 줄수록 원하는 보고서에 가까워집니다. 요청에 다음 항목을 포함해 보세요.

- **주제와 답해야 할 핵심 질문.** 토픽 이름만으로는 부족합니다. 예를 들어 “재생에너지 산업을 분석해 줘”라는 요청과 “이 세 벤더 중 향후 두 분기 안에 가격을 인하할 가능성이 가장 높은 곳은 어디이며 그 근거는 무엇인가?”라는 요청에서는 완전히 다른 보고서가 나옵니다.
- **시간 범위와 정보 컷오프 시점.** 사후 복기나 특정 시점 기준의 예측 재구성 작업에서는 컷오프 이후에 알려진 정보를 Job이 사용할 수 있는지가 이 설정에 따라 결정됩니다.
- **근거 규칙.** 1차 출처만 사용할지, 인용을 필수로 할지, 사실과 추론을 엄격히 구분할지 등을 지정합니다.
- **분석 방법론(선택 사항).** 예를 들어 경쟁 가설 분석(ACH)으로 대안들을 비교하거나, 역사적 사례 기반의 전향적 분석(analogical foresight)을 쓰도록 지정할 수 있습니다. 지정하지 않으면 Job이 질문 성격에 맞춰 스스로 선택합니다.
- **결과물 형식과 언어.** 기본 결과물은 Markdown 보고서입니다. PDF, PPT, 웹 페이지를 요청하면 Markdown 원본을 함께 달라고 명시하지 않는 한 요청한 형식만 반환하며, 별도 스타일 지침이 없으면 Agent의 `DESIGN` 시각 규칙을 따릅니다.
- **운영 경계.** 예산 한도, 유료 데이터 소스 사용 여부, 조사 범위 확장 조건, 마감 시한 등을 명시합니다.

분량 지정은 엄격한 제한을 요청하지 않는 한 대략적인 목표치로 해석됩니다. 예를 들어 “3페이지 분량 PDF”라고 적으면 약 3페이지 안팎으로 작성합니다.

## Job의 작동 방식

내부 진행 방식을 알아 두면 중간 상태를 읽고 결과물의 신뢰도를 가늠하거나 후속 질문을 던지기가 훨씬 수월해집니다. 모든 Deep Research Job은 전용 영속 워크스페이스에서 네 단계를 거칩니다.

### 1. 계획

Job은 먼저 워크스페이스에 있는 Playbook 목록을 확인하고 이번 질문에 해당하는 방법론 문서를 읽습니다. 조사 범위가 넓거나 주제가 아직 모호할 때, 또는 모델의 학습 시점 이후에 관련 사실이 바뀌었을 가능성이 있을 때는 서브에이전트 하나를 먼저 보내 빠른 사전 탐색을 수행합니다. 이 탐색 단계에서는 본격적인 근거 수집이나 결론 도출을 하지 않고, 주제의 현재 정의와 경계를 파악하며 모델이 놓치기 쉬운 핵심 개념, 분석 축, 검색어, 데이터 소스를 찾아냅니다.

사전 탐색이 끝나면 이를 바탕으로 세부 수집 계획을 세웁니다. 탐색을 계획보다 먼저 실행하는 이유는 모델 기억 속의 오래된 정보가 아니라 현재 시점의 실제 사실 위에서 출발하기 위해서입니다.

### 2. 증거 수집

여러 서브에이전트가 수집 계획을 병렬로 실행합니다. 유의미한 자료는 모두 `sources/` 아래에 개별 Markdown 노트로 저장되며, 파일 상단 YAML 프런트매터에 출처, 발행 시각, 작성자, 신뢰도, 원문 링크를 기록합니다. 이후 이어지는 모든 분석은 일회성 검색 결과에서 받은 인상이 아니라 이 소스 노트들을 근거로 인용합니다.

자료 수집은 단일 소유권 규칙을 따릅니다. 각 데이터 소스와 1차 문서마다 담당 서브에이전트(owner)를 하나만 두어 한 번만 수집하고 파일로 기록하게 하며, 다른 서브에이전트들은 같은 요청을 반복하는 대신 저장된 파일을 읽습니다. 공시 자료나 제출 서류, 데이터셋도 각각 한 번만 내려받고 식별자 기반 파일명을 붙여 후속 서브에이전트가 바로 찾을 수 있게 합니다. 또한 도구가 목록 입력을 지원하면 여러 번 나누어 호출하지 않고 한 번에 배치로 요청합니다.

활성화된 Skill 데이터 소스는 항상 공개 웹 검색보다 우선합니다. Job은 먼저 Skill 문서를 읽고 해당 인터페이스로 데이터를 조회하며, Skill이 다루지 않는 영역이거나 호출 결과 데이터가 비어 있는 항목에 한해서만 `web_search`나 `web_fetch`를 사용합니다. 정식 데이터 인터페이스로 가져와야 할 수치를 공개 웹 페이지에서 어림짐작으로 대체하지 않으며, 어떤 Skill로도 확보하지 못한 항목은 조용히 넘기지 않고 `sources/`에 근거 공백(evidence gap)으로 명시합니다.

물론 모든 근거가 검색에서만 나오는 것은 아닙니다. 필요할 때는 원시 데이터를 가공하는 스크립트를 직접 작성해 구조화된 데이터에서 필요한 지표를 산출합니다. 1차 정리가 끝나면 빠진 정보나 상충하는 자료가 없는지, 다음 분석 단계에 필요한 맥락이 충분한지 점검하고 부족한 부분을 추가로 수집합니다.

### 3. 분석 및 검증

결론은 확보된 근거로부터 단계적으로 도출되어야 하며 빈틈없는 논리 사슬을 이루어야 합니다. 결론을 미리 정해 놓고 입맛에 맞는 자료만 골라 담지 않으며, 보고서 본문에서도 사실, 의견, 가설, 추론을 명확히 구분합니다. 현재 확보된 근거가 두 가지 이상의 해석을 허용할 때는 가능한 해석을 모두 제시한 뒤 어느 쪽에 무게를 두는지와 신뢰도 수준을 함께 밝힙니다. 뉴스 기사나 마케팅성 주장은 비판적으로 검토하며, 작성 과정 전반에서 확증 편향, 표본 편향, 서사 오류(narrative fallacy)를 경계합니다.

초안이 준비되면 독립 검증자(verifier)가 분석을 검토합니다. 검증자는 이전 대화 턴을 물려받지 않고 Job의 비공개 작업 상태 파일도 보지 못한 채, 오직 보고서 본문과 사용자의 연구 목적만 전달받아 형식과 내용을 함께 점검합니다. 형식 면에서는 사실·의견·가설이 분리되어 있는지, 인용이 충분한지, 실질적인 정보 가치가 담긴 결론을 제시하는지 확인합니다. 내용 면에서는 비판적 관점에서 논리의 내적 일관성, 대안 설명의 가능성, 인과관계 역전 여부, 그리고 결론을 먼저 정해 놓고 근거를 사후에 끼워 맞춘 오류(화살을 쏜 뒤 과녁을 그리는 오류)가 없는지를 집중 검토합니다.

다만 검증자는 조언을 제공할 뿐 최종 판단 권한까지 갖지는 않습니다. 실질적인 이견이 제기되면 분석과 보고서를 수정하거나, 수정하지 않을 경우 그 이유와 함께 이견 자체를 보고서에 그대로 남깁니다. 쟁점을 어설픈 합의로 무마하지 않습니다.

### 4. 전달

최종 전달은 성공 기준 대조(audit)로 시작합니다. 보고서는 사전에 정의한 모든 성공 기준에 답해야 합니다. 출처가 뒷받침된 근거로 기준을 충족하든가, 아니면 채우지 못한 공백으로 명시하고 결론에 미치는 영향을 밝혀야 합니다. 만약 핵심 공백이 연구 목적 자체를 흔들 정도이고 시간 여유가 남아 있다면, 확보 가능한 추가 근거를 더 수집합니다. 보고서가 너무 늦어지면 내용이 부실할 때 못지않게 연구 목적을 달성하기 어렵기 때문에 시간 경계 안에서 판단합니다.

기준 대조를 마치면 요청받은 형식으로 최종 결과물을 생성하고, 서브에이전트 하나에 넘겨 가벼운 마무리 점검을 거칩니다. 보고서는 사용자가 요청한 언어로 작성되며, 조지 오웰의 여섯 가지 글쓰기 원칙을 따르고 불필요한 면책 문구를 덧붙이지 않습니다.

### 작업 상태, 복구, 재시작

Job은 워크스페이스의 `research-state.md` 파일에 비공개 작업 상태를 기록합니다. 여기에는 각 성공 기준과 달성 현황, 근거가 아직 부족한 후보 결론, 기각한 접근 방향과 그 사유, 수집된 자료의 타당성에 관한 미해결 우려 사항이 담깁니다. 이 파일은 최종 결과물이 아니라 내부 작업 기억일 뿐이며, 검증자가 연구자의 추론 흐름에 끌려가지 않고 독자적인 시각을 유지할 수 있도록 어떤 검증자에게도 공개하지 않습니다.

이 상태 파일 덕분에 작업 연속성도 보장됩니다. 실행 도중 Worker가 재시작되거나 컨텍스트가 끊기더라도 Job은 `research-state.md`를 읽고 이어서 진행하며, 이미 확정된 내용을 처음부터 다시 탐색하지 않습니다.

만약 조사 도중 애초의 분석 틀(frame) 자체가 잘못되었다는 사실(주제 오인, 질문 오독, 핵심 전제 붕괴 등)이 드러나면 기존 분석을 임시방편으로 기워 쓰지 않습니다. 수정된 분석 틀을 `research-state.md`에 기록하고, 잘못된 전제 위에서 도출된 분석을 폐기한 뒤 영향받는 단계를 다시 밟습니다. 이때 이미 모아 둔 `sources/` 자료는 유지하되, 바뀐 틀에서 새로 필요해진 부분만 추가로 수집합니다. 잘못된 전제 위에 보고서를 완성하면 작업 전체가 무용지물이 되므로, 도중에 틀을 바로잡고 다시 수행하는 편이 훨씬 경제적입니다.

## Playbook: 플러그 가능한 연구 방법

Playbook은 Job 워크스페이스의 `playbooks/` 디렉터리에 들어 있는 방법론 파일로, `deep-research` Agent Plugin의 워크스페이스 템플릿에 포함되어 배포됩니다. 각 Playbook 파일 상단에는 어떤 유형의 질문에 적용할지가 선언되어 있으며, Job은 계획 단계에서 전체 Playbook 목록을 훑어보고 관련 있는 파일을 읽어 들입니다.

Playbook은 단순한 참고 팁이 아니라, 기본 분석·검증·보고서 작성 절차를 고유한 프로토콜로 통째로 대체할 수 있는 실행 규약입니다(예를 들어 ACH Playbook은 기본 단일 패스 검증을 3단계 검증으로 대체합니다). 연구 방법이 모델 가중치나 애플리케이션 코드에 고정되어 있지 않고 파일로 분리되어 있으므로 언제든 교체하고 확장할 수 있습니다.

기본 템플릿에는 두 가지 범용 방법론이 내장되어 있습니다.

### ach: 경쟁 가설의 분석(Analysis of Competing Hypotheses)

정보가 불완전하거나 상충하고, 심지어 의도적인 왜곡 가능성까지 있을 때 중요한 예측이나 원인 진단을 내리려면 그럴듯한 여러 설명을 나란히 놓고 비교해야 합니다. ACH는 이 비교 과정을 명시적인 구조로 드러내어 판단 근거를 사후에 감사할 수 있게 해 줍니다. 물론 부실한 근거 자체를 좋은 근거로 바꾸어 주거나 사용자를 대신해 정답을 계산해 주지는 않습니다.

정답이 하나로 명확히 떨어지는 단순 사실 확인에는 ACH가 필요하지 않습니다. 또한 신뢰할 만한 데이터와 적절한 통계·인과 모델로 바로 답할 수 있는 문제라면 해당 모델을 직접 사용해야지 ACH로 대체해서는 안 됩니다.

**가설을 증거보다 먼저 세웁니다.** Job은 먼저 정확한 핵심 질문과 정보 컷오프 시점을 정의하고, 예측 과제라면 예측 기간(horizon)과 결과 판정 기준까지 명시합니다. 그런 다음 개별 증거를 평가하기 전에 합리적인 가설을 모두 나열합니다. 이 순서를 지켜야 처음 떠오른 그럴듯한 설명 하나가 분석 전체를 지배하는 현상을 막을 수 있습니다. 모든 가설은 동일한 기간과 분석 수준에서 같은 질문에 답해야 하며, 가설들이 상호 배타적인지 그리고 현실적인 가능성을 빠짐없이 포괄하는지도 함께 밝힙니다. 의무적으로 채워야 하는 가설 개수는 없으며, 비교 결과 수정할 이유가 생길 때까지 각 가설을 유지합니다. 뒷받침하는 근거가 아직 부족하다는 사실만으로는 반증이 되지 않기 때문입니다.

**증거는 도구가 검증할 수 있는 행렬(matrix)에 기록합니다.** Job은 가설 간 비교 결과를 담는 단일 파일 `competing-hypotheses.yaml`을 관리합니다. 각 행(row)은 모든 가설에 대조해 평가할 수 있는 단일 명제—직접 관찰 사실, 보도된 주장, 당연히 나타났어야 하나 포착되지 않은 부재 신호, 분석상 가정, 논리적 추론, 또는 기저율(base rate)—를 나타냅니다. 행마다 실제 명제 유형, 로컬 출처 경로 또는 분석 근거, 출처의 신뢰 자격을 함께 적습니다. 출처 본문에 “~로 추정된다”고 적혀 있다면 이는 추정일 뿐 확정된 사실로 기록하지 않습니다. 작성 후에는 다음 구조 검사 스크립트를 실행합니다.

```bash
bun tools/ach_check.ts
```

이 검사기는 필수 필드 누락이나 잘못된·존재하지 않는 로컬 소스 경로만 찾아낼 뿐, 가설의 타당성이나 명제의 진위, 출처의 뒷받침 여부, 관계 판정의 적절성은 평가하지 않습니다. 기계적으로 확인할 수 있는 형식 검증은 도구가 맡고, 실질적인 판단은 모델과 사용자에게 남깁니다.

**단순 지지 건수가 아니라 판별력(diagnosticity)으로 비교합니다.** 각 행을 평가할 때 Job은 “이 증거가 가설을 증명하는가?”라고 묻는 대신 “만약 이 가설이 참이라면 이 정보가 관찰될 가능성이 얼마나 자연스러운가?”를 묻습니다. 관계 라벨은 `expected`, `compatible`, `tension`, `contradicts`, `unknown`, `not applicable` 여섯 가지만 사용하며 각각 짧은 근거를 덧붙입니다. 판별력은 한 행 안에서 가설 간 평가가 갈릴 때 나타나므로, 특정 가설 열을 세로로 훑기 전에 각 행을 가로로 먼저 비교합니다. 모든 가설과 두루 부합(`compatible`)하는 정보는 배경 사실로서 중요할지 몰라도 가설을 가려내는 데는 거의 기여하지 못합니다.

**출처 의존성과 채널 커버리지를 점검합니다.** 같은 원문을 베껴 쓴 여러 기사는 출처가 하나일 뿐입니다. 단일 사건에서 파생된 여러 지표나 한 데이터셋에서 뽑아낸 여러 통계치 역시 서로 독립된 근거가 아닙니다. 상관관계가 있는 행들을 남겨 세부 맥락을 보존할 수는 있어도 독립된 지지 근거가 늘어난 것처럼 합산해서는 안 됩니다. 채널 커버리지 역시 놓치기 쉬운 대목입니다. 가설마다 흔적이 남는 경로(channel)가 다른데, 특정 가설의 증거가 아직 아무도 뒤져 보지 않은 채널에 있다면 비교 결과는 실제 현실이 아니라 검색 범위의 편향을 보여 줄 뿐입니다. 따라서 각 가설마다 흔적이 나타날 법한 채널을 명시하고, 해당 채널을 직접 조사하거나 미조사 영역을 커버리지 공백으로 기록합니다.

**부재 신호와 핵심 지렛대(linchpin)를 검증합니다.** 예상했던 신호가 나타나지 않았다는 사실은, 그 신호가 실제로 관찰 가능한 성격이었고 조사 과정에서 충분히 포착할 수 있었을 때만 부정적 증거로 인정됩니다. 아울러 결론을 좌우하는 소수의 핵심 증거(linchpin)와 핵심 가정을 추려내어 각각을 집중 검증합니다. 만약 그 항목이 거짓이거나 오해를 부르거나 불완전할 때, 다른 항목에 종속되어 있을 때, 혹은 의도적인 기만일 때 최종 판단이 어떻게 달라지는지를 따져 봅니다. 결론의 신뢰도는 모아 놓은 자료의 분량이 아니라 가설 포괄 범위, 근거의 질, 출처 독립성, 민감도에 좌우됩니다.

**점진적 정보 공개를 통한 3단계 검증을 거칩니다.** ACH는 기본 검토 절차를 전용 3단계 프로토콜로 대체합니다. 동일한 검증자가 세 차례 패스를 수행하되, 정보를 공개하는 순서 자체가 객관성을 지키는 안전장치 역할을 합니다.

1. **Pass A: 원천 자료 기반의 독립 재구성.** 검증자에게는 사용자의 연구 목적, 정확한 ACH 질문, 정보 컷오프 시점, 그리고 `sources/` 디렉터리 접근 권한만 주어집니다. 가설 행렬이나 보고서 초안, 연구자가 선호하는 가설, 내부 추론 과정은 일절 공개하지 않습니다. 검증자는 백지상태에서 성립 가능한 가설, 판별력이 높은 핵심 정보, 항목별·가설별 관계, 핵심 지렛대(linchpin)를 스스로 도출해 잠정 평가를 기록합니다. 아울러 부재 신호, 숨은 가정, 출처 간 종속성, 컷오프 시점 이후 정보 유입 여부, 기만 가능성, 대안 가설을 가려낼 후속 관찰 지표도 함께 짚어냅니다.
2. **Pass B: 가설 행렬 대조.** 검증자가 자체 재구성을 마쳐 기록한 뒤에야 `competing-hypotheses.yaml`을 전달합니다. 검증자는 두 분석을 맞대어 비교하고, 출처가 달린 진술을 실제 소스 노트와 대조하며, 핵심 지렛대와 평가가 엇갈린 행들의 원문 자료를 직접 확인해 구체적인 결함과 사유를 보고합니다.
3. **Pass C: 최종 보고서 검토.** Pass B에서 드러난 불일치를 모두 해소한 뒤 행렬을 바탕으로 작성한 보고서를 동일한 검증자에게 넘깁니다. 검증자는 상대 평가 결과, 핵심 판별 근거, 반증 요소, 미해결 쟁점, 신뢰도의 근거와 한계가 보고서에 충실히 반영되었는지 최종 확인합니다.

독립 재구성을 지켜 주는 핵심은 별도의 검증자를 여러 명 두는 것이 아니라 정보 공개 순서를 통제하는 데 있습니다. 결론을 먼저 본 검증자는 어쩔 수 없이 그 결론을 기준점(anchor)으로 삼기 때문에, 반드시 자체 재구성을 끝낸 뒤에야 행렬을 공개합니다.

**정성적 행렬을 확률 수치로 둔갑시키지 않습니다.** 정성 평가 행렬에서 곧바로 사후 확률이 계산되지는 않습니다. 관계 라벨은 우도(likelihood)가 아니며, 일치하는 행 개수를 세어도 확률이 되지 않습니다. 보고서에 수치를 적을 때는 주관적 추정치와 계산된 베이지안 확률을 엄격히 구분하며, 베이지안 계산을 제시하려면 상호 배타적·포괄적 가설 분할(또는 명시적 결합 모델), 사전 확률, 조건부 우도, 증거 간 종속성 처리가 모두 뒷받침되어야 합니다.

**‘증거 불충분’은 엄밀한 판정이지 손쉬운 도피처가 아닙니다.** 판단 유보는 가장 방어하기 편한 결론이기 때문에, 자칫하면 확보된 근거만으로도 충분히 우열을 가릴 수 있는 분석까지 ‘증거 불충분’으로 덮어 버리기 쉽습니다. 비교 결과 가설들을 끝내 가려내지 못했다면 그것이 사용자에게 어떤 실질적 의미를 갖는지, 기각하지 못한 가설이 실제로 참일 때 어떤 대가를 치르게 되는지, 그리고 앞으로 어떤 관찰이 이루어지면 가설을 구분할 수 있는지를 구체적으로 적어야 합니다. 추가 조사항목 역시 단순히 자료 분량을 늘리는 방향이 아니라 가설 간 판별력을 높이는 기준으로 선택합니다.

### analogical-foresight: 전향적 분석을 위한 역사적 사례

역사적 선례는 미래를 전망하는 전향적 분석에 작동 메커니즘, 핵심 변수, 검증 지표를 제공해 줄 수 있습니다. 이때 유추 분석의 기본 단위는 다음과 같은 전이 주장(transfer claim)입니다.

```text
supported source-case mechanism -> specific target mapping
  -> conditions required for transfer -> target-side observation
```

이 네 고리가 모두 빈틈없이 이어질 때만 과거 사례가 현재 분석의 근거가 됩니다. 겉모습이 비슷하다거나 과거 사례의 서사가 그럴듯하다는 이유만으로는 동일한 메커니즘이 현재 대상에서도 작동한다고 단정할 수 없습니다.

**역사적 사례를 꺼내기 전에 분석 대상의 틀(frame)부터 세웁니다.** Job은 먼저 대상 질문, 정보 컷오프, 전망 기간(horizon), 현재 진행 단계를 명시하고 대상 자체의 정보를 충분히 수집한 뒤, 과거 사례를 언급하기 전에 대상의 구조부터 그립니다. 지금까지 관찰된 선행 조건과 사건 전개 순서, 제약 조건, 결과는 물론 각 추론을 뒷받침하는 근거와 인과 관계, 그리고 결론을 뒤집을 수 있는 미지수나 미설명 단계를 먼저 정리합니다. 순서를 거꾸로 잡으면 생생한 과거 사례 하나가 현재 문제의 정의 자체를 왜곡해 버립니다. 또한 과거 시점의 예측을 재구성하는 과제에서는 정보 컷오프 이후에 벌어진 사건을 근거로 사례를 고르거나 대상 구조를 정의하거나 매핑 타당성을 판단할 수 없습니다.

**인과 공백에서 후보 사례를 도출합니다.** 비교할 과거 후보 사례는 대상 구조에서 드러난 불확실한 관계, 빠진 고리, 아직 설명되지 않은 단계로부터 찾습니다. Job은 서로 다른 행위자와 시대, 산업 영역을 가로질러 유사한 방향의 관계와 인과 역학, 기능적 제약을 폭넓게 탐색하며, 익숙한 첫 사례 하나에서 탐색을 멈추지 않도록 평가에 앞서 후보군부터 넓게 모읍니다. 만약 후보들이 익숙한 단일 분야에 갇혀 있거나 똑같은 역사적 서사만 반복한다면, 대상 구조만 전달받아 컨텍스트가 격리된 서브에이전트에 타 분야 사례, 실패 사례, 정반대 결과가 나온 사례를 제안하도록 요청할 수 있습니다. 이때 해당 서브에이전트는 후보만 제시할 뿐 대상 문제를 판정하지는 않습니다.

**과거 사례 자체의 작동 메커니즘을 먼저 입증합니다.** 사건이 시간순으로 이어졌다는 사실만으로는 인과 설명이 되지 않습니다. Job은 채택한 각 사례의 사실관계를 검증하고, 주장된 메커니즘을 뒷받침하는 근거를 확인하며, 공통 원인·대안 메커니즘·우연·선택 편향·후대의 사후 해석으로도 같은 사건 전개를 설명할 수 없는지 따져 봅니다. 동일한 역사적 사건을 다른 이름으로 부르거나 하위 사건·상위 범주·다른 서술 방식으로 중복 인용하더라도 독립된 근거가 늘어나지는 않습니다. 한편 관계가 반대로 작동한 사례, 전이에 실패한 사례, 진행 단계가 달랐던 사례, 경계 조건이 깨진 사례는 메커니즘의 한계를 짚어 주는 반례로서 중요한 가치를 지닙니다.

**모든 전이 주장을 여섯 항목으로 대조(audit)합니다.** 최종 결론에 영향을 주는 모든 유추 기반 주장은 다음 여섯 요소를 세트로 갖추어야 합니다. 근거로 입증된 과거 메커니즘, 현재 대상에 대응하는 구체적 관계, 선행 조건·역할·방향·시점·규모·범위·유인 구조의 실질적 차이, 전이가 성립하기 위한 가정, 공유 출처·중첩 사건·공통 외부 충격·정책 모방·동일 제도·동일 측정 방식 같은 종속성, 그리고 전이 가설을 지지하거나 반박할 현재 대상 측 관찰 지표입니다. 행위자의 행동을 분석할 때는 그 행위자 고유의 목표, 제약, 유인, 보유 정보, 의사결정 절차를 기준으로 삼아야 하며, “내가 저 자리였다면 이렇게 했을 것”이라는 추측은 근거가 될 수 없습니다. 채택된 사례는 후보 메커니즘, 누락 변수, 조건부 경로, 대상 측 관찰 지표, 반례, 경계 조건 가운데 적어도 하나에 실질적으로 기여해야 하며, 그저 흥미로운 역사 이야기에 그치는 사례는 제외합니다.

**여러 사례를 묶기 전에 상호 종속성을 확인합니다.** 각기 유의미한 여러 사례를 함께 보면 단일 일화에 매몰되는 위험은 줄어들지만, 그렇다고 해서 해당 메커니즘이 현재 대상에서도 작동한다는 사실까지 증명되지는 않습니다. Job은 여러 사례에서 반복되는 듯 보이는 패턴이 실은 동일한 사건이나 제도, 단일 출처 서사, 공통 충격, 전파 경로, 정책 확산, 동일한 측정 방식에서 비롯된 착시가 아닌지 점검합니다. 긍정적 패턴이 핵심 논거로 쓰일 때는 해당 요인이 있었는데도 결과가 나타나지 않았던 사례나, 전혀 다른 메커니즘으로 같은 결과가 나왔던 사례도 함께 찾습니다. 의도적으로 골라 모은 유추 사례 집합은 통계적 준거 집단(reference class)이 아니므로, 사례 개수를 기저율이나 확률, 신뢰도로 환산해서는 안 됩니다.

**“방어 가능한 유추 없음”도 정당한 결론으로 인정합니다.** 결론에 영향을 미치는 모든 유추 기반 주장이 작동 메커니즘과 대안 설명 배제 근거, 방향·단계·범위를 포함한 구체적 대상 매핑, 실질적 차이·종속성·전이 조건, 그리고 이를 검증할 대상 측 관찰 지표를 빠짐없이 갖추었을 때만 분석을 마칩니다. 조사 과정에서 발견된 반례와 실패한 매핑도 모두 설명되어야 합니다. 만약 어떤 후보 사례도 전이 사슬 전체를 충족하지 못한다면 방어 가능한 유추를 찾지 못했다고 결론 내리는 것이 옳으며, 그럴듯해 보인다는 이유만으로 부실한 사례를 보고서에 남겨 두지 않습니다.

### 두 방법의 협력

두 방법론은 서로 다른 층위의 문제를 다루므로 하나의 연구 과제 안에서 자연스럽게 결합할 수 있습니다. 예를 들어 `analogical-foresight`로 비교할 가설 후보를 도출하거나 확인해야 할 관찰 지표를 찾고, `ach`로 그 가설들 사이의 판별력을 엄밀히 겨루는 식입니다. 다만 역사적 선례는 현재 대상에 대한 직접 관찰이 아니므로, 반드시 명시적이고 방어 가능한 전이 주장을 거쳐서만 근거로 반영됩니다.

### 도메인에 맞는 Playbook 추가하기

프라이빗 배포 환경에서는 사내 실사(due diligence) 절차, 업종별 데이터 소스 카탈로그, 특정 의사결정용 검토 기준 등 고유한 방법론 파일을 워크스페이스 템플릿에 직접 추가할 수 있습니다. 파일 상단에 `name`과 `description` 필드를 선언해 두면 새 Job이 계획 단계에서 자동으로 목록을 인식하고, 질문과 관련이 있을 때 읽어 들여 적용합니다. 이를 위해 모델을 재학습하거나 애플리케이션 코드를 수정할 필요는 없습니다.

## Job 실행 중

Agent가 백그라운드 Job을 생성한 뒤에도 현재 채팅방은 멈추지 않고 그대로 사용할 수 있습니다. 평소처럼 Agent와 다른 대화를 이어 갈 수 있으며, **Console → Background Agent Jobs** 화면을 열면 수립된 계획과 진행 단계, 모델 사용량, 현재 상태를 실시간으로 볼 수 있습니다.

진행 도중 사람의 결정이 꼭 필요해지면 Job이 원래 대화방에 질문을 남깁니다. 해당 대화방에서 바로 답변해 주면 작업이 이어서 진행됩니다. 이때 표시되는 `waiting_on_user` 상태는 오류나 실패가 아니라 사용자의 응답을 기다리는 정상 대기 상태입니다. 또한 언제든 원래 대화방에서 참고 자료를 추가로 건네거나 요구 사항을 조정할 수 있으며, 메인 Agent가 이를 실행 중인 Job에 전달합니다.

## 결과 읽기

Job이 완료되면 메인 Agent가 먼저 보고서를 읽고 검토한 뒤 사용자에게 전달합니다. 만약 보고서에 연구 목적 자체를 해칠 만한 공백이나 한계가 적혀 있으면 이를 투명하게 알립니다. 특히 빠진 내용이 메인 Agent가 이미 알고 있는 맥락이거나 사용자에게 확인받아 채울 수 있는 결정 사항이라면, 미완성 보고서를 그대로 넘기는 대신 해당 정보를 Job에 보충해 연구를 이어 가게 합니다.

전달받은 보고서를 읽을 때는 인용된 출처가 결론을 실제로 뒷받침하는지, 시간 범위와 컷오프가 지켜졌는지, 사실과 추론이 구분되어 있는지, 한계와 신뢰도가 솔직하게 명시되어 있는지를 확인하세요. 좋은 보고서는 다른 보조 파일 없이 그 자체만으로 결론과 근거, 한계, 불확실성을 온전히 이해할 수 있어야 합니다. 특정 근거를 더 깊이 확인하고 싶다면 Agent에게 Job 워크스페이스의 해당 소스 노트를 읽어 달라고 요청하세요. ACH 분석을 거친 보고서라면 가설 행렬의 특정 행에 담긴 평가 근거를 물어볼 수도 있습니다.

후속 조사가 더 필요할 때는 배경 설명을 처음부터 다시 적을 필요 없이 같은 Job을 이어서 진행해 달라고 요청하면 됩니다. 반대로 Job이 실패했거나 대기 상태에서 멈추어 있다면 상세 화면을 열어 상태 코드와 오류 메시지를 확인하세요. 각 상태의 의미와 작업 취소, 런타임 설정 방법은 [Background Agent Jobs](../background-jobs/)를 참조하세요.

## 참고 자료 및 Ankole과의 차이

Ankole Deep Research의 설계는 아래 공개 연구 논문들과 문제의식을 같이하며 여러 통찰을 참고했습니다. 각 논문은 자체 벤치마크에서 최고 수준(state-of-the-art)의 성능을 입증했지만, Ankole이 집중한 질문은 조금 다릅니다. 바로 “프라이빗 엔터프라이즈 배포 환경 안에서 이러한 원칙이 실제로 어떻게 작동해야 하는가”입니다.

- Chen, Y., Chen, G., Sun, Y., & Zhang, K. (2026). <a href="https://arxiv.org/abs/2607.13602" target="_blank" rel="noreferrer">Analogical Deep Research: Retrieving and Integrating Historical Analogies for Foresight Analysis</a>. arXiv:2607.13602.
- Zhu, C., Xu, B., Du, M., Wang, S., Wang, X., Mao, Z., & Zhang, Y. (2026). <a href="https://arxiv.org/abs/2602.01566" target="_blank" rel="noreferrer">FS-Researcher: Test-Time Scaling for Long-Horizon Research Tasks with File-System-Based Agents</a>. arXiv:2602.01566.
- MiroMind Team. (2026). <a href="https://arxiv.org/abs/2603.15726" target="_blank" rel="noreferrer">MiroThinker-1.7 & H1: Towards Heavy-Duty Research Agents via Verification</a>. arXiv:2603.15726.

**방법론을 모델 가중치가 아니라 파일에 담습니다.** CANA는 전용 에이전트 프레임워크이며, MiroThinker는 에이전트 중간 학습 단계를 통해 단계별 신뢰도를 높이고 검증 과정을 모델 자체의 추론 루프 안에 내재화합니다. 두 접근 모두 특정 모델과 한 몸으로 묶여 제공됩니다. 반면 Ankole은 연구 방법론을 워크스페이스의 Playbook 파일로 분리해 두며, Job이 계획 단계에서 이를 읽고 필요하면 기본 검증 프로토콜까지 교체합니다. 물론 실행 품질이 모델의 지침 준수 능력에 영향을 받는다는 비용은 따르지만, 모델을 교체해도 재학습이 필요 없고 각 조직이 사내 도메인에 맞는 방법론을 자유롭게 추가·제거할 수 있다는 큰 이점을 얻습니다. 실제 엔터프라이즈 조사에서는 범용 추론 능력 못지않게 업종별 실무 절차와 사내 데이터 소스 활용법이 결과를 좌우하기 때문입니다.

**검증의 독립성을 자가 점검이 아닌 정보 통제로 확보합니다.** MiroThinker는 추론 도중 자신의 추론 궤적을 스스로 점검(self-audit)합니다. 반면 Ankole의 검증자는 이전 대화 턴도, `research-state.md`도 받지 못하며, ACH에서는 아예 `sources/`만 보고 가설 비교를 처음부터 독립 재구성한 뒤에야 행렬을 보고 마지막에 보고서를 읽습니다. 이유는 명확합니다. 자신이 만든 추론 궤적을 스스로 감사하면 처음 추론을 만들 때와 똑같은 편향(사전 확률)에 갇히고, 결론을 먼저 본 검증자는 그 결론에 판단이 고정되기 때문입니다.

**영속성을 컨텍스트 창 확장에 그치지 않고 Job 수명 주기 전체로 확장합니다.** FS-Researcher가 파일 시스템을 활용해 단일 컨텍스트 창의 한계를 넘어서는 방식은 Ankole의 소스 노트 및 워크스페이스 구조와 정확히 맞닿아 있습니다. 차이점은 Ankole의 워크스페이스가 대여(lease), 장애 복구, 후속 메시지 전달, 사용자 응답 대기 상태를 갖춘 Background Agent Job 위에 놓여 있다는 데 있습니다. 덕분에 컨텍스트 창이 가득 찼을 때뿐 아니라 Worker 프로세스가 중단되었다가 다시 올라온 뒤에도 작업이 끊김 없이 이어집니다. 또한 사서(librarian)와 집필자 역할을 기계적으로 분리하지도 않습니다. 깊이 있는 보고서를 쓰려면 분석 논리 사슬 전체를 꿰고 있어야 하는데, 역할을 경직되게 갈라 놓으면 보고서가 단편적인 노트 요약본에 그치기 때문입니다. 대신 수집 단계에서는 데이터 소스당 단일 소유자 규칙으로 중복을 막고, 컨텍스트 격리는 오직 독립 검증자에게만 강제합니다.

**유추에는 반증 가능한 전이 사슬을 요구합니다.** ADR 논문은 모델이 근본 작동 메커니즘 대신 피상적인 유사성에 끌려 유추 사례를 고르는 문제를 짚어내고, 메커니즘 정렬과 교차 사례 확인을 해법으로 제시합니다. Ankole 역시 같은 관점을 취하면서 `analogical-foresight` Playbook을 통해 이를 빈틈없이 채워야 하는 4단계 전이 사슬로 구체화하고 두 가지 요건을 더했습니다. 첫째, 여러 사례를 엮기 전에 상호 종속성을 먼저 점검합니다. 단일 외부 충격이나 같은 출처 서사, 동일한 측정 방식에서 비롯된 반복은 겉보기만 교차 검증일 뿐 독립된 근거가 아니기 때문입니다. 둘째, 모든 전이 주장은 현재 대상에서 확인할 수 있는 관찰 지표를 제시해야 합니다. 그래야 유추가 그저 그럴듯한 비유에 머물지 않고 추후 실제 관찰로 반증 가능한 주장이 됩니다.

**최종 기준점은 벤치마크 점수가 아니라 사용자가 확인한 연구 목적입니다.** 학술 논문이 정해진 벤치마크 점수에 최적화한다면, Ankole은 실제 담당자가 이 보고서를 받아 어떤 의사결정을 내릴지에 최적화합니다. 생성 전에 성공 기준을 명확히 합의하고, 전달 직전에 기준별로 달성 여부를 대조하며, 채우지 못한 공백마다 결론에 미치는 파급력을 명시합니다. 핵심 공백이 연구 목적을 무너뜨릴 때는 메인 Agent가 보충 가능한 맥락을 채워 넣어 Job을 이어 가게 합니다. 자료 수집도 같은 원칙을 따릅니다. 활성화된 Skill 데이터 소스를 공개 웹 검색보다 먼저 조회하고, 어떤 Skill로도 채울 수 없는 빈자리는 숨기지 않고 근거 공백으로 기록합니다. 실무에서 신뢰할 수 있는 엔터프라이즈 보고서는 권위 있는 원본 데이터를 썼는지, 그리고 확인하지 못한 한계를 얼마나 정직하게 밝혔는지에 달려 있으며, 이 두 가지는 일반 벤치마크 점수표로는 드러나지 않습니다.

워크스페이스의 Playbook 체계, 검증 프로토콜, 연구 상태 파일, 전달 대조(audit) 절차는 AgentBull Ankole 팀이 설계하고 구현했습니다.
