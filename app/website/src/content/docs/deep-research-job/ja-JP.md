Deep Research は、文献レビュー、競合調査、複数ソースの突き合わせによる事実確認、複数の仮説を比較検討する将来予測、あるいは過去の予測と実際の結果の振り返りに適した機能です。こうした調査では検索・精読・裏付け確認を何度も往復する必要があるため、Agent は作業を [Background Agent Job](../background-jobs/) に切り出し、調査中も通常のチャットであなたの別の依頼に応答できるようにします。

これは単に Web ページを数件検索して要約するのとはまったく異なります。Job は専用の永続ワークスペース上で段階的に進行します。まず調査計画を立て、並列で資料を集めてソースノートとして書き出し、その証拠にもとづいて結論を組み立て、調査過程の内部メモを持たない独立した検証者（verifier）にレポートをレビューさせ、最後にすべての成功基準を満たしているか監査してから納品します。本格的な調査には通常 30〜90 分ほどかかるため、手早く簡単な答えが欲しいだけのときは Deep Research を指定せず直接質問してください。

## 始める前に

あらかじめ [Quick start](../quickstart/) を完了し、チャットチャネルで Agent とやり取りできることを確認してください。公開 Web ページの検索や読み取りを行う場合は、対象 Agent に `web_search` と `web_fetch` のモデルプロファイルを設定しておきます。

すべてのモデル呼び出しは AIGateway を通ります。ChatGPT サブスクリプションの利用枠で調査を回したい場合は、[ChatGPT subscription provider](../chatgpt-subscription-provider/) を登録し、**Console → Agents → Background Agent Jobs** でその provider を選択してください。

また、対象 Agent で有効になっており Background Agent Jobs での利用が許可されているすべての Skill は、自動的に調査ジョブへ引き継がれます。金融データ API や社内システム連携などのデータソース Skill が有効になっていれば、Job は公開 Web を検索する前にまずそれらの信頼できるデータソースを優先して参照します（ジョブごとに別途権限を承認する必要はありません）。

## 調査を開始する

調査対象、対象期間、根拠のルール、求める出力形式を明記したうえで、バックグラウンド実行を依頼します。

```text
Run this as a Deep Research Background Agent Job.
Compare the pricing and product updates from these three vendors over the last
two quarters. Cite primary sources, separate facts from inference, and return
a report with links. Ask me before you expand the scope or use paid data.
```

### 作成前の明確化

たった 1 文の曖昧な依頼からいきなり長時間ジョブが走り出すことはありません。Job を作成する前に、まだ決まっていない重要な前提（調査の目的と使い道、成功基準、対象範囲と期間、証拠ルール、納品形式）について Agent が順番にヒアリングを行います。一度に 1 問ずつ推奨案を添えて尋ね、システム側で調べればわかる事実は自分で確認し、本当に人間の判断が必要な項目だけを確認します。あなたが合意した時点で初めて Job が作成されます。

最初の数分間でここをすり合わせておく価値は十分にあります。方向性がずれたまま走り出すと続く 60 分間の収集・分析が丸ごと無駄になりますが、事前の 1 問でそのずれを防げるからです。

もし事前のヒアリングを省略したい場合は、「確認は不要です。そのまま Job を作成し、細かい前提はそちらで決めて進めてください」と伝えてください。その場合、Agent は置いた前提条件と Job 側に委ねる判断事項を明示したうえで、すぐに Job を開始します。

### 良いリクエストが含むもの

単に「〇〇について深く調べて」と頼むよりも、スコープを明確に切った依頼の方がはるかに実用的なレポートになります。特に次の要素を含めると効果的です。

- **調査対象と、答えを出すべき具体的な問い:** テーマ名だけでなく「何を知りたいか」を書きます。「再生可能エネルギー業界を分析して」と頼むのと、「この 3 社のうち今後 2 四半期で値下げに踏み切る可能性が最も高いのはどこか、その根拠は何か」と頼むのとでは、出来上がるレポートの質が大きく変わります。
- **対象期間と情報のカットオフ時点:** 過去の意思決定の振り返りやバックテストを行う場合、「いつ時点までに公開されていた情報だけを使ってよいか」をこの指定で制御します。
- **証拠ルール:** 一次資料のみに限定するか、出典リンクを必須とするか、事実と推論を明確に書き分けるかなどを指定します。
- **分析手法（任意）:** たとえば「ACH（競合仮説分析）で複数の説明を比較して」「過去の類似事例から前方視的に分析して」といった手法指定が可能です。指定がなければ、問いの性質に合う手法を Job が自動で選びます。
- **納品形式と言語:** 既定は Markdown レポートです。PDF・プレゼンスライド（PPT）・Web ページなどを指定した場合はその形式で納品され（Markdown 原稿も併せて欲しい場合はその旨を伝えます）、デザインの指定がなければ Agent の `DESIGN` ドキュメントの視覚ルールが適用されます。
- **制約条件:** コスト上限、有料データソースの利用可否、スコープ拡大時の事前確認、締め切りなどを伝えます。

なお、ページ数や文字数の指定は厳密な制約を求めない限り目安として扱われます（たとえば「3 ページの PDF」ならおよそ 3 ページ前後でまとめられます）。

## Job の仕組み

裏側でどのように調査が進むかを知っておくと、途中経過の読み取りや結論の信頼度評価、追加指示の出し方がわかりやすくなります。各 Deep Research Job は専用の永続ワークスペース内で次の 4 段階を順に進めます。

### 1. 計画

まずワークスペース内の利用可能な Playbook 一覧を確認し、今回の問いに当てはまる調査手法を読み込みます。テーマが広範だったり、対象の定義がまだ曖昧だったり、あるいはモデルの学習時期以降に状況が変化している可能性がある場合は、先にサブエージェントを 1 つ出して短時間の予備探索を行います。この予備探索の目的は証拠集めや結論出しではなく、現在の正確な定義や境界を把握し、モデルの知識だけでは見落としがちな重要概念・切り口・検索キーワード・データソースを洗い出すことにあります。

その予備探索を踏まえて詳細な情報収集計画を立てることで、モデル内部の古い記憶ではなく「現在の事実」を出発点にした計画になります。

### 2. 証拠を収集する

複数のサブエージェントが収集計画を並列に実行します。集めた有益な資料はすべて `sources/` 配下に Markdown 形式のソースノートとして保存され、冒頭の YAML フロントマターに出典元・公開日時・著者・信頼度・URL が記録されます。以降の分析はすべて、検索結果の一時的な印象ではなく、この保存済みノートを根拠として引用します。

情報収集では「1 つのデータソース・一次資料につき担当オーナーは 1 つだけ」というルールを徹底しています。担当のサブエージェントが 1 回だけ取得してファイルに書き出し、他のサブエージェントは同じリクエストを繰り返さずにそのファイルを参照します。プレスリリースや開示書類、データセットも重複ダウンロードせず、後から他のサブエージェントが探しやすいよう識別子付きのファイル名で保存します。また、一括取得に対応したツールを使う際は 1 回の呼び出しでバッチ取得を行います。

収集の優先順位は「有効な Skill のデータソース ＞ 公開 Web 検索」です。まず利用可能な Skill のドキュメントを確認し、Skill では提供されていない領域や、Skill を叩いた結果データが存在しなかった項目についてのみ `web_search` や `web_fetch` を使います（専用 API から正確に取れるデータを公開 Web 記事で代用することはしません）。Skill でも公開情報でも取得できなかった項目は、黙って飛ばすのではなく「確認できなかった証拠ギャップ」として `sources/` に明記します。

さらに、必要に応じて生データを集計・加工するスクリプトを書いて構造化データから指標を算出します。一通りの整理が終わった段階で、情報の欠落や食い違い、後続の分析に足りない前提文脈がないかを点検し、必要なら追加収集を行います。

### 3. 分析と検証

結論は集まった証拠から一段ずつ論理的につながる必要があり、先に結論を決めてから都合のよい根拠を探すような進め方はしません。レポート内では「客観的事実・第三者の意見・仮説・推論」を明確に区別します。手元の証拠から複数の解釈が成り立つ場合は、それらをすべて併記したうえでどれを最も有力と見るかとその確信度を示します。報道記事や企業の宣伝文句には健全な懐疑心を持って接し、確証バイアス・サンプリングバイアス・もっともらしいストーリーへの飛びつき（物語の誤謬）を意識的に排除しながら執筆します。

初稿がまとまると、独立した検証者（verifier）が分析をレビューします。この検証者はそこまでの会話履歴も Job の内部メモ（`research-state.md`）も一切渡されず、完成したレポート案とあなたの調査目的だけを受け取って形式面・内容面の両方から検証します。形式面では、事実・意見・仮説の切り分け、引用の十分さ、結論の具体性をチェックします。内容面ではあえて批判的な視点（レッドチーム）に立ち、論理の飛躍や内部矛盾がないか、別の説明が成り立たないか、因果関係を逆転させていないか、結果を見てから都合よく的を描いていないか（後付けの標的設定）を厳しく点検します。

なお、検証者の役割はあくまで問題点の指摘であり、最終判断の主導権を奪うことではありません。実質的な異論が出た箇所については、分析とレポート自体を修正するか、あるいは「なぜ見解が分かれるか」をレポート本文に明記して残します（無理に丸めて表面的な合意を装うことはしません）。

### 4. 納品

納品フェーズでは、まず成功基準の監査を行います。最初に合意したすべての成功基準に対し、引用付きの証拠で回答できているか、あるいは未解決のギャップとして結論への影響とともに明記されているかを 1 つずつ確認します。もし調査の根幹に関わるギャップが残っており、時間的にも余裕がある場合は、手の届く範囲で追加の証拠収集を行います（ただし締め切りに遅れるレポートは不完全なレポートと同様に目的を損なうため、時間境界は守ります）。

最後に指定されたフォーマットで成果物を出力し、別のサブエージェントが最終的な体裁チェックを行って完了となります。レポートは依頼された言語で書かれ、ジョージ・オーウェルの「執筆の 6 原則」に従った簡潔で明快な文体を保ち、冗長な定型免責文は付けません。

### 作業状態、回復、再起動

進行中の内部状態はワークスペースの `research-state.md` に記録されます（各成功基準の達成状況、裏付けがまだ不十分な仮説案、却下した調査方針とその理由、収集データの妥当性に関する懸念点など）。これはあくまで調査員用の作業メモリであり、最終納品物ではありません。また、独立した視点で検証できるよう、検証者にはこのファイルは渡されません。

このファイルがあるおかげで、途中で Worker の再起動やコンテキスト上限によるリセットが起きても進捗は失われません。Job は `research-state.md` を読み直して続きから再開し、すでに確定した調査を最初からやり直すことはありません。

一方、調査の途中で「そもそもの前提フレーム自体が誤っていた（対象の取り違え、問いの誤読、中核前提の崩壊など）」と判明した場合は、小手先のパッチ当てで済ませることはしません。修正後の新しいフレームを `research-state.md` に記録し、誤った前提に依存していた分析を破棄して該当フェーズをやり直します（収集済みの `sources/` はそのまま活かし、新しいフレームで不足する資料だけを追加収集します）。前提がずれたまま最後まで書き上げてもレポート全体が無駄になるため、途中で立ち戻って組み直す方が結果的にずっと低コストです。

## Playbook: プラグ可能な調査方法

Playbook は、deep-research Agent Plugin のワークスペーステンプレートに同梱され、Job ワークスペースの `playbooks/` ディレクトリに配置される調査手法定義ファイルです。各ファイルの冒頭には「どのような問いに適用すべきか」が記されており、計画フェーズで Job が全 Playbook を確認して該当するものを読み込みます。

Playbook は単なるヒント集ではなく、標準の分析・検証・執筆フロー自体を専用のプロトコルに差し替えることができます（後述する ACH が標準の 1 パス検証を 3 パス検証に置き換えるのがその好例です）。つまり調査方法論はモデルや本体コードにハードコードされておらず、ファイルとして自由に追加・差し替えが可能です。

標準では、代表的な 2 つの調査手法が組み込まれています。

### ach: 競合仮説の分析 (Analysis of Competing Hypotheses)

情報が断片的だったり、互いに食い違っていたり、意図的な情報操作の懸念がある状況で重要な予測や原因究明を行うには、複数の筋の通った仮説を並べて比較する必要があります。ACH はその比較過程を構造化して監査可能にする手法です（粗悪な証拠を魔法のように良質化したり、人間の代わりに答えを自動計算したりするものではありません）。

答えが 1 つに定まる単純な事実確認には ACH は不要です。また、信頼性の高い定量データと適切な統計モデル・因果推論モデルで直接解ける問いであれば、そちらのモデルを使うべきであり、ACH で代用すべきではありません。

**1. 証拠を見る前に仮説を出し切る。** まず答えるべき正確な問い、情報のカットオフ時点、そして予測タスクであれば対象期間と結果の定義を明文化します。そのうえで、個別の証拠を評価する前に「考えられるすべての妥当な仮説」を洗い出します。最初に思いついたもっともらしい説明に引きずられるのを防ぐためです。各仮説は同じ問い・同じ粒度・同じ時間軸で記述し、互いに排他的か、現実的な可能性を網羅できているかも明記します。仮説の数に決まったノルマはなく、比較によって棄却する明確な根拠が出るまで残します（「裏付けがまだ見つかっていない」ことは「反証された」こととは違うためです）。

**2. 機械チェック可能な仮説×証拠マトリクスを作る。** 仮説横断の比較表として `competing-hypotheses.yaml` を作成・管理します。各行には、すべての仮説に照らして評価可能な 1 つの命題（観察事実、報道上の主張、本来あるはずなのに見当たらないシグナル、分析上の仮定、論理的推論、または基準率）を置き、種別・ソースファイルのパスまたは論理的根拠・情報源の適格性を記録します（たとえば情報源が「〜という疑惑がある」と述べているだけなら、それを確定事実として扱うことはしません）。記述後、次のスクリプトで構造チェックを実行します。

```bash
bun tools/ach_check.ts
```

このチェッカーが検出するのは、記述漏れや不正・存在しないローカルソースパスといった構造上の不備だけです。仮説自体が妥当か、命題が真実か、出典が本当にその主張を裏付けているかといった実質的な判断はモデルと人間の役割として残されています。

**3. 「裏付けの数」ではなく「仮説を見分ける力（判別力）」で比較する。** マトリクスの各行では「この証拠は仮説を証明するか」ではなく、「もしこの仮説が正しいとしたら、この証拠が観測されるのはどれほど自然か」を問います。評価ラベルは `expected`・`compatible`・`tension`・`contradicts`・`unknown`・`not applicable` の 6 種類だけを使い、それぞれ短い理由を添えます。仮説ごとの優劣を分ける判別力は「同じ証拠に対する仮説間の反応の違い」に現れるため、仮説ごとに縦に読む前に、まず各行を横方向に読み比べます。どの仮説とも矛盾しない（すべて `compatible` になる）情報は、背景として重要ではあっても仮説の絞り込みにはほとんど寄与しません。

**4. 情報源の独立性とチャネルカバレッジを確認する。** 同じ元記事を転載した複数のニュースは、情報源としては 1 件にすぎません。1 つの出来事から派生した複数の指標や、同一データセットから切り出した複数の集計も独立した裏付けにはなりません（細部の補足にはなっても、証拠の重みを何倍にも増やすことはできません）。また見落としがちなのが「チャネルの偏り」です。仮説ごとに証拠が現れる媒体や経路（チャネル）は異なるため、ある仮説の証拠が存在し得るチャネルをそもそも誰も調べていなければ、マトリクスが測っているのは「現実の確からしさ」ではなく単なる「調査範囲の偏り」になってしまいます。そのため、仮説ごとに証拠が現れるはずのチャネルを明示し、実際にそこを調査するか未調査ギャップとして記録します。

**5. 不在シグナルと要石（リンチピン）を検証する。** 「期待されるシグナルが見当たらないこと」が反証になるのは、もし起きていれば観測できるはずであり、かつ今回の調査範囲で合理的に見つけられたはずである場合に限られます。あわせて、結論全体を左右している少数の決定的な証拠や前提（リンチピン）を特定し、「もしこの証拠が誤報・ミスリード・不完全・他ソースの受け売り・意図的な欺瞞だったとしたら結論はどう変わるか」を感度分析します。最終判断の信頼度は集めた資料の分量ではなく、仮説の網羅性・証拠の質・独立性・リンチピンへの依存度で決まります。

**6. 段階的開示による 3 パス検証を行う。** ACH では標準のレビューを置き換え、同一の検証者が情報を段階的に受け取りながら 3 段階で検証します。この「開示の順序」そのものがバイアス防止の仕組みです。

1. **パス A（ソースノートのみからの独自再構成）:** 検証者には、調査目的、ACH の問い、カットオフ時点、および `sources/` へのアクセス権だけが渡されます（マトリクスもレポート案も、メイン調査員の推し仮説も一切見せません）。検証者は白紙の状態から妥当な仮説、判別力の高い証拠、仮説との関係、リンチピンを洗い出し、独自の暫定評価を記録します。あわせて不在シグナル、暗黙の仮定、ソース間の従属関係、カットオフ以降の情報の混入、欺瞞の可能性、そして仮説を決着させるために次に観測すべき指標も特定します。
2. **パス B（マトリクスとの突き合わせ）:** パス A の独自評価を記録し終えた後に初めて `competing-hypotheses.yaml` が開示されます。検証者は 2 つの分析を突き合わせ、主張からソースノートへの追跡、リンチピンや評価が割れた行の原資料確認を行い、具体的な問題点を理由付きで指摘します。
3. **パス C（最終レポートのレビュー）:** パス B の指摘をすべて解消したあと、マトリクスにもとづいて執筆されたレポートが同じ検証者に渡されます。各仮説の相対評価、決め手となった判別情報、反証要素、未解決の論点、確信度の根拠と限界が誠実に表現されているかを確認します。

別の検証者を何人並べても、最初から完成結論を見せてしまえばアンカリング効果に引きずられます。先に原資料だけで自分の見立てを作らせる「順序の制御」こそが独立性を守ります。

**7. 定性マトリクスを確率の計算結果のように扱わない。** 定性的な評価表から自動的に事後確率が算出されるわけではありません（ラベルは尤度そのものではなく、行数も確率ではありません）。レポート内で数値的な確率を示す場合は、分析者の主観的見積もりなのかベイズ更新による計算値なのかを明確に区別します（後者を行うには、排他的かつ網羅的な事象分割または明示的な結合モデル、事前確率、条件付き尤度、および証拠間の従属性の適切な処理が不可欠です）。

**8. 「証拠不十分」を安易な逃げ道にしない。** 「現時点では判断材料が足りない」という結論は最も安全で反論されにくいため、本来なら手元の証拠で十分に優劣をつけられる問題まで曖昧に丸めてしまいがちです。本当に仮説を絞り込めない場合は、「それが意思決定にとって何を意味するか」「もし棄却した側の仮説が本当だったらどんな損失が生じるか」「次に何を観測すれば決着がつくか」まで具体的に踏み込んで記述します。追加調査の優先順位も、単に情報量を増やせるかではなく「仮説を見分けられるか」で決めます。

### analogical-foresight: 前方視的分析のための歴史的ケース

過去の歴史的事例（アナロジー）は、将来予測において「起こり得る因果メカニズム・注目すべき変数・検証すべき兆候」を教えてくれます。この手法における分析の基本単位は、次の 4 要素からなる**転移主張（transfer claim）**です。

```text
裏付けのある過去事例の因果メカニズム -> 今回の対象への具体的な対応付け
  -> メカニズムが同様に働くための前提条件 -> 対象側で確認すべき観測指標
```

この連鎖がすべて揃って初めて、過去の事例が今回の分析の根拠になります。見た目が似ているだけのエピソードや引き込まれるような歴史ストーリーを並べても、今回の対象で同じメカニズムが働く証明にはなりません。

**1. 過去事例を探す前に、まず今回の対象自体の構造を描く。** 答えるべき問い、カットオフ時点、予測期間、現在のフェーズを定義して対象の情報を十分に集め、具体的な歴史事例の名前を挙げる前に「今回の対象の構造」をスケッチします（これまでに観測された前提条件・時系列・制約・結果、根拠付きの因果推論、結論を左右し得る未知の要因や未解明のステップ）。この順序を逆にすると、印象的な過去事例の枠組みに今回の問題を無理やり当てはめてしまいます。また、過去時点からの予測再構成を行う場合は、カットオフより後に起きた出来事を使って類似事例を選んだり対応付けを評価したりしないよう厳密に制限します。

**2. 因果の空白（ギャップ）を手がかりに候補事例を広く集める。** 対象フレームの中で「まだ関係が不確かな箇所・欠けている要因・説明がつかない段階」を起点にして、異なる時代・業界・主体から同じ因果ダイナミクスや機能的制約を持つ候補事例を探します。最初に思いついた有名な事例で探索を打ち切らないよう、評価に入る前にまず候補を広く出します。もし候補が特定の業界や定番の歴史談義ばかりに偏っている場合は、対象フレームだけを渡した別コンテキストのサブエージェントを使い、異分野の事例・移転が失敗した事例・逆の結末に終わった事例を提案させます（そのサブエージェントは候補出しのみを行い、本件の結論判断は行いません）。

**3. まず過去事例側の因果メカニズム自体を検証する。** 「A のあとに B が起きた」という時系列だけでは因果説明になりません。残した各候補事例について事実関係を裏付け、主張されているメカニズムを支える証拠を確認し、共通要因・別のメカニズム・偶然・選択バイアス・後付けの物語化によって同じ経緯を説明できないかを点検します。同一事件の別名や部分エピソード、上位概念の言い換えを並べて「複数の独立事例がある」と見せかけることはできません。一方、逆の結果になった事例や前提条件が崩れてメカニズムが働かなかった事例は、反例や適用限界を示す貴重な証拠として活用します。

**4. すべての転移主張を 6 項目で監査する。** 結論に関わるすべての類比主張について、次の 6 要素をセットで保持します。(1) 根拠付きの過去メカニズム、(2) 今回の対象における具体的な対応関係、(3) 前提条件・立場・因果の向き・タイミング・規模・スコープ・インセンティブにおける実質的な相違点、(4) 転移が成立するための仮定、(5) 共通の情報源・包含関係にある出来事・共通の外部ショック・政策模倣・共通制度・同一の測定手法といった従属性、(6) 転移の成否を裏付ける（または覆す）対象側の観測指標。なお、登場主体の行動を予測する際は「自分ならどう動くか」ではなく、その主体自身の目標・制約・インセンティブ・手持ち情報・意思決定プロセスにもとづいて考えます。最終的に残す事例は、候補メカニズム・見落としていた変数・条件分岐シナリオ・観測指標・反例・境界条件のいずれか最低 1 つに実質的な貢献をしているものに限り、単なる読み物としての歴史エピソードは削ぎ落とします。

**5. 複数事例を統合する前に従属性を確認する。** 独立した複数の有益な事例があれば単一ストーリーへの過度な依存は減らせますが、それだけで今回の対象でも同じメカニズムが作動すると決まるわけではありません。一見すると何度も繰り返されているパターンが、実は同じ元の事件・制度・定番言説・共通ショック・波及経路・政策の横並び導入・同じ測定方法から生じていないかを精査します。また、ある要因から特定の結果が生じると主張したいときは、「その要因があったのに結果が起きなかった事例」や「別の経路で同じ結果に至った事例」もあわせて探します。分析者が意図的に選んだ類似事例の集まりは統計的な母集団（参照クラス）ではないため、集めた事例の件数をそのまま基準率や発生確率、信頼度として扱うことはできません。

**6. 「妥当な類似事例は見つからなかった」も正当な結論として認める。** 結論に関わるすべての類比主張について、代替説明と区別できるメカニズムの根拠、向き・段階・スコープ付きの具体的な対応付け、実質的な相違点・従属性・転移条件、および対象側での観測指標が揃い、見つかった反例や破綻した対応付けにも説明がついて初めて分析完了となります。どの候補もこの転移連鎖を満たせない場合は、説得力がありそうなエピソードを無理に残すのではなく、「依拠できる歴史的類比は存在しない」と結論づけます。

### 2 つの方法は連携する

これら 2 つの手法は補完関係にあり、1 つの調査タスクの中で組み合わせることもできます。たとえば `analogical-foresight` で歴史事例から見落としがちな仮説や注目すべき観測シグナルを洗い出し、続く `ach` でそれらの仮説間の判別比較を行うといった連携が可能です。その場合も、歴史事例は今回の対象の直接観測データではなく、あくまで検証可能な転移主張を通じて仮説を支える位置づけになります。

### ドメイン用の Playbook を追加する

プライベートデプロイ環境では、ワークスペーステンプレートに自社独自の Playbook ファイルを追加できます（社内のデューデリジェンス手順、業界固有のデータソース一覧、特定領域の審査基準など）。ファイル冒頭に `name` と `description` を記述しておけば、新しい Job が計画フェーズで自動的にそれを検出し、関連する調査依頼のときに読み込んで適用します。モデルの再学習や本体コードの変更は必要ありません。

## Job の実行中

Agent が調査 Job を作成したあとも、現在のチャット画面はそのまま自由に使えます。別の話題で Agent と会話を続けながら、必要に応じて **Console → Background Agent Jobs** を開けば、調査計画・進捗状況・モデルのトークン消費・現在のステータスをいつでも確認できます。

調査途中で人間の判断が必要になった場合、Job は元の会話スレッドに質問を投稿して `waiting_on_user` 状態になります（これはエラーではなく回答待ちの一時停止です）。元の会話で返信すればそのまま調査が再開されます。また、実行途中に元の会話から参考資料を追加したり条件を補足したりすることもでき、メイン Agent がそれを稼働中の Job へ引き継ぎます。

## 結果を読む

調査 Job が完了すると、メイン Agent はまず生成されたレポートに目を通してからあなたへ届けます。もし調査目的を損なうような重大な情報ギャップや制約がレポート内に記されていた場合、Agent はその旨を正直に伝えます。さらに、不足していた情報が実はメイン Agent 側の記憶にあったり、あなたに 1 つ確認すれば埋まる判断事項だったりする場合は、不完全なレポートをそのまま渡すのではなく、必要な情報を補って Job を継続実行させます。

納品されたレポートを読む際は、出典が結論を本当に裏付けているか、対象期間が守られているか、事実と推論が混同されていないか、そして未解明のギャップや確信度が率直に書かれているかを確認してください。レポートは単体で完結して読める構成になっていますが、個別の根拠をさらに深掘りしたい場合は「Job ワークスペースにある該当ソースノートを読んで詳細を教えて」と Agent に依頼できます。ACH を使った調査であれば、仮説マトリクスの特定の行の評価理由を尋ねることも可能です。

追加の掘り下げが必要になったときも、最初から背景を説明し直す必要はありません。同じ Job を引き継いで続きを調査するよう Agent に伝えるだけです。もし Job が `failed` で止まっていたり `queued` のまま動かなかったりする場合は、詳細画面でステータスやエラー内容を確認してください。各ステータスの意味、キャンセル手順、ランタイム設定については [Background Agent Jobs](../background-jobs/) を参照してください。

## 参考文献と Ankole の違い

Ankole Deep Research の設計は、以下の公開研究の知見と軌を一にしつつ、そこから多くの示唆を得ています。各論文はそれぞれのベンチマークにおける最先端のスコアを報告していますが、私たちが解こうとしている問いは「それらの原則を企業のプライベートデプロイ環境でどう実運用に耐える形にするか」という点にあります。

- Chen, Y., Chen, G., Sun, Y., & Zhang, K. (2026). <a href="https://arxiv.org/abs/2607.13602" target="_blank" rel="noreferrer">Analogical Deep Research: Retrieving and Integrating Historical Analogies for Foresight Analysis</a>. arXiv:2607.13602.
- Zhu, C., Xu, B., Du, M., Wang, S., Wang, X., Mao, Z., & Zhang, Y. (2026). <a href="https://arxiv.org/abs/2602.01566" target="_blank" rel="noreferrer">FS-Researcher: Test-Time Scaling for Long-Horizon Research Tasks with File-System-Based Agents</a>. arXiv:2602.01566.
- MiroMind Team. (2026). <a href="https://arxiv.org/abs/2603.15726" target="_blank" rel="noreferrer">MiroThinker-1.7 & H1: Towards Heavy-Duty Research Agents via Verification</a>. arXiv:2603.15726.

**1. 調査手法をモデルの重みではなく「ファイル」として持つ。** たとえば CANA はエージェントフレームワークとして構成され、MiroThinker はエージェント的な中間学習（mid-training）によってステップごとの信頼性を高め、検証プロセス自体をモデルの推論軌跡に焼き込んでいます。これに対し Ankole では、調査手法をワークスペース上の Playbook ファイルとして記述し、計画時に読み込んで標準の検証手順ごと差し替えられるようにしています。モデルの指示追従能力に品質が左右されるというトレードオフはありますが、その代わりに再学習なしで基盤モデルを自由に乗り換えられ、企業ごとに自社の業務手順や審査基準を Playbook として追加・更新できます。実務の企業調査で本当に差がつくのは汎用知識ではなく「業界固有の型と社内データソースの扱い」だからです。

**2. 自己点検ではなく「情報の遮断と開示順序」で検証の独立性を担保する。** MiroThinker は推論の途中で自らの思考軌跡を自己監査します。一方 Ankole の検証者は、そこまでの会話履歴も内部メモ `research-state.md` も一切引き継がず、さらに ACH では最初に `sources/` だけを読んで独自の仮説比較を組み立ててからでなければ、メイン調査員のマトリクスやレポート案を見ることができません。理由は明快です。自分の思考ログを自分で点検しても同じ思い込み（事前分布）を引きずったままであり、他人の検証であっても先に結論を見せてしまえばアンカリングが起きるからです。

**3. コンテキスト外への退避だけでなく、ジョブのライフサイクル全体で永続化する。** FS-Researcher はファイルシステムを活用してコンテキストウィンドウの壁を越えており、私たちのソースノートとワークスペース設計もその考え方に全面的に賛同しています。Ankole がさらに踏み込んでいるのは、そのワークスペースがリース管理・障害復旧・途中からの追加指示・人間の回答待ち（`waiting_on_user`）を備えた Background Agent Job に紐付いている点です。コンテキストがあふれたときだけでなく、Worker コンテナ自体が再起動・置換されたあとでもそのまま調査を再開できます。また、収集係（ライブラリアン）と執筆係（ライター）を固定的に分業させる構成もとっていません。説得力のある執筆には分析の思考連鎖そのものが必要であり、機械的に役割を切り離すとノートの表面的なつぎはぎになりやすいからです。そのため収集時は「1 ソース 1 オーナー」の重複防止ルールだけを敷き、厳格なコンテキスト分離は独立検証者にのみ適用しています。

**4. 歴史的類比には「反証可能な転移連鎖」を必須とする。** ADR 論文は、モデルが本質的な因果構造ではなく表面的な似通いで過去事例を引いてしまう問題を示し、メカニズムの整列と複数事例のクロス確認を提案しています。私たちの `analogical-foresight` Playbook もこの知見を取り入れたうえで、さらに厳格な「転移連鎖」を課しています。具体的には、複数事例を統合する前に情報源や外部ショックの従属性をチェックすること（同じ 1 つの出来事や言説の反復を「複数の独立した裏付け」と誤認しないため）、そしてすべての類比主張に「今回の対象側で後から観測できる検証指標」を含めることです。レポートを読んだときにただもっともらしく響くだけでなく、後から現実のデータで「この類比は当たっていた／外れていた」と反証できるようにするためです。

**5. ゴールはベンチマークの点数ではなく「依頼者が確認した意思決定目的」に置く。** 研究論文は固定ベンチマークのスコアを最大化しますが、私たちは「このレポートを受け取った 1 人の担当者が次にどんな判断を下すか」に合わせて設計しています。開始前に成功基準をすり合わせ、納品前に 1 項目ずつ達成度を監査し、埋まらなかったギャップには結論への影響を明記します。ギャップが目的達成を妨げるなら、メイン Agent が手持ちの情報を補って Job を続行させます。公開検索より先に社内 Skill の正規データソースを当たり、取れなかったデータを隠さず証拠ギャップとして記録するのも同じ理由からです。企業の現場で本当に使えるレポートかどうかは、「信頼できる正本データに当たったか」と「わからなかったことを正直に書いたか」で決まります——どちらも一般的なベンチマークの採点表には表れない要素です。

ワークスペースの Playbook、検証プロトコル、調査状態ファイル、および納品監査の仕組みは、AgentBull Ankole チームによって設計・実装されています。
