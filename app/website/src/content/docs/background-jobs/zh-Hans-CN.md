后台 Agent 任务适合调研、整理大量文件、制作文档、分析数据或修改代码仓库等耗时工作。任务在后台独立运行，不会占住当前对话；你可以继续与 Agent 交流。

如果你用过 <a href="https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/features/delegation.md" target="_blank" rel="noreferrer">Hermes Agent</a> 或 <a href="https://docs.openclaw.ai/subagents" target="_blank" rel="noreferrer">OpenClaw</a>，可以把它理解为一种类似 subagent（子 Agent）的委派机制：主 Agent 把一项独立工作交给另一个运行上下文。

Ankole 把它称为“后台 Agent 任务”，因为系统保存的是一项有完整生命周期的工作，而不是一次临时调用。任务可以在 Worker 中断后恢复。

主 Agent 可以继续向任务补充信息。大多数任务会把需要确认的问题、失败状态和最终结果送回原会话；若你没有要求回传，也可以让任务静默运行，之后再主动查看。

## 选择 Workflow 还是后台 Agent 任务

两者都能委派工作，但负责的工作形态不同：

| 使用 | 适用情况 |
|---|---|
| [Workflow](../workflows/) | 输入数量有限，任务可以相互独立执行，而且运行前就能固定各个阶段。它可以并行展开有界核验，并返回一个汇总结果。 |
| 后台 Agent 任务 | 一项长期工作需要持久工作区、文件或浏览器操作、后续消息、向你提问，或可恢复的 Codex thread。 |

Workflow 任务不能接收后续消息、创建嵌套工作或使用后台任务工作区；后台 Agent 任务则可以在收到新信息后调整方向。工作需要保留持续上下文时选择后台任务；主要需求是有界并行时选择 Workflow。

## 让 Agent 创建后台任务

直接在聊天中说明目标，并明确希望后台执行。例如：

```text
请把这项工作作为后台 Agent 任务执行：阅读这些材料，整理一份决策备忘录，
列出依据、分歧和仍需确认的问题。完成后把结果发回这个会话。
```

把输入文件、完成标准和输出格式一次说清楚。若任务必须在某个时间前结束，也应在消息中写明。Agent 会决定怎样拆解和执行，但不会因为任务进入后台就自动获得额外权限。

## 在任务运行时继续沟通

任务开始后，主 Agent 仍可以向它补充材料、修正要求或询问当前状态。任务正在执行时，新消息会交给当前工作；任务正在等你回答时，新消息会让它从原有上下文继续。

你只需在请求中说明希望怎样协作：

- **完成后通知我**：适合可以独立完成的长任务。你可以继续聊天，任务结束后会把结果发回原会话。
- **先在后台查清，再继续回答**：适合当前问题必须等研究结果才能回答的情况。Agent 会等待任务完成，再用结果继续当前工作。
- **有关键选择时问我**：适合方向或成本需要你决定的任务。任务会暂停并在原会话提问，收到回答后继续。
- **静默执行**：适合只需在后台产出文件，或准备稍后主动查看的工作。告诉 Agent 不必主动回传；之后可以在原会话询问，也可以在 Console 中查看。
- **继续上一次任务**：告诉 Agent 要继续哪项工作及新增要求。只要原任务仍可继续，Agent 会保留既有上下文，不必从头开始。

例如：

```text
请在后台比较这三份方案。完成后告诉我；如果需要扩大调研范围，
或要使用付费数据源，请先在这个会话里问我。
```

若任务需要代码仓库、资料集或预装工具，可以在请求中说明。Agent 会选择合适的工作区；你不需要填写工作区模板 ID 或调用后台任务接口。

## 选择模型 Provider

所有后台任务都通过 AIGateway 运行。创建任务时，Ankole 会保存当时生效的“后台 Agent 任务”模型档案；若该档案为空，则回退到 Agent 的 `heavy` 档案。

要使用 ChatGPT 订阅，先创建一个 [ChatGPT 订阅 Provider](../chatgpt-subscription-provider/)。然后打开 Console 的**智能体**，在该 Agent 的模型档案中找到**后台 Agent 任务**，选择该 Provider、账号有权使用的模型、推理强度和 Fast Mode。Provider 的凭据池会自动选择并轮换账号，任务本身不选择账号。

## 在 Console 中查看任务

打开**后台 Agent 任务**。看板按状态分为待处理、进行中和已结束三列。选择一个任务可以查看原始要求、当前计划、各轮执行记录、模型用量、结果或错误。

| 状态 | 含义 | 需要做什么 |
|---|---|---|
| `queued` | 已接受，正在等待可用 Worker | 通常只需等待；若长期不动，检查 Worker 是否可用 |
| `running` | 正在执行 | 打开任务查看计划和最新进展 |
| `waiting_on_user` | 等待你的补充或确认 | 回到创建该任务的原会话回答问题 |
| `succeeded` | 已完成 | 查看结果；若要求了回传，再确认原会话是否收到通知 |
| `failed` | 执行失败 | 读取错误；修正配置或输入后，让 Agent 创建新任务 |
| `stopped` | 已取消 | 任务不会继续执行 |

`waiting_on_user` 不是故障。任务会释放运行资源，等你在原会话回答后再继续。不要另开一个无关会话回答，否则任务无法确定这条回复属于哪个问题。

## 取消任务

打开任务详情，选择**取消**。已经开始的一轮可能需要短暂时间才能停下，所以状态不会总是立即变成 `stopped`。取消不会删除已经产生的文件和执行记录。

如果只是想修正目标，先在原会话告诉 Agent。只有任务已经走错方向、占用资源或不再需要时，才取消并重新创建。

## 常见问题

- **一直处于 `queued`**：确认至少有一个 Worker 处于可用状态，并检查是否已有较多任务占用运行槽。
- **开始后立即失败**：检查已保存的后台任务模型档案，以及所选 Provider 的凭据池状态。
- **显示 `waiting_on_user`，但聊天中没有问题**：检查原会话的信号路由规则和聊天渠道是否还能投递消息。
- **任务完成但没有回到聊天**：先确认任务是否采用了静默方式。若没有，打开任务确认结果已经生成，再检查原会话的路由规则。
- **修改模型档案后已 admission 的任务没有变化**：Provider 绑定在第一次 execution admission 时确定。修改只影响尚未 admission 的任务。
