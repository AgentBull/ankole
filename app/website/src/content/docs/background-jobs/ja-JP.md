Background Agent Job は、本格的な調査、大量ファイルの処理、ドキュメント生成、データ分析、リポジトリのコード変更など、時間のかかる作業を任せるための機能です。バックグラウンドで独立して処理が進むため、実行中もそのまま同じ会話で Agent とやり取りを続けられます。

<a href="https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/features/delegation.md" target="_blank" rel="noreferrer">Hermes Agent</a> や <a href="https://docs.openclaw.ai/subagents" target="_blank" rel="noreferrer">OpenClaw</a> を使ったことがあれば、最も近い概念はサブエージェントです。メイン Agent が独立した作業を別の実行コンテキストへ切り出して委任します。

大きな特徴として、Ankole は各タスクを一度きりの関数呼び出しではなく、完全なライフサイクルを備えた「復旧可能な永続ジョブ」として管理します。途中で Worker の切断やクラッシュ、サーバーの再起動が起きても、中断した地点からそのまま処理を再開できます。

実行中にメイン Agent から追加情報を渡すことも可能です。通常、Job からの確認事項やエラー報告、最終成果物は元の会話へ返されますが、途中経過の通知が不要な場合は静かに実行させて後から結果だけを確認することもできます。

## Workflow と Background Agent Job を選ぶ

どちらも作業を委任する機能ですが、向いているタスクの形が異なります。

| 使用する機能 | 選ぶ場面 |
|---|---|
| [Workflow](../workflows/) | 入力数が有限で、各タスクを独立して並行処理でき、実行開始前に処理ステップが固まっている場合。上限付きのチェックを並列実行（fanout）し、集約した結果を 1 つ返せます。 |
| Background Agent Job | 1 つの長いタスクで、永続的な workspace、ファイル操作やブラウザー操作、途中での追加指示、人間への確認質問、または再開可能な Codex スレッドが必要な場合。 |

Workflow の各タスクは実行開始後に追加メッセージを受け取ることができず、ネストした子作業の作成や Job workspace の利用もできません。一方、Background Agent Job は実行途中で新しい情報が届けば方針を柔軟に切り替えられます。継続的な文脈や試行錯誤が必要なら Background Agent Job を、定型かつ上限付きの並列処理が目的なら Workflow を選んでください。

## Agent に Job の作成を依頼する

チャットで達成したい目標を伝え、バックグラウンドで実行してほしい旨を明記します。たとえば次のように依頼します。

```text
Run this as a Background Agent Job. Read these materials and prepare a decision
memo with evidence, disagreements, and open questions. Return the result here.
```

参照してほしい入力ファイル、完了条件、求める出力フォーマットも最初の依頼にまとめて書いておくとスムーズです。締め切りがある場合はそれも伝えてください。具体的な進め方は Agent が組み立てますが、バックグラウンド実行だからといって通常より広いアクセス権限が付与されるわけではありません。

## Job の実行中も会話を続ける

Job が動き始めたあとも、メイン Agent を通じて参考資料を追加したり、要件を軌道修正したり、現在の進み具合を尋ねたりできます。送ったメッセージによって、進行中の作業の方向性を調整（ステアリング）したり、回答待ちで一時停止している Job を再開させたりできます。

依頼時には、Agent と Job にどう連携してほしいかをあわせて伝えておくと効果的です。

- **完了したら通知:** 単独で最後まで進められる作業に向いています。元の会話に最終結果が届くのを待つ間も、別の話題でチャットを続けられます。
- **バックグラウンドで調査してから回答を続ける:** 今の会話の結論を出すために、まずまとまった下調べが必要な場合に使います。
- **重要な選択の前に確認:** 方針転換や有料データソースの利用など、人間の判断を挟みたい場合に使います。Job は該当箇所で一時停止して元の会話に質問を投げ、あなたが返信すると再開します。
- **サイレントに実行:** ファイルの生成だけ済ませておいて、後から自分のタイミングで確認したい場合に使います。途中経過を送らないよう伝えておけば、後からチャットで尋ねるか Console で結果を確認できます。
- **前の Job を継続:** 以前の作業を指定したうえで追加要件を伝えます。対象の Job が再開可能な状態であれば、既存の workspace とコンテキストを引き継いで作業を続けられます。

依頼例:

```text
Compare these three proposals in the background. Notify me when you finish.
Ask me here before you expand the scope or use a paid data source.
```

リポジトリやドキュメント一式、特定のインストール済みツールが必要かどうかも伝えておけば、Agent が適切なワークスペースを自動で選びます。ユーザーが workspace テンプレート ID を調べたり、Job API を直接叩いたりする必要はありません。

## モデル provider を選択する

すべての Job は AIGateway 経由でモデルを呼び出します。Job の作成時に、その時点で有効な **Background Agent Jobs** モデルプロファイルが記録されます（未設定の場合は、その Agent の `heavy` プロファイルにフォールバックします）。

ChatGPT サブスクリプションを利用したい場合は、まず [ChatGPT subscription provider](../chatgpt-subscription-provider/) を登録します。その後 Console で **Agents** を開き、対象 Agent のモデルプロファイル欄にある **Background Agent Jobs** でその provider、使用モデル、推論強度（reasoning effort）、および Fast Mode を選択してください。複数アカウントを登録している場合は、provider の認証情報プールが自動でアカウントの選択とローテーションを行います。

## Console で Job を確認する

Console の **Background Agent Jobs** を開くと、すべての Job が `queued`・`active`・`finished` の列に整理されたボード形式で表示されます。各 Job を開くと、元の依頼内容、現在の実行計画、ターン履歴、モデルのトークン使用量、最終結果やエラー詳細を確認できます。

| ステータス | 意味 | 対処方法 |
|---|---|---|
| `queued` | 受け付け済みで、Agent の Worker 起動または空きスロットを待機中 | 通常はそのまま待ちます。長く進まない場合は **Console → Workers** で対象 Agent の Worker 状態を確認してください。 |
| `running` | 作業を実行中 | Job 詳細を開くと、現在のプランと最新の進捗を確認できます。 |
| `waiting_on_user` | Agent または人間からの回答を待機中 | Agent 自身で判断できる質問には Agent が自動で回答します。あなたに質問が届いた場合は、Job を依頼した元の会話で返信してください。 |
| `succeeded` | 正常に完了 | 結果を確認します。完了通知を依頼していた場合は、元の会話にも返信が届いているか確認してください。 |
| `failed` | エラーにより完了できず終了 | エラー内容を確認し、入力資料やモデル設定を見直したうえで、Agent に新しい Job の作成を依頼してください。 |
| `stopped` | キャンセル済み | これ以上処理は続行されません。 |

なお、`waiting_on_user` はエラーではありません。Job から確認事項が上がってきた際、メイン Agent がすでに答えを持っていれば自分で回答を返し、人間の判断・承認・追加情報が必要な場合だけあなたに尋ねます。待機中は Worker の実行スロットを解放し、回答が届き次第そのまま再開します。Agent から質問されたときは、必ず Job を開始した元の会話スレッドで返信してください（別の無関係な会話で返答しても、待機中の質問と紐付けることができません）。

## Job をキャンセルする

停止したい Job を開いて **Cancel** を選択します。すでに進行中のターンがある場合は安全な停止処理に少し時間がかかるため、ステータスが即座に `stopped` へ切り替わらないことがあります。

キャンセルしても、そこまでに Job が生成したファイルや実行ログは削除されずに残ります。

作業のゴールを少し修正したいだけであれば、キャンセルする前にまず元の会話で Agent に伝えてみてください。見当違いの方向へ進んでしまっている場合や、不要なリソースを消費している場合、あるいは作業自体が不要になった場合は、キャンセルしてから新しい Job を依頼するのが確実です。

## よくある問題

- **Job が `queued` のまま進まない:** 対象 Agent の Worker が `ready` になっているか、また同じ Agent の他の実行中 Job が同時実行上限（`background_agent_jobs.max_running_per_agent`）を使い切っていないか確認してください。
- **開始直後に `failed` になる:** Agent に保存されている Background Agent Jobs モデルプロファイルの設定と、選択した provider の認証情報プールの状態を確認してください。
- **`waiting_on_user` なのに質問が届かず、Agent も自動回答していない:** 元の会話に紐付くシグナルルーティングルールと Channel Provider の接続状態を確認してください。
- **`succeeded` になったのにチャットへ結果が返ってこない:** まず「サイレント実行」を指示していなかったか確認してください。通知ありで依頼していた場合は、Job 詳細画面に結果が出力されているかを見たうえで、元の会話のルーティングルールを確認してください。
- **実行中（admission 済み）の Job にモデルプロファイルの変更が反映されない:** 使用する provider とモデルの紐付けは、初回の実行受け入れ（execution admission）時点で固定されます。プロファイルの変更は、まだ admission されていない新しい Job から適用されます。
