Ankole は、Company Brain を備えた企業向け Agent Harness です。企業が管理する基盤で動作し、意思決定に必要なコンテキスト、権限、永続的な実行、フィードバックをモデルに提供します。

Agent は数時間にわたって作業し、共有の Company Brain を使い、ブラウザー、ターミナル、ファイル、外部システムで仕事を実行し、人が確認して後の結果で検証できる判断を提示します。

Harness は各行動主体を識別し、アクセス規則を適用し、長時間の仕事を復旧し、コンテキストを最新に保ち、修正を次の意思決定に引き継ぎます。

## システム全体図

<DocsArchitectureDiagram lang="ja-JP" />

1 つのプライベートな deployment instance は、1 つの論理 control plane と、Agent ごとに 1 台の Agent Computer Worker を持ちます。control plane は Identity、state、schedule を管理し、Worker を作成します。各 Worker は、その Agent が実際に働く compute 環境を提供します。

Pod と外部アダプターが会話の発言を記録します。Signals が発言、外部イベント、時刻の刺激を受け付け、Sessions が作業を実行します。Identity Provider が人と組織ディレクトリを供給します。AIGateway は model、embedding、rerank、画像、web 能力に対する 1 つの境界を提供します。

## Control plane と Agent Computer Worker

### control plane は state を保存し、決定を行います

Elixir/OTP の control plane は、Console、Principal とアクセス、システム configuration、signal の routing、実行セッション、Brain、Background Agent Job、AIGateway、Control Plane Plugin を担います。

これらの module はすべて同じ規則に従います。ユーザーに見える結果を変える state は、実行や外部への送信を駆動する前に PostgreSQL に書き込まれます。

process は再起動できますが、受け付け済みの message、Job state、memory、audit 記録は残らなければなりません。

OTP の supervision tree は、Agent、connection、Job それぞれに独立した failure domain を与えます。1 つの実行 branch がハングまたは crash しても、control plane は deployment instance 全体を失敗させることなく、その branch だけを復旧できます。

### Worker は Agent の仕事用コンピュータです

主 Agent loop は control plane で動作します。環境ツールまたは Codex が必要な時点で Agent Computer Worker を起動します。Worker はツール、Skills、browser、terminal、file 操作、automation script、Codex Job を実行し、control plane が永続結果をコミットします。

各 Agent は 1 つの Worker ID を持ち、同時に接続を許可する Worker インスタンスは最大 1 つです。Agent 同士が Worker、キャッシュディスク、credential を共有することはありません。Worker の container または Pod が唯一の分離境界です。Agent のコマンドは内側の sandbox なしで実行され、Agent 自身のコンピュータを変更できます。Kubernetes では、Pod template の runtime class で gVisor を追加できます。

control plane は Agent が選んだ provider で Worker を管理します。Docker、Kubernetes、Cloudflare、Vercel、AWS Lambda MicroVMs、Alibaba Function Compute に対応します。Home は `/workspace` の永続ストレージで、`/var/cache/ankole` は破棄可能なキャッシュです。コマンドは sudo なしの uid 1000 で動作します。

RuntimeFabric は Worker ごとに 1 本の Phoenix Channel で control plane と Worker を接続します。wakeup、steering、cancel、進捗、実行結果を運びます。

これは低遅延のライブ channel であり、database ではありません。connection が切れた後の復旧は、依然として PostgreSQL の state を使います。

### Worker pool がプラットフォームと設定を選ぶ

オペレーターは **Settings → Worker providers** で Worker pool を設定します。1 つの provider は site 全体の pool で、プラットフォームの種類、YAML 設定、暗号化したプラットフォーム認証情報を持ちます。複数 Agent が同じ pool を使っても、各 Agent のコンピュータと永続 Home は専用です。種類やインスタンス仕様が異なる場合は別の pool を使います。

Agent 作成時に pool を選ぶか、site の既定 pool を使います。その選択は後から変更できません。control plane は必要時に Worker を起動し、アイドル時に解放または休止します。古いインスタンスは Home を保持して置換し、キャッシュは別途再構築できます。[Worker pool](../worker-management/) を参照してください。

環境 workspace と Codex turn の容量は Worker ごとに制限します。主会話と Workflow のモデル呼び出しは control plane で実行し、この容量を使いません。pool の追加は配置先の選択肢を増やしますが、既存 Agent の作業を共有コンピュータ間で移動しません。

## 1 つのメッセージが再開可能な仕事になるまで

### 会話は参加者の発言を保存する

会話は人と Agent が共有する空間です。`Ankole.Conversations` は参加者とメッセージを保存します。Pod はネイティブの発言を直接書き込みます。アダプターは外部の会話を観測し、その内容の正本は外部プラットフォームにあります。

会話の発言と Agent の作業は別の記録です。発言は参加者の記録です。モデル呼び出し、ツール結果、圧縮は、実行セッションに対応する AIGateway のモデル状態に属します。実行セッションは複数の会話をまたがず、ある会話の作業が別の会話に入りません。

### Signals はすべての刺激を受け付ける

Agent を指名した発言は signal を生成します。時刻、外部イベント、check-back、タスク完了も signal です。`Ankole.Signals` は、実行セッションを起こす前に、出所、出所イベント ID、宛先、帰属、認可を永続化します。

ネイティブの発言とその signal は同じトランザクションでコミットされます。受付時に `(Agent, source, id)` で重複を除きます。後続のすべての操作が 1 回だけ実行される保証ではありません。

signal は実行セッションを直接指定できます。指定がなければ、会話への参加関係または Signal Routing Rule が宛先を選びます。会話ホストのアダプターは発言を観測し、返信を配送します。イベントソースのアダプターは signal だけを生成します。Automation Job は機械的な検査を行い、判断が必要なときに親の実行セッションへ signal を送ります。[Automation Jobs](../automation-jobs/) を参照してください。

### Sessions は作業を実行して復旧する

`Ankole.Sessions` はキュー、Admission、Driver、Run、ツール、復旧を所有します。1 つの実行セッションは同時に 1 つの Run を実行します。開始のたびに Admission がテナント、Agent の状態、認可、使用量制限を確認します。

各 Agent は会話内で独自の実行セッションを持ち、その作業を会話の全参加者が閲覧できます。指名されたターンは依頼者の認可を使います。自発的な介入は既定で Agent 自身の権限を使います。既存の介入方針がある人を現在の依頼者と認定した場合だけ、その人の認可を使います。

cron 規則とバックグラウンドタスクは独立した実行セッションを持ち、結果を対象の会話に発言します。会話の次のターンは新しい発言を読み込み、他の実行セッションの内部作業は取り込みません。

AIGateway はモデル状態を保存して継続します。ランタイムは入力、指示、ツール、継続、圧縮を決めます。Driver の PostgreSQL epoch は古い書き込みを拒否します。復旧はコミット済みの進捗から続きます。モデル呼び出しは繰り返す場合があります。記録済みのツール結果は再利用し、結果が不明な呼び出しは中断として報告します。

### Presentation と Delivery は可視の結果をコミットする

Presentation は可視の返信を 1 回だけ決定します。ネイティブの返信は完了トランザクション内で発言になります。silent turn は発言しません。外部の返信は永続的な Delivery 意図を作り、アダプターが送信します。

外部プラットフォームが成功を確認したら、配送成功を記録する同じトランザクションで発言を保存します。その後の同じメッセージ ID のイベントは同じ発言に統合されます。失敗、期限切れ、結果不明の配送は発言を作りません。結果不明の送信を無条件に繰り返しません。

ストリームのテキストは進捗であり、発言のコミット後に会話履歴となります。切断後はコミット済み履歴と実行状態を読み直し、途中のストリームは再送しません。

設計の選択、コスト、ソースを確認した比較は[会話、シグナル、実行セッション](../conversations-signals-sessions/)を参照してください。

## Brain: 現在の状態を保つ世界モデル

Brain はチャットの抜粋を詰め込んだベクトルデータベースではありません。変化し続ける世界の見取り図を維持します。新しい証拠は以前の Claim を補足、修正、または置換できます。証拠が矛盾する場合、Dreaming は人が確認できる記録を作り、関連する Claim を密かに書き換えません。

知識は、Agent との会話、対象となるグループ内で誰も Agent に宛てなかったメッセージ、登録済みのファイルまたは URL Source から得られます。

同じテナントの Agent が知識空間を共有し、テナント間の知識空間は分離されます。保護された本文、Claim、Timeline イベントは、`world`、権限グループ、または 1 つの Principal の開示範囲を持ちます。Source と外部の会話は出所を記録しますが、学習した知識へのアクセス権を付与しません。

ターンの間、統合された想起が現在の仕事に必要な長期コンテキストを供給します。オフラインの Dreaming は新しい証拠を整理し、パターンを見つけ、以前の予測を採点し、確認が必要な矛盾を示します。

[Brain](../brain/) は「世界が今どのような状態か」を担います。[Skill Lessons](../skill-lessons/) は、繰り返し現れる作業証拠から Agent が学んだ手順上のガードレールを保存します。対応する Skill と共に提示されますが、Skill のソースは書き換えません。適用できなくなった Lesson は退役します。

この構造は、Agent が時間とともにチームの規則を学ぶというホームページ上の約束を実現します。蓄積は、より長い log を意味しません。次の Job がより良い知識とより良い方法から始まることを意味します。

ユーザーから見えるのはこの仕組みの長期記憶であり、保存、Dreaming、書き込み権限は Brain が担います。

## Background Agent Job: メイン session をブロックしない長時間の仕事

メイン Agent は、調査、データ分析、file 作業、code 変更、Deep Research を Background Agent Job に委任できます。メイン session は利用可能なまま、ユーザーとの会話を続けられます。

control plane は Job の lifecycle を保存します。インスタンス置換後は永続 Home の workspace と Codex スレッドから再開します。PostgreSQL は受け付けた作業と復旧状態を保持します。

メイン Agent と Job は通信を続けられます。Job は input を求めたり、失敗や最終結果を返したり、要求されれば沈黙を保ったりできます。人を待つ間は実行 slot を解放し、回答が届いてから再開します。

Deep Research はこの architecture の高度な利用法です。Agent Plugin が workspace template を提供し、Skill が調査方法を提供し、Background Agent Job が durable な実行を提供します。

Job の workspace は永続 Home に残ります。Worker の外で使う調査資料と成果物は、Agent がコントロールプレーンのドライブに公開します。

[Background Agent Jobs](../background-jobs/) と [Deep Research](../deep-research-job/) を参照してください。

## AIGateway: AI 能力のための 1 つの境界

AIGateway は model の能力を Agent の実行から分離します。メイン Agent、Job、Brain、外部 API client は、LLM、embedding、rerank、画像、Web Search、Web Fetch Provider に対して同じ境界を使います。

Agent の model profile が実行モデルを選択します。各テナントが選ぶ Brain maintainer Agent の `light`、`heavy`、`web_fetch` profile が Brain の作業を担当します。サイトの AppConfigure が embedding モデルを、テナントの AppConfigure が rerank モデルを選択します。control plane は Provider credential を暗号化して保存し、AIGateway が上流への request に使用します。

Agent と Worker が受け取るのは、使用できる model の選択と呼び出し結果だけです。

AIGateway は、履歴を保存しない呼び出しと、継続できる モデルセッション状態の両方をサポートします。request の変換、stream event、tool の結果、context の圧縮、使用量記録、最終結果のコミットを担います。

Worker は Provider ごとに個別の lifecycle を実装しません。

tool catalog が大きい場合、model は Tool Search で tool をオンデマンドに検索するか、制限された sandbox 内で多数の tool を呼び出して結果だけを返す 1 つの program を提出できます。ネイティブ対応の Provider は呼び出しをそのまま透過させ、AIGateway はそれ以外のすべての Provider に対して gateway 内で同じ能力を提供します。1 つの Provider は複数の credential を pool として保持することもでき、ChatGPT サブスクリプションのような account credential も含まれます。失敗の帰属、retry、使用量記録は credential 単位で残ります。

[AIGateway](../ai-gateway/) と [LLM Provider の追加](../adding-a-provider/) を参照してください。

## エンタープライズ Identity、アクセス、拡張

Ankole は、人、Agent、システムサービスを Principal として表します。Identity Provider が Console の SSO を提供し、従業員、連絡先、組織ディレクトリを同期します。

chat channel が message を送受信します。これらの Provider は異なる platform を使えます。

AuthZ は実行時に、Principal、permission group、resource、action、condition から判定します。アクセスは prompt の中の 1 文ではなく、model が permission を持っていると宣言することもできません。

Control Plane Plugin が IdP、chat channel、その他の control plane 能力を接続します。Agent Plugin は tool と workspace template を追加します。

Skill は、ある種の仕事のやり方を説明し、メイン Agent または Background Agent Job に限定できます。

外部の MCP server は Skill を通じて入ります。Skill が接続を宣言し、Worker が実行ごとの configuration を生成して実行終了時に削除するため、model がすべての MCP tool の常駐リストに直面することはありません。

[Principal と permission group](../principal-and-groups/)、[signal routing rule](../signal-bindings/)、[Agent Library](../skills/)、[MCP server リファレンス](../mcp/) を参照してください。

## Durability の境界

PostgreSQL は、identity、access、configuration、message、session、Job、memory、delivery state、audit 記録などの durable な domain 事実を保存します。システムが結果をコミットしたかどうかの判断には、これらの記録を使います。

control plane のファイルストアは添付ファイル、公開ファイル、Skill、Automation スクリプトを保持します。永続 Home は workspace、ユーザーパッケージ、Codex スレッドを別に保持します。PostgreSQL、ファイルストア、全 Home、元の暗号化キーを一緒にバックアップします。

RuntimeFabric、Worker プロセス、ストリーム表示、`/var/cache/ankole` は再作成できます。永続 Home はインスタンス削除後も残し、ストレージバックアップが必要です。[バックアップとリストア](../backup-and-restore/)を参照してください。

## 3 つの deployment 形態

| 形態 | control plane と Worker | 永続化 |
| --- | --- | --- |
| **Docker Compose · 単一ホスト向け推奨** | 1 台の Linux、macOS、Windows ホストが control plane を実行し、control plane が Agent ごとに Docker socket を通じて 1 台の Worker container を作成 | PostgreSQL、ファイルストア、Agent ごとの専用永続 Home volume |
| **Kubernetes · エンタープライズ deployment 向け推奨** | 1 つの control plane が、Agent ごとに Kubernetes API を通じて 1 つの Worker Pod を作成 | PostgreSQL、ファイルストア、Home PVC または共有ストレージ。キャッシュは別 volume |
| **ソースインストール** | `bun dev` が control plane を実行し、control plane が Agent ごとに Docker の Worker container を作成。container はローカルの Agent Computer ソースを watch モードで実行 | PostgreSQL、`var/ankole-dev/files`、専用 Docker 永続 Home volume |

論理的な境界はどの形態でも同じです。instance は control plane を 1 つ持ち、control plane が各 Agent に専用の Worker を用意します。完全な手順は [クイックスタート](../quickstart/#deployment) を参照してください。

## 5 つの技術的判断

| 判断 | 解決する問題 |
| --- | --- |
| **Virtual Actor が AI の仕事を担う** | 各 session に address、mailbox、lifecycle、recovery position を与える |
| **OTP supervision tree が failure domain を定義する** | instance 全体を失敗させずに、1 つの Agent または connection の branch を復旧する |
| **Phoenix Channel がライブ制御を運ぶ** | Agent の実行中に wakeup、steering、進捗、backpressure を運ぶ |
| **Agent Computer Worker が実行を提供する** | 各 Agent に、tool、file、terminal、browser、Codex のための専用コンピュータを与える |
| **PostgreSQL の ledger が事実を保存する** | message、Job、memory、決定、コミット済み操作を再開可能かつ audit 可能にする |

これらの判断は 1 つの結果を支えます。Agent は数時間働き、実行中に新しい情報を受け取り、独立して失敗と復旧を行い、コミットされた各 action の痕跡を残せます。
