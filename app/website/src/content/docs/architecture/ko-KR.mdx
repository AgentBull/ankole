Ankole은 Company Brain을 갖춘 오픈 소스 엔터프라이즈 Agent Harness입니다. 조직이 직접 운영하는 인프라 위에서 모델 추론, 영구 상태, 권한 체계, 전용 실행 환경을 하나로 결합합니다.

이를 통해 Agent는 몇 시간에 걸친 장기 업무를 수행하고, 공유 Company Brain을 참조하며, 브라우저·터미널·파일·외부 시스템을 다루어 실무를 처리하고, 사람이 검토하고 실제 결과로 사후 검증할 수 있는 의사결정을 남깁니다.

여기서 모델은 추론을 맡고, Harness는 작업 주체 식별, 접근 권한 강제, 장기 작업의 장애 복구, 컨텍스트 갱신, 그리고 피드백과 결과의 반영을 책임집니다.

## 시스템 지도

<DocsArchitectureDiagram lang="ko-KR" />

단일 프라이빗 배포 인스턴스는 논리적 컨트롤 플레인 하나, 무상태(stateless) `Function Runtime`(`ankole-function-runtime`) 서비스, 그리고 Agent마다 할당되는 전용 Agent Computer Worker로 구성됩니다. 컨트롤 플레인은 identity와 상태 및 스케줄링을 총괄하고 Pod 협업 워크스페이스를 운영합니다. 또한 Pod Applet 백엔드 함수나 결정론적 TypeScript 프로그램을 실행할 때는 `Function Runtime` isolate를 호출하며, 환경 작업이 필요할 때는 각 Agent에게 전용 컴퓨팅 환경을 제공하는 Worker를 기동합니다.

대화 발언은 Pod(페이지, 실시간 협업 문서, 물리 샤드 기반 2계층 Base 테이블, Applet, 멀티플레이어 Pod Chat)와 외부 채널 어댑터를 통해 기록됩니다. 발언이나 외부 이벤트, 예약 시각 같은 자극은 Signals가 접수하고 실제 실행은 Sessions가 담당합니다. 인증 계층과 Identity Provider는 패스워드리스 Email OTP(`SiteCredential`), 엔터프라이즈 SSO, 조직 디렉터리 동기화를 제공하며, AIGateway는 언어 모델, 임베딩, 리랭크, 이미지 생성, 웹 도구를 아우르는 단일 호출 경계를 형성합니다.

## 컨트롤 플레인, Function Runtime 및 Agent Computer Worker

### 컨트롤 플레인은 상태를 저장하고 결정을 내립니다

Elixir/OTP 기반 컨트롤 플레인은 Pod(페이지, 문서, Base 테이블 및 물리 샤드, Applet, 멀티플레이어 Pod Chat), Console, Principal과 접근 권한, 시스템 설정, 신호 라우팅, 실행 세션, Brain, Workflow, Background Agent Jobs, AIGateway, Control Plane Plugins를 통합 관리합니다.

이 모든 하위 모듈은 한 가지 원칙을 공유합니다. 사용자에게 보이는 동작을 바꾸는 모든 상태 변경은 실제 실행이나 외부 메시지 전송에 앞서 반드시 PostgreSQL에 먼저 커밋됩니다.

따라서 런타임 프로세스가 재시작되더라도 이미 수락한 메시지와 Job 진행 상태, 기억(memory), 감사 기록은 유실되지 않고 그대로 보존됩니다.

또한 OTP 감독 트리(supervision tree)를 통해 Agent, 외부 연결, 백그라운드 Job마다 독립된 장애 도메인을 둡니다. 특정 실행 경로 하나가 멈추거나 비정상 종료되더라도 컨트롤 플레인이 해당 브랜치만 격리해 복구하므로 전체 배포 인스턴스는 영향받지 않습니다.

아울러 핵심 상태 머신과 컨트롤 플레인 주요 경로에는 정형 검증(formal verification)을 적용하여, 재시도·프로세스 재시작·동시 입력이 겹치는 상황에서도 상태 전이와 경계 불변식이 깨지지 않도록 검증합니다.

### Worker는 Agent의 작업용 컴퓨터입니다

주 Agent 루프는 컨트롤 플레인에서 실행되며, 파일·셸 같은 환경 도구나 Codex 실행이 필요해질 때 비로소 Agent Computer Worker를 시작합니다. Worker가 도구, Skill, 브라우저, 터미널, 파일 조작, automation script, Codex Job을 실행하면 컨트롤 플레인이 최종 영구 결과를 커밋합니다.

각 Agent는 고유한 Worker ID를 하나씩 가지며, 동시에 유효한 것으로 인정되는 Worker 인스턴스도 최대 한 대뿐입니다. 서로 다른 Agent끼리는 Worker 인스턴스나 캐시 디스크, 자격 증명을 절대 공유하지 않습니다. 컨테이너(또는 Pod) 자체가 격리 경계이므로 내부 명령은 추가 샌드박스 없이 실행되어 해당 Agent 전용 컴퓨터 환경을 자유롭게 변경할 수 있습니다. 더 강한 커널 격리가 필요한 Kubernetes 환경에서는 Pod 템플릿에 gVisor runtime class를 지정할 수 있습니다.

컨트롤 플레인은 Agent에 지정된 provider 설정에 따라 Docker, Kubernetes, Cloudflare, Vercel, AWS Lambda MicroVMs, Alibaba Function Compute 위에서 Worker 수명 주기를 관리합니다. `/workspace`는 영구 보존되는 Agent Home이고 `/var/cache/ankole`은 언제든 재생성할 수 있는 임시 캐시이며, 모든 명령은 `sudo` 없이 `uid 1000`으로 실행됩니다.

컨트롤 플레인과 각 Worker는 Worker당 하나씩 열리는 RuntimeFabric Phoenix Channel로 실시간 연결되어 웨이크업, 스티어링, 취소 지시, 진행 상태, 실행 결과를 주고받습니다.

다만 RuntimeFabric은 저지연 실시간 제어 채널일 뿐 데이터베이스가 아니므로, 연결이 끊겼다가 복구될 때는 언제나 PostgreSQL에 커밋된 상태를 기준으로 재개합니다.

### Worker pool은 플랫폼과 설정을 선택합니다

운영자는 **Settings → Worker providers**에서 사이트 단위의 Worker pool을 구성합니다. 각 provider 항목은 실행 플랫폼 종류, YAML 세부 설정, 암호화된 플랫폼 자격 증명을 담습니다. 여러 Agent가 동일한 pool을 바라보더라도 실제 컴퓨터 인스턴스와 영구 Home은 Agent마다 개별 할당되며, 플랫폼 종류나 인스턴스 사양을 달리해야 할 때는 별도의 pool을 추가합니다.

Agent를 생성할 때 특정 pool을 지정하거나 사이트 기본 pool을 할당하면 이후 그 선택이 계속 유지됩니다. 컨트롤 플레인은 작업이 들어올 때 Worker를 띄우고 유휴 상태가 지속되면 일시 중지하거나 회수합니다. 오래된 인스턴스를 교체하더라도 영구 Home은 그대로 이어지며, 임시 캐시 디스크만 별도로 재구축할 수 있습니다. 자세한 구성 방법은 [Worker pool](../worker-management/)을 참조하세요.

열린 환경 workspace와 Codex turn 동시 실행 수는 Worker 단위로 제한됩니다. 반면 일반 대화와 Workflow의 모델 호출은 컨트롤 플레인에서 바로 실행되므로 Worker 슬롯을 점유하지 않습니다. 새 pool을 추가하면 신규 Agent에 부여할 배치 선택지가 늘어나며, 기존 Agent의 작업이 여러 공유 컴퓨터 사이를 오가며 섞이지는 않습니다.

## 하나의 메시지가 재개 가능한 작업이 되는 방법

### 대화는 참여자의 발언을 저장합니다

대화(Conversation)는 사람과 Agent가 함께 참여하는 소통 공간이며 `Ankole.Conversations`가 참여자 목록과 발언 기록을 관리합니다. Pod 내부에서 작성한 네이티브 메시지는 Ankole이 직접 정본으로 기록하고, 외부 메신저 대화는 어댑터가 관찰해 동기화하되 원본 메시지의 최종 기준은 해당 외부 플랫폼에 둡니다.

대화 발언 기록과 Agent의 내부 추론 기록은 철저히 분리됩니다. 대화에는 참여자 간에 오간 발언만 남고, 모델 호출 이력·도구 실행 결과·컨텍스트 압축 데이터는 해당 실행 세션에 연결된 AIGateway 모델 상태에 저장됩니다. 실행 세션은 단일 대화에 고정되므로 한 대화방의 내부 작업 문맥이 다른 대화방으로 섞여 들어가지 않습니다.

### Signals는 모든 자극을 접수합니다

대화에서 Agent를 호출한 발언뿐 아니라 예약된 시각 도래, 외부 웹훅 이벤트, 대기 후 재확인(check-back), 백그라운드 작업 완료 알림까지 모두 Signal로 접수됩니다. `Ankole.Signals`는 실행 세션을 깨우기 전에 발신 출처, 원본 이벤트 ID, 수신 대상, 귀속 주체, 권한 정보를 먼저 영구 저장합니다.

Pod 네이티브 발언과 그로부터 파생된 Signal은 단일 트랜잭션에서 원자적으로 커밋되며, 유입 단계에서 `(Agent, source, id)` 키로 중복 접수를 걸러냅니다. 다만 이 중복 제거는 접수 단계의 보장이며 이후 이어지는 모든 외부 부수 효과가 정확히 한 번만 실행된다는 뜻은 아닙니다.

Signal에 대상 실행 세션이 직접 명시되어 있으면 그 세션으로 바로 전달되고, 그렇지 않으면 대화 참여 관계나 Signal Routing Rule에 따라 대상이 결정됩니다. 이때 대화 호스트형 어댑터는 메시지 수신과 응답 전달을 모두 수행하는 반면, 이벤트 소스형 어댑터는 단방향으로 Signal만 생성합니다. 또한 Automation Job은 정해진 스크립트로 기계적인 점검을 수행하다가 모델의 판단이 필요한 변화가 감지될 때만 상위 실행 세션에 Signal을 보냅니다. 자세한 동작은 [Automation Jobs](../automation-jobs/)를 참조하세요.

### Sessions는 작업을 실행하고 복구합니다

실행 대기열, Admission 검증, Driver 프로세스, Run 상태, 제어 도구, 장애 복구는 모두 `Ankole.Sessions`가 담당합니다. 단일 실행 세션에서는 한 번에 하나의 Run만 실행되며, 매 실행이 시작될 때마다 Admission 단계에서 테넌트 일치 여부, Agent 활성 상태, 접근 권한, 토큰 할당량을 검증합니다.

각 Agent는 대화마다 독립된 Session을 가지며 출력은 대화 참여자에게 공유됩니다. 대화형 턴, 사람의 메시지로 시작하는 `may_intervene`, 예약 작업과 서비스 트리거 모두 실행 Agent의 권한으로 리소스에 접근합니다. Agent 메시지는 다른 Agent를 깨우지 않습니다. 사람의 재직 상태와 지시 버전은 위임의 유효성을 계속 검증하지만, 사람과 Agent의 리소스 권한을 교차 적용하지 않습니다.

정기 cron 작업이나 백그라운드 작업은 별도의 독립된 실행 세션에서 돌아간 뒤 결과만 대상 대화방에 발언으로 남깁니다. 이후 해당 대화방의 다음 턴이 실행될 때는 새로 게시된 발언 텍스트만 읽을 뿐 다른 실행 세션의 내부 추론 과정은 가져오지 않습니다.

모델 대화 상태의 저장과 연속 실행은 AIGateway가 맡고, 매 라운드의 입력 조립·지시문 구성·도구 분기·연속 진행·압축 시점 판단은 세션 런타임이 맡습니다. Driver는 PostgreSQL의 epoch 번호로 교체된 이전 프로세스의 지연 쓰기를 차단하며, 장애 복구 시에는 마지막으로 커밋된 지점부터 실행을 재개합니다. 복구 과정에서 모델 호출은 다시 실행될 수 있으나 이미 체인에 기록된 도구 결과는 그대로 재사용하고, 실행 여부를 확정할 수 없는 외부 호출은 중단(`interrupted`)으로 보고합니다.

### Presentation과 Delivery는 보이는 결과를 커밋합니다

Presentation 계층은 사용자에게 보여 줄 최종 응답을 한 번만 확정합니다. Pod 네이티브 대화에서는 세션 완료 트랜잭션 안에서 응답이 곧바로 발언 행으로 커밋되며, 침묵 턴(silent turn)은 발언을 남기지 않습니다. 외부 메신저로 나가야 하는 응답은 먼저 영구 Delivery 의도 레코드를 커밋한 뒤 채널 어댑터가 실제 전송을 수행합니다.

외부 플랫폼이 수신 성공을 확인해 주면 Ankole은 전달 완료 상태와 대화 발언 행을 단일 트랜잭션으로 함께 저장합니다. 이후 외부 플랫폼 웹훅으로 동일한 메시지 ID의 에코 이벤트가 뒤늦게 도착하더라도 기존 발언 행에 병합됩니다. 반대로 전송이 실패하거나 만료되었거나 성공 여부를 알 수 없는 상태라면 발언 행을 생성하지 않으며, 중복 발송을 막기 위해 결과 불명확 상태의 전송을 무조건 자동 재전송하지도 않습니다.

실시간 스트리밍 텍스트는 진행 상황을 보여 주는 미리 보기일 뿐이며, 발언이 정식 커밋된 뒤에야 대화 기록이 됩니다. 따라서 네트워크가 끊겼다가 다시 연결된 클라이언트는 커밋된 발언 기록과 현재 실행 상태만 다시 읽어 오며 중간 스트림 조각을 재전송받지는 않습니다.

각 계층의 설계 배경과 트레이드오프 비교는 [대화, 신호, 실행 세션](../conversations-signals-sessions/)을 참조하세요.

## Brain: 현재 상태를 유지하는 세계 모델

Brain은 단순히 채팅 조각을 쌓아 두는 벡터 데이터베이스가 아니라, 끊임없이 변하는 조직과 업무 환경의 최신 상태를 유지하는 세계 모델입니다. 새로운 근거가 들어오면 기존 Claim을 보강하거나 수정·대체하며, 서로 충돌하는 근거가 발견되면 오프라인 Dreaming 작업이 임의로 내용을 덮어쓰는 대신 사람이 검토할 수 있도록 모순 관계를 명시적으로 기록합니다.

지식은 Agent와 나눈 대화, 관찰 대상 그룹방에서 Agent 호출 없이 오간 일반 대화, 그리고 직접 등록한 파일이나 URL Source에서 수집됩니다.

같은 테넌트에 속한 Agent들은 하나의 지식 공간을 공유하며, 서로 다른 테넌트 간에는 지식 공간이 완전히 격리됩니다. 보호 대상 본문과 Claim 및 Timeline 이벤트에는 `world`, 특정 권한 그룹, 또는 단일 Principal 단위의 공개 범위(audience scope)가 부여됩니다. 원본 Source 문서나 외부 대화 기록은 지식의 출처(provenance)를 추적하는 용도로만 연결될 뿐, 원본을 볼 수 있다고 해서 파생된 지식에 대한 열람 권한까지 자동 부여되지는 않습니다.

실행 턴 도중에는 통합 회상(unified recall) 파이프라인이 현재 업무에 필요한 장기 맥락을 찾아 주입하고, 백그라운드 Dreaming 작업은 새로 쌓인 근거를 정돈해 패턴을 추출하고 이전 예측을 평가하며 검토가 필요한 상충 지점을 표시합니다.

이처럼 [Brain](../brain/)이 “지금 세계가 어떤 상태인가”라는 사실 지식을 다룬다면, [Skill Lessons](../skill-lessons/)는 반복된 실무 경험에서 도출한 절차적 가드레일을 보관합니다. 교훈은 관련 Skill을 읽을 때 함께 덧붙여 제공되지만 원본 `SKILL.md`를 직접 고쳐 쓰지는 않으며, 환경이 바뀌어 유효하지 않게 되면 폐기됩니다.

“시간이 지날수록 Agent가 우리 팀의 업무 방식과 규칙을 배운다”는 Ankole의 핵심 가치는 바로 이 구조에서 나옵니다. 지식이 복리로 쌓인다는 것은 단순히 로그가 길어진다는 뜻이 아니라, 다음 업무를 시작할 때 이전보다 더 정확한 배경지식과 검증된 절차 위에서 출발한다는 뜻입니다.

사용자 눈에는 하나의 자연스러운 장기 기억으로 보이지만, 내부적으로는 저장소와 Dreaming 및 쓰기 권한 검증을 Brain이 체계적으로 관리합니다.

## Background Agent Jobs: 메인 세션을 막지 않는 긴 작업

메인 Agent는 심층 조사, 대용량 데이터 분석, 복잡한 파일 작업, 코드 수정, Deep Research처럼 시간이 오래 걸리는 과제를 Background Agent Job에 위임할 수 있습니다. 위임한 뒤에도 메인 세션은 블로킹되지 않으므로 사용자와 자연스럽게 대화를 이어 갈 수 있습니다.

컨트롤 플레인은 Job의 전체 수명 주기를 영구 관리합니다. 실행 도중 Worker 인스턴스가 교체되더라도 영구 Home에 보존된 작업 공간과 Codex 스레드를 바탕으로 작업을 이어 가며, 수락된 작업 목록과 복구 기준 상태는 모두 PostgreSQL이 보장합니다.

실행 중에도 메인 Agent와 백그라운드 Job은 양방향으로 소통할 수 있습니다. Job은 추가 정보나 의사결정을 요청할 수도 있고, 실패 원인이나 최종 산출물을 보고할 수도 있으며, 지시에 따라 조용히 종료할 수도 있습니다. 사람의 응답을 기다려야 할 때는 점유하던 실행 슬롯을 반납하고 대기하다가 답변이 도착하면 즉시 실행을 재개합니다.

Deep Research는 이 백그라운드 구조를 활용한 대표적인 심화 워크플로입니다. Agent Plugin이 초기 workspace 템플릿을 준비하고, Skill이 조사 방법론을 안내하며, Background Agent Job이 중단 없는 장기 실행을 뒷받침합니다.

작업 중 생성되는 임시 파일과 Job workspace는 영구 Home에 남고, Worker 외부의 사용자나 다른 도구에 전달할 최종 보고서와 산출물은 Agent가 컨트롤 플레인 드라이브에 게시합니다.

자세한 운영 방식은 [Background Agent Jobs](../background-jobs/)와 [Deep Research](../deep-research-job/)를 참조하세요.

## AIGateway: AI capability를 위한 하나의 경계

AIGateway는 모델 기능 제공 계층과 Agent 실행 로직을 깔끔하게 분리합니다. 메인 Agent, 백그라운드 Job, Brain, 외부 API 클라이언트가 모두 동일한 AIGateway 경계를 통해 LLM, 임베딩, 리랭크, 이미지 생성, Web Search, Web Fetch 제공자를 호출합니다.

일반 실행 모델은 각 Agent의 model profile에서 선택하고, Brain 유지 관리 작업은 테넌트별로 지정된 Brain maintainer Agent의 `light`, `heavy`, `web_fetch` 프로필을 사용합니다. 또한 임베딩 모델은 사이트 범위 AppConfigure에서, 리랭크 모델은 테넌트 범위 AppConfigure에서 지정합니다. 모든 업스트림 Provider 자격 증명은 컨트롤 플레인이 암호화해 보관하며 AIGateway가 외부 요청을 보낼 때만 내부적으로 복호화해 사용합니다.

따라서 Agent와 Worker에는 허용된 모델 셀렉터 목록과 호출 결과만 전달될 뿐 원본 키는 노출되지 않습니다.

AIGateway는 단발성(stateless) 호출과 여러 턴에 걸쳐 이어지는 상태 보존형(stateful) 모델 세션을 모두 지원하며, 요청 포맷 변환, 스트림 이벤트 정규화, 도구 실행 결과 기록, 컨텍스트 압축(compaction), 토큰 사용량 집계, 최종 응답 커밋을 일괄 관리합니다.

덕분에 Worker 측에서는 개별 모델 제공자마다 제각각인 세션 수명 주기를 별도로 구현할 필요가 없습니다.

사용 가능한 도구 카탈로그가 방대할 때 모델은 Tool Search로 필요한 도구만 그때그때 검색하거나, Programmatic Tool Calling을 통해 여러 도구를 연속 호출하고 요약 결과만 돌려주는 TypeScript 프로그램 하나를 제출할 수 있습니다. 이때 AIGateway와 Workflow는 무상태 `ankole-function-runtime` isolate(`POST /v1/program/run`)에서 결정론적 TypeScript 프로그램을 안전하게 실행합니다. 업스트림 제공자가 해당 기능을 네이티브로 지원하면 네이티브 호출을 그대로 활용하고, 지원하지 않는 제공자에 대해서는 게이트웨이 계층에서 동일한 기능을 에뮬레이션해 제공합니다. 또한 단일 Provider 아래에 ChatGPT 구독 계정을 포함한 여러 자격 증명을 풀(pool)로 묶어 둘 수 있으며, 오류 시 쿨다운 귀속과 재시도 및 사용량 집계는 모두 개별 자격 증명 단위로 정확히 기록됩니다.

자세한 구조는 [AIGateway](../ai-gateway/)와 [LLM Provider 추가](../adding-a-provider/)를 참조하세요.

## 엔터프라이즈 identity, 접근, 확장

Ankole에서는 사람, Agent, 내부 시스템 서비스를 모두 일관된 Principal 모델로 표현합니다. Pod와 Console 전반에는 통합 패스워드리스 인증이 적용되어, 개인별 `SiteCredential` Email OTP와 테넌트 엔터프라이즈 Identity Provider(OIDC/OAuth SSO 및 조직 디렉터리 동기화)를 통해 비밀번호를 직접 저장하지 않고도 구성원과 관리자를 안전하게 인증합니다.

메시지 수발신은 채팅 채널 어댑터가 담당하며, 인증용 IdP와 채팅용 채널은 서로 다른 플랫폼을 조합해 구성할 수도 있습니다.

모든 접근 제어는 AuthZ 계층이 Principal, 권한 그룹, 대상 리소스, 요청 작업, 조건을 바탕으로 런타임에 직접 판정합니다. 권한은 프롬프트 문구로 부탁하는 규칙이 아니므로 모델이 스스로 권한이 있다고 선언해 우회할 수 없습니다.

시스템 확장은 두 층위로 나뉩니다. 컴파일 시점에 결합되는 사이트 범위 Control Plane Plugins를 통해 서브시스템 어댑터(Signals, Identity Provider, AI Gateway provider, Worker provider), 감독 대상 OTP 프로세스, 외부 HTTP plug, 확장 JSON:API 라우트, 도메인 트랜잭션 훅, `AppConfigure` 설정 키, 타입 안전 UI 슬롯을 추가할 수 있습니다. 반면 Agent Plugins는 모델이 활용할 도구와 작업 공간 템플릿을 제공합니다.

Skill은 특정 유형의 업무를 수행하는 절차를 정의하며, 필요에 따라 메인 Agent 전용이나 Background Agent Jobs 전용으로 노출 범위를 제한할 수 있습니다.

외부 MCP 서버 역시 Skill을 통해 연동합니다. 필요한 MCP 연결 사양을 Skill에 선언해 두면 Worker가 해당 작업 실행 시점에만 구성을 생성했다가 실행이 끝나면 즉시 정리하므로, 모델 프롬프트에 수백 개의 MCP 도구 목록이 상시 적재되는 부담을 피할 수 있습니다.

관련 세부 내용은 [Principal과 권한 그룹](../principal-and-groups/), [신호 라우팅 규칙](../signal-bindings/), [Agent Library](../skills/), [MCP server 참조](../mcp/)를 참조하세요.

## 내구성 경계

컨트롤 플레인의 PostgreSQL 18+ 데이터베이스는 identity, 접근 권한, 설정, Pod 메타데이터와 문서, 대화 메시지, 세션, Job, 기억, 메시지 전달 상태, 감사 이력 등 핵심 도메인 사실을 영구 저장하며, 물리 **Base 샤드 데이터베이스(`BASE_DB_URLS`)**는 테넌트별 Base 테이블 행을 저장합니다. 시점 복구(PITR)를 수행할 때는 모든 Base 샤드의 복구 목표 시점이 컨트롤 플레인 데이터베이스의 복구 목표 시점과 같거나 그 이후(`>=`)여야 참조 일관성이 유지됩니다. 시스템이 특정 작업을 최종 커밋했는지 판단할 때는 언제나 이 PostgreSQL 기록을 기준으로 삼으세요.

오브젝트 스토리지(컨트롤 플레인 파일 저장소)에는 Pod 파일, Pod 및 대화 첨부 파일, 컴파일된 Applet 번들, 게시된 산출물, 설치형 Skill, Automation 스크립트가 보관됩니다. 이와 별도로 각 Agent의 영구 Home은 작업 공간, 설치한 패키지, Codex 스레드 파일을 보존합니다. 따라서 백업을 구성할 때는 컨트롤 플레인 PostgreSQL 데이터베이스, 모든 물리 Base 샤드 데이터베이스, 오브젝트 스토리지, 전체 Agent Home 볼륨, 그리고 배포 시 생성된 원본 암호화 키를 반드시 함께 백업해야 합니다.

반면 RuntimeFabric 연결, `ankole-function-runtime` isolate, 실행 중인 Worker 프로세스, 스트리밍 미리 보기 조각, `/var/cache/ankole` 캐시는 무상태이거나 언제든 재구축할 수 있습니다. 단, 영구 Home은 컨테이너 삭제 후에도 유지되어야 하므로 반드시 스토리지 백업 대상에 포함하세요. 자세한 절차는 [백업 및 복원](../backup-and-restore/)을 참조하세요.

## 세 가지 deployment 형태

| 형태 | 컨트롤 플레인, Function Runtime 및 Worker | 영속화 |
| --- | --- | --- |
| **Docker Compose · 단일 호스트 권장** | 단일 Linux, macOS, Windows 호스트에서 컨트롤 플레인과 `ankole-function-runtime`을 실행하고, 컨트롤 플레인이 Docker 소켓을 통해 Agent마다 전용 Worker 컨테이너를 생성 | PostgreSQL 18+(구성된 `BASE_DB_URLS` 샤드 포함), 오브젝트 스토리지, Agent별 전용 영구 Home 볼륨 |
| **Kubernetes · 엔터프라이즈 deployment 권장** | Helm 차트로 컨트롤 플레인과 `ankole-function-runtime` Deployment를 배포하고, 컨트롤 플레인이 Kubernetes API를 호출해 Agent마다 전용 Worker Pod를 생성 | PostgreSQL 18+ 및 물리 Base 샤드 데이터베이스, 오브젝트 스토리지, Home용 PVC 또는 공유 스토리지(캐시 볼륨은 별도 분리) |
| **소스 설치** | `bun run services:start`로 PostgreSQL 18과 `ankole-function-runtime`을 기동하고, `bun dev`로 컨트롤 플레인을 실행해 Agent마다 watch 모드의 Docker Worker 컨테이너를 생성 | PostgreSQL 18, `var/ankole-dev/files`, 전용 Docker 영구 Home 볼륨 |

어느 배포 형태를 선택하든 논리적 아키텍처 경계는 동일합니다. 배포 인스턴스마다 하나의 컨트롤 플레인이 중심을 잡고 각 Agent에게 독립된 전용 Worker를 할당합니다. 설치 절차는 [빠른 시작](../quickstart/#deployment)을 참조하세요.

## 다섯 가지 기술적 결정

| 결정 | 해결하는 문제 |
| --- | --- |
| **Virtual Actor가 AI 작업을 담당** | 각 실행 세션에 고유 주소, 메일박스, 수명 주기, 명확한 복구 지점을 부여 |
| **OTP 감독 트리가 장애 도메인을 정의** | 전체 서비스를 중단시키지 않고 문제가 생긴 개별 Agent나 연결 브랜치만 격리 복구 |
| **Phoenix Channel이 실시간 제어를 전달** | 실행 중인 Agent에게 웨이크업, 스티어링, 진행 상황 보고, 백프레셔를 저지연으로 전달 |
| **Agent Computer Worker가 실행을 제공** | 각 Agent에게 도구, 파일, 터미널, 브라우저, Codex를 자유롭게 다룰 전용 컴퓨터를 할당 |
| **PostgreSQL 원장이 사실을 저장** | 메시지, Job, 기억, 의사결정, 커밋된 결과물을 언제든 재개하고 감사할 수 있도록 보장 |

이 다섯 가지 설계 결정은 모두 한 가지 목표를 향합니다. Agent가 수 시간 동안 자율적으로 업무를 수행하고, 실행 도중 새로운 정보를 받아들이며, 장애가 나더라도 개별적으로 복구하고, 커밋된 모든 판단과 행동에 투명한 추적 기록을 남기도록 만드는 것입니다.
