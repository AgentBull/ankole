Ankole은 Meta Ankole의 Company Brain을 중심으로 구축된 오픈 소스 디지털 본사 및 엔터프라이즈 Agent Harness입니다. 조직이 직접 운영하는 인프라 위에서 협업용 Pod 워크스페이스와 개인 비서·전문 AI 동료를 하나로 결합해, 지속적인 기업 실무에 필요한 조직 맥락, 범위가 제한된 권한, 영속적 실행, 피드백 루프를 제공합니다.

Harness 안에서 구성원과 Agent는 수 시간에 걸친 업무를 함께 처리하고, 공유 Company Brain을 참조하며, 브라우저·터미널·통합 Drive 파일·Applet·연결된 사내 시스템을 통해 작업한 뒤 사람이 근거를 검토하고 실제 결과로 검증할 수 있는 산출물을 전달합니다. 모든 단계에서 Ankole은 실행 주체(Principal)를 식별하고, 런타임 접근 규칙을 강제하며, 중단된 작업을 PostgreSQL에서 복구하고, 교정 사항을 다음 의사결정으로 이어 갑니다.

## 시스템 지도

단일 프라이빗 배포 인스턴스는 하나의 논리적 컨트롤 플레인, 무상태 `Function Runtime`(`ankole-function-runtime`) 서비스, 그리고 Agent마다 할당되는 전용 Agent Computer Worker로 구성됩니다. 컨트롤 플레인은 ID·영구 상태·통합 Connectors·스케줄링을 총괄하며 Pod 워크스페이스를 호스팅하고, Pod Applet 백엔드·게시된 Applet Action·호스트 MCP 호출·결정론적 TypeScript 프로그램을 위해 `Function Runtime` isolate를 호출하며, `WorkerProviders`를 통해 각 Agent에게 전용 컴퓨팅 환경을 프로비저닝합니다.

워크스페이스 전반에서 Pod(계층형 Docs, 물리 샤드 기반 2계층 Base 테이블, React + TypeScript Applet, 통합 Drive, 멀티플레이어 Pod Chat)와 외부 채널 어댑터가 대화 메시지를 기록합니다. `Ankole.Signals`는 수신 메시지, Connector 트리거, Webhook, 예약 이벤트를 접수해 Agent 실행용 `Ankole.Sessions` 또는 결정론적 Applet Action 실행용 `Ankole.AutomationJobs`로 전달합니다. 통합 인증과 Identity Provider가 패스워드리스 Email OTP(`SiteCredential`), 엔터프라이즈 SSO, 디렉터리 동기화를 제공하고, AIGateway가 모델·임베딩·리랭크·이미지·웹 기능을 위한 단일 경계를 형성합니다.

## 컨트롤 플레인, Function Runtime 및 Agent Computer Worker

### 컨트롤 플레인은 상태를 저장하고 결정을 확정합니다

Elixir/OTP 컨트롤 플레인은 Pod(Docs, Base 테이블 및 물리 샤드, Applet, 통합 Drive, Pod Chat), Meta Ankole(`Brain`, `Skills`, `AGENTS.md` / `DESIGN.md` 계약), 통합 Connectors(`Ankole.Connectors`), Console, Principal과 AuthZ, 시스템 설정, 신호 라우팅, Sessions, Workflow, Automation Jobs, Background Agent Jobs, AIGateway, Control Plane Plugins를 소유합니다. 모든 모듈은 사용자에게 보이는 결과를 바꾸는 상태 변경을 실행이나 외부 전송 전에 반드시 PostgreSQL에 먼저 커밋하므로, 프로세스가 재시작되어도 수락된 메시지, Job 상태, 지식, 감사 기록이 온전히 보존됩니다.

런타임에는 OTP 감독 트리가 Agent, 외부 연결, Job을 독립된 장애 도메인으로 분리해 특정 실행 분기가 멈추거나 종료되더라도 전체 인스턴스 중단 없이 해당 분기만 복구합니다. 핵심 컨트롤 플레인 코드와 주요 상태 머신에는 정형 검증을 적용해 재시도·재시작·동시 입력 상황에서도 상태 전이와 경계 불변식을 보장합니다.

### Worker는 Agent 전용 작업 컴퓨터입니다

주 Agent 루프는 컨트롤 플레인에서 실행되며, 환경 도구나 Codex 실행이 필요할 때 Agent Computer Worker를 온디맨드로 기동합니다. Worker 안에서 Agent는 셸 도구, Skills, 헤드리스 브라우저, 파일 작업, MCPorter 도구 호출, Git 자격 증명 도우미, Codex Job을 실행하며, 결정론적 자동화는 게시된 Applet Action으로서 `Function Runtime`에서 별도로 실행됩니다.

각 Agent는 고유한 Worker ID와 최대 한 대의 활성 Worker 인스턴스를 가지며, Agent 간에 Worker·캐시 디스크·자격 증명을 공유하지 않습니다. Worker 컨테이너(또는 Pod) 내부에서는 신뢰된 supervisor가 FUSE로 `/drive`를 마운트하고 모델이 구동하는 하위 명령을 Linux capability와 `sudo`가 제거된 `uid 1000`으로 실행합니다(Kubernetes에서는 Pod 템플릿의 RuntimeClass로 gVisor를 추가할 수도 있습니다). 선택된 `WorkerProvider`(Docker, Kubernetes, Cloudflare, Vercel, AWS Lambda MicroVMs, Alibaba Function Compute)에 따라 컨트롤 플레인은 영속 Agent Home을 `/workspace`에, 재구축 가능한 캐시를 `/var/cache/ankole`에 마운트하고, `/drive` 아래에 `Public`, `MyDrive`, `AgentDrive`, `ChatDrive`와 읽기 전용 `Brain`, `Skills`, `AGENTS.md`, `DESIGN.md`를 FUSE로 투영합니다.

RuntimeFabric은 Worker당 하나의 Phoenix Channel로 컨트롤 플레인과 Worker를 연결해 웨이크업, 스티어링, 취소, `/drive` 캐시 표적 무효화 알림, 진행 상황, 실행 결과를 저지연으로 전달합니다. RuntimeFabric은 데이터베이스가 아닌 실시간 전송 계층이므로 연결 해제 후 복구는 항상 PostgreSQL의 커밋된 상태를 기준으로 재개합니다.

### WorkerProviders가 플랫폼과 구성을 정의합니다

운영자는 **Console → Worker Providers**에서 사이트 단위의 `WorkerProviders`를 구성하며, 각 프로바이더는 플랫폼 종류, YAML 설정, 암호화된 플랫폼 자격 증명을 정의합니다. 여러 Agent가 같은 `WorkerProvider`를 사용하더라도 컴퓨터와 영속 `/workspace` Home은 Agent마다 분리되며, 다른 플랫폼이나 인스턴스 사양이 필요할 때 별도 프로바이더를 추가합니다.

Agent 생성 시 `WorkerProvider`를 직접 선택하거나 사이트 기본값을 사용하면 해당 바인딩이 영구 고정됩니다. 이후 컨트롤 플레인이 필요 시 Worker를 시작하고 유휴 시 일시 중지·회수하며, 구성이 갱신되면 `/workspace`를 보존한 채 인스턴스를 교체하고 `/var/cache/ankole`은 별도로 재구축합니다. 자세한 내용은 [WorkerProviders](../worker-providers/)와 [Workers](../worker-management/)를 참조하세요.

각 Worker는 환경 작업 공간과 Codex 턴 슬롯만 계산하며, 주 대화 턴·Workflow·게시된 Applet Action은 Worker 외부에서 실행되어 Worker 슬롯을 소모하지 않습니다.

## 하나의 메시지가 재개 가능한 작업이 되는 과정

### 대화는 참여자의 발언을 보존합니다

대화(Conversation)는 사람과 Agent가 소통하는 공유 공간으로, `Ankole.Conversations`가 1:1 DM, 멀티플레이어 그룹방, 그리고 Agent 간 위임을 위한 격리된 `agent_peer` 스레드의 참여자와 메시지를 관리합니다. Pod 네이티브 메시지는 PostgreSQL에 직접 기록되고, 외부 메신저 대화는 채널 어댑터가 관찰해 기록하되 원본 기준은 외부 플랫폼에 남습니다.

대화 메시지와 Agent 내부 실행 상태는 분리되어 저장됩니다. 메시지는 참여자에게 속하고, 모델 호출·도구 결과·컨텍스트 압축은 AIGateway의 Session 모델 체인에 속합니다. Session은 대화 경계를 넘지 않으므로 한 대화의 내부 작업이 다른 대화로 유출되지 않습니다.

### Signals가 모든 자극을 접수합니다

Agent를 호출한 메시지, 예약 일정 도래, Connector 트리거 및 Webhook 수신, check-back 타이머, 백그라운드 작업 완료가 발생하면 `Ankole.Signals`가 출처·원본 이벤트 ID·대상·귀속·권한 정보를 먼저 기록한 뒤 Session을 깨우거나 Automation Job Run을 대기열에 넣습니다.

Pod 네이티브 메시지와 파생 Signal은 단일 트랜잭션으로 커밋되며, 유입 단계에서 `(target, source, id)` 기준으로 중복 접수를 제거합니다. 하위 작업은 자체 멱등성 키와 attempt fence로 안전성을 보장합니다.

Signal은 대상 Session을 직접 지정하거나 대화 참여 관계 및 Signal Routing Rule을 통해 대상을 결정합니다. 대화 호스트형 어댑터는 메시지 관찰과 응답 전달을 함께 수행하고, 이벤트 소스형 어댑터는 Signal만 발행합니다. 결정론적 일정·Webhook·Connector 이벤트의 경우 `Ankole.AutomationJobs`가 무모델(zero-LLM) 게시형 **Applet Action**을 `Function Runtime`에서 실행하고 모델 판단이 필요할 때만 Agent Session으로 후속 Signal을 보냅니다([Automation Jobs](../automation-jobs/) 참조).

### Sessions가 작업을 실행하고 복구합니다

`Ankole.Sessions`는 대기열, Admission, Driver, Run, 도구, 콜드 웨이크 회전, 복구를 담당합니다. 각 Session은 한 번에 하나의 Run만 실행하며, 실행 시작마다 Admission이 테넌트·Agent 상태·사람의 작업 권한·인가·토큰 쿼터를 검증합니다.

각 Agent는 대화마다 고유한 Session에서 실행되며, Agent 하위 유형에 따라 권한 모델이 구분됩니다.

- **개인 비서(`personal_assistant`):** 내부 Human 멤버와 1:1로 짝지어지며, Drive·Pod·권한 그룹 등 협업 리소스에서는 `Principals.authority_uid/1`을 통해 소유자 본인의 권한을 투영합니다(`site_console:**` 및 `tenant_console:**` 관리 권한은 제외). 감사 기록과 Worker 스토리지에는 비서 고유의 Principal ID를 유지합니다.
- **AI 동료(`ai_colleague`):** Drive, Pod, Workflow, 일정, Background Agent Jobs 전반에서 Agent 자신의 Principal 권한으로 실행됩니다. 보호된 지식 객체 생성·수정처럼 동료 자신의 쓰기 권한을 넘어서는 작업이 필요하면 Pod 대화에서 `propose_action_card`를 호출해 권한 있는 사람의 승인을 요청합니다. 지식 조회 시 Brain은 요청자와 Agent의 열람 권한 교집합(`strict` 그룹방에서는 모든 참여자의 교집합)을 적용합니다.

공유 대화방에서 Agent의 일반 응답은 다른 Agent를 자동으로 깨우지 않아 무한 루프를 방지합니다. 전문 AI 동료의 도움이 필요할 때는 `send_to_agent`로 명시적 위임을 수행해 격리된 `agent_peer` 대화를 열고 내부 도구 이력을 섞지 않은 채 비동기로 답변을 받아 옵니다. 정기 cron 일정과 백그라운드 작업 역시 별도 Session에서 실행된 뒤 완료된 메시지만 대상 대화방에 게시합니다.

AIGateway가 모델 세션 상태를 영속화·연결하는 동안 런타임은 입력, 지시문, 도구, 연속 실행 체크포인트, 콜드 웨이크 회전(`sessions.wake_recycle`), 컨텍스트 압축을 조율합니다. Driver의 단조 증가 PostgreSQL epoch가 지연 쓰기를 차단하며, 복구 시에는 커밋된 진행 지점부터 재개합니다(중단된 모델 호출은 재시도 가능, 커밋된 도구 결과는 재사용, 결과 미확정 Worker 도구 호출은 `interrupted`로 표시).

### Presentation과 Delivery가 가시적 결과를 커밋합니다

턴 종료 시 Presentation이 가시적 응답을 한 번만 확정합니다. 침묵 턴은 메시지를 남기지 않고, Pod 네이티브 응답이나 대화형 Action Card는 완료 트랜잭션에서 즉시 커밋되며, 외부 메신저 응답은 영구 Delivery 의도를 기록해 어댑터가 전송하게 합니다.

외부 플랫폼이 수신 성공을 확인하면 전달 완료 표시와 대화 메시지 저장을 같은 트랜잭션에서 커밋하며, 동일한 외부 메시지 ID의 플랫폼 에코는 해당 행으로 병합됩니다. 실패·만료·결과 불명확 Delivery는 메시지를 생성하지 않고 결과 불명확 전송을 임의로 재전송하지도 않습니다.

실시간 토큰 스트리밍은 진행 미리 보기일 뿐 최종 메시지가 커밋된 뒤에야 대화 이력이 됩니다. 자세한 설계 비교는 [대화, 신호, 실행 세션](../conversations-signals-sessions/)을 참조하세요.

## Meta Ankole과 Brain: 진화하는 세계 모델

Meta Ankole의 **Brain**은 단순한 채팅 조각 벡터 DB가 아니라, 독립된 `Brain` 루트 아래 설치된 온톨로지 카테고리별로 구성되는 `:knowledge` 페이지와 원자적 Facts, Takes, 타임라인, 타입화된 `brain_links` 관계 엣지로 이루어진 세계 모델을 유지합니다. 지식은 Agent 대화, 조건을 충족한 그룹 메시지, 등록된 URL Source, 그리고 사실 추출을 활성화한 Space 페이지(`metadata.extract_facts: true`)에서 유입됩니다. 새 근거가 도착하면 기존 Claim을 확장·개정·대체하고, 상충하는 근거가 발견되면 오프라인 Dreaming이 임의로 덮어쓰지 않고 사람이 검토할 수 있도록 모순을 기록합니다.

한 테넌트의 모든 Agent는 테넌트별로 격리된 단일 지식 그래프를 공유하며, 실시간 Pod 페이지 ACL 앵커 그래프로 접근 권한이 제어됩니다. 공용 엔티티에 연결된 비공개 Claim도 원본 출처의 가시성을 그대로 유지하며, 원본 페이지 권한을 회수하면 파생 Claim과 청크도 다음 조회부터 즉시 제외됩니다.

실행 턴 중에는 BM25 + 벡터 하이브리드 회상이 장기 맥락을 공급하고, 오프라인에서는 Dreaming이 근거 통합, 출처 범위 분석 페이지 작성, 만기 도래한 Take 채점, 모순 탐지를 수행합니다. [Brain](../brain/)이 조직 지식을 담당하는 동안 Meta Ankole은 공유 **Skills**와 조합형 `AGENTS.md` / `DESIGN.md` 계약을 함께 관리하며, [Skill Lessons](../skill-lessons/)는 Background Agent Job 실행 궤적에서 7일 임대 방식의 Agent별 절차 주의사항을 자동 추출해 공유 `SKILL.md` 원본을 수정하지 않고 덧붙입니다.

## Background Agent Jobs: 메인 세션을 막지 않는 장기 실행

포그라운드 Agent는 장시간 리서치, 데이터 분석, 파일 생성, 코드 수정, Deep Research를 Background Agent Job에 위임하고 메인 Session에서는 사용자와의 대화를 끊김 없이 이어 갑니다.

컨트롤 플레인이 PostgreSQL에 Job 수명 주기를 영속화하므로 Worker 인스턴스가 교체되어도 `/workspace`에 보존된 Job 작업 공간과 Codex 스레드 파일에서 그대로 재개됩니다. 실행 중 메인 Agent와 Job은 양방향으로 소통할 수 있으며, 사람의 입력을 기다리는 동안에는 Worker 실행 슬롯을 반납했다가 답변이 오면 즉시 재개합니다.

Deep Research는 이 기본 요소들을 결합해 Agent Plugin이 `workspace-template`을, Skills가 조사 방법론을, Background Agent Job이 영속 실행을 제공합니다. 임시 작업 공간은 `/workspace`에 머물고 외부에서 열람할 결과물은 통합 Drive에 게시됩니다. 자세한 내용은 [Background Agent Jobs](../background-jobs/)와 [Deep Research](../deep-research-job/)를 참조하세요.

## AIGateway: AI 기능을 위한 단일 경계

AIGateway는 업스트림 AI 제공자와 호출 주체를 분리해 개인 비서, AI 동료, Background Agent Jobs, Brain, Pod Applet, 외부 OIDC 클라이언트가 LLM·임베딩·리랭크·이미지·Web Search·Web Fetch 제공자에 대해 단일 경계를 공유하게 합니다.

`Ankole.AIGateway.ModelProfiles`는 3계층 희소 상속(`Site -> Pod -> Agent/System`)과 슬롯 간 폴백(`coding -> heavy -> primary`, `light -> primary`)으로 모델을 결정합니다. 등록된 `system` Principal은 포그라운드 Agent의 토큰 쿼터를 전혀 소모하지 않고 내부 작업을 수행합니다. `ankole_brain`은 Brain 추출(`light`), Dreaming 및 교훈 검토(`heavy`, 미설정 시 `primary`), URL Source 수집(`web_fetch`), 회상 리랭킹(`rerank`)을 실행하고, `system`은 Pod/Site 기본 프로필로 무상태 Pod Applet `ctx.ai` 호출을 처리하며, 사이트 설정 `brain.embedding_model`이 공유 벡터 인덱스를 담당합니다. 운영자는 **Console → Model Profiles**에서 Site·Pod·`system` Principal 프로필을 관리하며 모든 업스트림 Provider 자격 증명은 컨트롤 플레인 내부에 암호화되어 보관됩니다.

단발성 호출과 상태 보존형 WebSocket 모델 세션을 모두 지원하는 AIGateway는 요청 변환, 스트림 정규화, 도구 결과, 컨텍스트 압축, 사용량 기록, 최종 커밋을 처리합니다. 도구가 많을 때는 Tool Search나 Programmatic Tool Calling(PTC)을 사용할 수 있으며, AIGateway와 Workflow는 무상태 `ankole-function-runtime` isolate(`POST /v1/program/run`)에서 결정론적 TypeScript 프로그램을 실행합니다. 또한 ChatGPT 구독 같은 OAuth 풀을 포함한 다중 자격 증명 풀을 지원해 쿨다운·재시도·사용량을 개별 자격 증명 단위로 추적합니다. 자세한 내용은 [AIGateway](../ai-gateway/)와 [LLM Provider 추가](../adding-a-provider/)를 참조하세요.

## 엔터프라이즈 ID, 통합 Connectors 및 확장

Ankole은 사람, Agent, 내부 서비스(`system`, `ankole_brain`)를 감사 기록이 남는 테넌트 내 이름 변경을 지원하는 `(tenant_id, uid)` Principal로 일관되게 표현합니다. 패스워드리스 인증은 Pod와 Console 전반에 적용되어 개인 `SiteCredential` Email OTP와 테넌트 엔터프라이즈 Identity Provider(OIDC/OAuth SSO 및 디렉터리 동기화)로 비밀번호 저장 없이 구성원과 관리자를 인증합니다.

`Ankole.AuthZ`는 Elixir 컨트롤 플레인과 Rust 커널에서 Principal(개인 비서의 협업 리소스 접근 시에는 Human 소유자), 권한 그룹, Drive 5비트 ACL 앵커, 요청 동작, CEL 조건을 런타임에 직접 검증합니다.

컴파일 시 결합되는 사이트 범위 Control Plane Plugins는 6가지 서브시스템 어댑터 계약(Signals 어댑터, Webhook 핸들러, Identity Provider, AIGateway 제공자, `WorkerProvider` 종류, `connectors.connector` 통합 Connectors), 감독 대상 OTP 프로세스, 외부 HTTP plug, 이중 범위 `/api/v2` JSON:API 라우트, 도메인 트랜잭션 훅, `AppConfigure` 필드, 타입 안전 UI 슬롯을 제공합니다. Agent Plugins는 멤버 Skills·Codex Hooks·`workspace-template` 디렉터리를 패키징하고, `Ankole.Connectors`는 컨트롤 플레인 MCP 게이트웨이(`/api/internal/mcp/toolkits/:toolkit` 및 `/api/internal/mcp/skills/:skill/:server`)를 구동해 테넌트 앱 시크릿(`authConfigId`)과 개인 OAuth 토큰을 PostgreSQL 안에 보관하면서 Worker(MCPorter 경유)와 `Function Runtime` Applet(호스트 브리지 경유)에 명시적 Toolkit 계약을 제공합니다. 자세한 내용은 [Principal과 권한 그룹](../principal-and-groups/), [Control Plane Plugins](../control-plane-plugins/), [Agent Library](../agent-library/), [MCP 사용하기](../using-mcp/)를 참조하세요.

## 내구성 경계

컨트롤 플레인의 PostgreSQL 18+ 데이터베이스는 ID, AuthZ 권한, 설정, Connector 자격 증명 및 트리거, Pod 페이지 트리와 XML 본문, Meta Ankole의 `Skills`(`skills`, `skill_files`)와 `AGENTS.md` / `DESIGN.md` 계약(`agent_contracts`), 메시지, Sessions, Automation Jobs, Background Agent Jobs, Brain Claim과 온톨로지 링크, 전달 상태, 감사 이력을 영구 저장하며, 물리 **Base 샤드 데이터베이스(`BASE_DB_URLS`)**가 테넌트 Base 테이블 행을 저장합니다. 시점 복구(PITR) 시 모든 Base 샤드의 복구 목표 시점은 컨트롤 플레인 데이터베이스 이상(`>=`)이어야 합니다.

오브젝트 스토리지(컨트롤 플레인 파일 저장소의 `file_objects`)는 통합 Drive 불변 파일 블롭, Pod 및 대화 첨부 파일, Skill 부속 파일, 컴파일된 Applet 번들을 보관하고, 영속 Agent Home(`/workspace`)은 Session·Job 작업 공간, 사용자 설치 패키지, Codex 스레드를 보관합니다. 백업 시에는 컨트롤 플레인 PostgreSQL 데이터베이스, 모든 물리 Base 샤드 데이터베이스, 오브젝트 스토리지, 모든 Agent Home, 배포 암호화 키를 반드시 함께 백업하세요.

RuntimeFabric 연결, `ankole-function-runtime` isolate, 실행 중인 Worker 프로세스, `/drive` FUSE 캐시, 스트림 미리 보기, `/var/cache/ankole`은 무상태이거나 재구축 가능하지만, `/workspace` Home은 인스턴스 교체 후에도 유지되어야 하는 영구 영역입니다([백업 및 복원](../backup-and-restore/) 참조).

## 세 가지 배포 형태

| 형태 | 컨트롤 플레인, Function Runtime 및 Worker | 영속화 |
| --- | --- | --- |
| **Docker Compose · 단일 호스트 권장** | 단일 Linux, macOS, Windows 호스트에서 컨트롤 플레인과 `ankole-function-runtime`을 실행하고 Docker 소켓으로 Agent마다 전용 Worker 컨테이너 생성 | PostgreSQL 18+(구성된 `BASE_DB_URLS` 샤드 포함), 오브젝트 스토리지, Agent별 전용 영구 `/workspace` Home 볼륨 |
| **Kubernetes · 엔터프라이즈 권장** | Helm 차트로 컨트롤 플레인과 `ankole-function-runtime`을 배포하고 Kubernetes API로 Agent마다 `/drive`용 `/dev/fuse`가 마운트된 Worker Pod 생성 | PostgreSQL 18+ 및 물리 Base 샤드 데이터베이스, 오브젝트 스토리지, 영속 Home PVC 또는 공유 스토리지(캐시 볼륨 분리) |
| **소스 설치** | `bun run services:start`로 PostgreSQL 18과 `ankole-function-runtime` 기동, `bun dev`로 컨트롤 플레인과 watch 모드 Docker Worker 생성 | PostgreSQL 18, `var/ankole-dev/files`, 전용 Docker 영구 Home 볼륨 |

세 가지 형태 모두 하나의 논리적 컨트롤 플레인이 `WorkerProviders`를 통해 Agent마다 격리된 전용 Worker를 할당합니다. 단계별 설치 절차는 [빠른 시작](../quickstart/#deployment)을 참조하세요.

## 다섯 가지 기술적 결정

| 결정 | 해결하는 문제 |
| --- | --- |
| **Virtual Actor가 AI 작업을 담당** | 각 Session에 고유 주소, 메일박스, 수명 주기, 정확한 복구 체크포인트를 부여 |
| **OTP 감독 트리가 장애 도메인을 격리** | 전체 인스턴스 중단 없이 개별 Agent, Connector 스트림, Job 분기만 독립 복구 |
| **Phoenix Channel이 실시간 제어를 전달** | 실행 중 웨이크업, 스티어링, `/drive` 무효화 알림, 진행 상황, 백프레셔를 저지연으로 전달 |
| **Worker와 Function Runtime이 실행을 분담** | 각 Agent에게 `/drive` FUSE와 `/workspace`를 갖춘 전용 컴퓨터를 제공하고 Applet Action과 PTC/Workflow는 무상태 isolate에서 실행 |
| **PostgreSQL 원장이 사실을 저장** | Pod 페이지, Connectors, 메시지, Job, Brain Claim, 커밋된 작업을 재개 및 감사 가능하게 보장 |

이 다섯 가지 선택을 통해 개인 비서와 AI 동료는 Pod와 메신저 전반에서 수 시간 동안 작업하고, 실행 중 새 맥락을 받아들이며, 장애 시 격리 복구하고, 모든 확정 작업에 감사 가능한 기록을 남깁니다.

런타임 설계 배경은 <a href="https://ding.ee/en-US/why-otp-is-a-better-runtime-for-multi-agent-orchestration/" target="_blank" rel="noreferrer">OTP가 멀티 에이전트 오케스트레이션에 더 나은 런타임인 이유</a>를 읽어 보세요.
