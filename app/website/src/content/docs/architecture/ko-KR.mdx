Ankole은 Company Brain을 갖춘 기업용 Agent Harness이며 오픈 소스로 배포됩니다. 회사가 관리하는 인프라에서 모델, 영속 상태, 권한, 실행 환경을 결합합니다.

Agent는 몇 시간 동안 작업하고, 공유 Company Brain을 사용하고, 브라우저, 터미널, 파일, 외부 시스템으로 업무를 실행하며, 사람이 검사하고 이후 결과로 검증할 수 있는 판단을 전달합니다.

모델은 추론을 담당합니다. Harness는 행동 주체, 접근 권한, 긴 작업의 복구, 컨텍스트 갱신, 수정과 결과의 반영을 관리합니다.

## 시스템 지도

<DocsArchitectureDiagram lang="ko-KR" />

하나의 private deployment 인스턴스에는 논리적 컨트롤 플레인 하나, stateless `Function Runtime`(`ankole-function-runtime`) 서비스, 그리고 Agent마다 한 대의 Agent Computer Worker가 있습니다. 컨트롤 플레인은 identity, 상태, 스케줄링을 관리하고, Pod 협업 워크스페이스를 운영하며, Pod Applet 백엔드 함수와 결정론적 TypeScript 프로그램을 위해 `Function Runtime` isolate를 호출하고 Worker를 만듭니다. 각 Worker는 자신의 Agent가 일하는 전용 컴퓨팅 환경을 제공합니다.

Pod(페이지, 실시간 문서, 물리 샤드 기반 2계층 Base 테이블, Applet, 멀티플레이어 Pod Chat)와 외부 어댑터는 대화 발언을 기록합니다. Signals는 발언, 외부 이벤트, 시간 자극을 접수하고 Sessions는 해당 작업을 실행합니다. 통합 인증과 Identity Provider가 패스워드리스 Email OTP(`SiteCredential`), 엔터프라이즈 SSO, 조직 디렉터리를 제공합니다. AIGateway는 모델, embedding, reranking, 이미지, 웹 capability를 위한 하나의 경계를 제공합니다.

## 컨트롤 플레인, Function Runtime 및 Agent Computer Worker

### 컨트롤 플레인은 상태를 저장하고 결정을 내립니다

Elixir/OTP 컨트롤 플레인은 Pod(페이지, 문서, Base 테이블과 물리 샤드, Applet, 멀티플레이어 Pod Chat), Console, Principal과 접근 권한, 시스템 구성, 신호 라우팅, 실행 세션, Brain, Workflow, Background Agent Jobs, AIGateway, Control Plane Plugins를 소유합니다.

이 모든 모듈은 같은 규칙을 사용합니다. 사용자에게 보이는 결과를 바꾸는 상태는 실행이나 외부 전달을 구동하기 전에 PostgreSQL에 기록됩니다.

프로세스는 재시작될 수 있지만, 수락된 메시지, Job 상태, memory, audit 기록은 남아 있어야 합니다.

OTP 감독 트리는 Agent, 연결, Job에 별도의 장애 도메인을 제공합니다. 하나의 실행 브랜치가 멈추거나 크래시되어도 컨트롤 플레인은 그 브랜치만 복구할 수 있으며 전체 deployment instance가 실패하지는 않습니다.

컨트롤 플레인의 핵심 코드와 주요 상태 머신에는 정형 검증을 적용하여, 재시도, 재시작, 동시 입력 상황에서도 핵심 상태 전이와 경계 불변식이 유지되도록 검증합니다.

### Worker는 Agent의 작업용 컴퓨터입니다

주 Agent loop는 control plane에서 실행됩니다. 환경 도구나 Codex가 필요할 때 Agent Computer Worker를 시작합니다. Worker는 도구, Skills, 브라우저, 터미널, 파일 작업, automation script와 Codex Job을 실행하고 control plane이 영구 결과를 커밋합니다.

각 Agent에는 Worker ID가 하나 있으며 동시에 승인하는 Worker 인스턴스는 최대 하나입니다. Agent끼리 Worker, 캐시 디스크, credential을 공유하지 않습니다. Worker 컨테이너 또는 Pod가 유일한 격리 경계입니다. Agent의 명령은 내부 sandbox 없이 실행되며 Agent 자신의 컴퓨터를 바꿀 수 있습니다. Kubernetes에서는 Pod 템플릿의 runtime class로 gVisor를 추가할 수 있습니다.

control plane은 Agent가 선택한 provider로 Worker를 관리합니다. Docker, Kubernetes, Cloudflare, Vercel, AWS Lambda MicroVMs, Alibaba Function Compute를 지원합니다. Home은 `/workspace`의 영구 스토리지이며 `/var/cache/ankole`은 버릴 수 있는 캐시입니다. 명령은 sudo 없이 uid 1000으로 실행됩니다.

RuntimeFabric은 Worker마다 하나인 Phoenix Channel로 컨트롤 플레인과 Worker를 연결합니다. 웨이크업, 스티어링, 취소, 진행 상황, 실행 결과를 전달합니다.

지연 시간이 낮은 실시간 channel이지 데이터베이스가 아닙니다. 연결이 실패한 후에도 복구는 PostgreSQL 상태를 사용합니다.

### Worker pool은 플랫폼과 설정을 선택합니다

운영자는 **Settings → Worker providers**에서 Worker pool을 설정합니다. provider 하나는 site 수준의 pool이며 플랫폼 유형, YAML 설정과 암호화한 플랫폼 자격 증명을 가집니다. 여러 Agent가 같은 pool을 사용해도 각 Agent의 컴퓨터와 영구 Home은 전용입니다. 유형이나 인스턴스 사양이 다르면 별도 pool을 사용합니다.

Agent 생성 시 pool을 선택하거나 site의 기본 pool을 사용합니다. 이후 이 선택은 유지됩니다. control plane은 필요할 때 Worker를 시작하고 유휴 시 해제하거나 일시 중지합니다. 오래된 인스턴스는 Home을 유지하며 교체하고 캐시는 별도로 재구축할 수 있습니다. [Worker pool](../worker-management/)을 참조하세요.

환경 workspace와 Codex turn의 용량은 Worker마다 제한합니다. 주 대화와 Workflow 모델 호출은 control plane에서 실행되므로 이 용량을 사용하지 않습니다. pool을 추가하면 배치 선택지가 늘어나지만 기존 Agent의 작업을 공유 컴퓨터 사이에서 옮기지는 않습니다.

## 하나의 메시지가 재개 가능한 작업이 되는 방법

### 대화는 참여자의 발언을 저장합니다

대화는 사람과 Agent가 공유하는 공간입니다. `Ankole.Conversations`는 참여자와 메시지를 저장합니다. Pod는 네이티브 발언을 직접 기록합니다. 어댑터는 외부 대화의 발언을 관찰하며, 내용의 기준은 외부 플랫폼입니다.

대화 발언과 Agent 작업은 서로 다른 기록입니다. 발언은 참여자의 기록입니다. 모델 호출, 도구 결과, 압축은 실행 세션에 대응하는 AIGateway 모델 상태에 속합니다. 실행 세션은 여러 대화를 넘나들지 않으므로 한 대화의 작업이 다른 대화에 들어가지 않습니다.

### Signals는 모든 자극을 접수합니다

Agent를 지칭한 발언은 signal을 생성합니다. 시간, 외부 이벤트, check-back, 작업 완료도 signal입니다. `Ankole.Signals`는 실행 세션을 깨우기 전에 출처, 출처 이벤트 ID, 대상, 귀속, 권한을 영구 저장합니다.

네이티브 발언과 파생 signal은 같은 트랜잭션에서 커밋됩니다. 접수 시 `(Agent, source, id)`로 중복을 제거합니다. 이후의 모든 동작이 한 번만 실행된다는 보장은 아닙니다.

signal은 실행 세션을 직접 지정할 수 있습니다. 그렇지 않으면 대화 참여 관계나 Signal Routing Rule이 대상을 선택합니다. 대화 호스트 어댑터는 발언을 관찰하고 응답을 전달합니다. 이벤트 소스 어댑터는 signal만 생성합니다. Automation Job은 기계적인 검사를 수행하고 판단이 필요할 때 부모 실행 세션에 signal을 보냅니다. [Automation Jobs](../automation-jobs/)를 참조하십시오.

### Sessions는 작업을 실행하고 복구합니다

`Ankole.Sessions`는 큐, Admission, Driver, Run, 도구, 복구를 소유합니다. 하나의 실행 세션은 동시에 하나의 Run을 실행합니다. 실행을 시작할 때마다 Admission이 테넌트, Agent 상태, 권한, 할당량을 확인합니다.

각 Agent는 대화에서 자신의 실행 세션을 가지며 모든 대화 참여자가 그 작업을 볼 수 있습니다. 대화형 턴과 사람이 트리거한 턴 — 사람이 깨운 `may_intervene` 턴 포함(Agent 메시지는 결코 다른 Agent를 깨우지 않음) — 은 **`Human ∩ Agent` 권한 교집합**(`%Ankole.AuthZ.Actor{principal: agent, interactive_principal: human}`) 아래에서 실행되며, 사람과 Agent 모두 접근 권한을 보유해야 합니다. 대화형 사람이 없는 자율 비인간 턴(`cron`, `webhook`, 백그라운드 서비스 트리거)은 Agent 자신의 권한으로 실행됩니다.

cron 규칙과 백그라운드 작업은 별도의 실행 세션을 가지며 대상 대화에 결과를 발언합니다. 대화의 다음 턴은 새 발언을 읽고 다른 실행 세션의 내부 작업은 가져오지 않습니다.

AIGateway는 모델 상태를 저장하고 이어 갑니다. 런타임은 입력, 지시, 도구, 이어 가기, 압축을 결정합니다. Driver의 PostgreSQL epoch는 오래된 쓰기를 거부합니다. 복구는 커밋된 진행 상태에서 계속됩니다. 모델 호출은 반복될 수 있고 기록된 도구 결과는 재사용하며, 결과가 불명확한 호출은 중단으로 보고합니다.

### Presentation과 Delivery는 보이는 결과를 커밋합니다

Presentation은 보이는 응답을 한 번만 결정합니다. 네이티브 응답은 완료 트랜잭션에서 발언이 됩니다. silent turn은 발언하지 않습니다. 외부 응답은 영구적인 Delivery 의도를 생성한 다음 어댑터가 보냅니다.

외부 플랫폼이 성공을 확인하면 전달 성공을 기록하는 같은 트랜잭션에서 발언을 저장합니다. 나중에 도착한 동일 메시지 ID의 이벤트는 같은 발언으로 병합됩니다. 실패, 만료, 결과 불명확 상태의 전달은 발언을 만들지 않습니다. 결과가 불명확한 전송을 무조건 다시 보내지 않습니다.

스트리밍 텍스트는 진행 상황이며 발언을 커밋한 뒤에만 대화 기록이 됩니다. 연결이 끊긴 페이지는 커밋된 기록과 실행 상태를 다시 읽고 중간 스트림은 재전송하지 않습니다.

설계 선택, 비용, 소스를 확인한 비교는 [대화, 신호, 실행 세션](../conversations-signals-sessions/)을 참조하십시오.

## Brain: 현재 상태를 유지하는 세계 모델

Brain은 채팅 발췌문으로 채워진 벡터 데이터베이스가 아닙니다. 계속 변하는 세계의 현재 모습을 유지합니다. 새 증거는 이전 Claim을 보완하거나 수정하거나 대체할 수 있습니다. 증거가 충돌하면 Dreaming은 사람이 검토할 수 있도록 모순을 기록하며 관련 Claim을 조용히 고쳐 쓰지 않습니다.

지식은 Agent와의 대화, 대상 그룹에서 누구도 Agent를 지칭하지 않은 메시지, 등록된 파일 또는 URL Source에서 올 수 있습니다.

같은 테넌트의 Agent가 지식 공간을 공유하며 테넌트 간 지식 공간은 분리됩니다. 보호된 본문, Claim, Timeline 이벤트는 `world`, 권한 그룹 또는 하나의 Principal 공개 범위를 가집니다. Source와 외부 대화는 출처를 기록하지만 학습한 지식에 대한 접근 권한을 부여하지 않습니다.

턴 동안 통합 회상이 현재 작업에 필요한 장기 컨텍스트를 제공합니다. 오프라인 Dreaming은 새 증거를 정리하고, 패턴을 찾고, 이전 예측을 채점하고, 검토가 필요한 충돌을 표시합니다.

[Brain](../brain/)은 “지금 세계가 어떤 상태인가”를 담당합니다. [Skill Lessons](../skill-lessons/)는 반복되는 작업 증거에서 Agent가 학습한 절차 가드레일을 보관합니다. 해당 Skill과 함께 제공되지만 Skill 원본을 고쳐 쓰지 않으며, 더 이상 적용되지 않으면 폐기됩니다.

이 구조는 Agent가 시간이 지나면서 팀의 규칙을 학습한다는 홈페이지의 약속을 구현합니다. 복리(compounding)는 더 긴 로그를 의미하지 않습니다. 다음 Job이 더 나은 지식과 더 나은 방법에서 시작한다는 뜻입니다.

사용자 관점에서 이 시스템은 장기 기억이며, 저장, Dreaming, 작성 권한은 Brain이 담당합니다.

## Background Agent Jobs: 메인 세션을 막지 않는 긴 작업

메인 Agent는 조사, 데이터 분석, 파일 작업, 코드 변경, Deep Research를 Background Agent Job에 위임할 수 있습니다. 메인 세션은 계속 사용 가능하며 사용자와 대화를 이어갈 수 있습니다.

control plane은 Job 수명 주기를 저장합니다. 인스턴스를 교체하면 영구 Home의 작업 공간과 Codex 스레드에서 재개합니다. PostgreSQL은 접수한 작업과 복구 상태를 보존합니다.

메인 Agent와 Job은 계속 통신할 수 있습니다. Job은 입력을 요청하거나, 실패와 최종 결과를 반환하거나, 요청되면 침묵할 수 있습니다. 사람을 기다릴 때는 실행 슬롯을 해제하고 답이 도착하면 재개합니다.

Deep Research는 이 아키텍처의 고급 용도입니다. Agent Plugin이 workspace 템플릿을 제공하고, Skill이 연구 방법을 제공하며, Background Agent Job이 내구성 있는 실행을 제공합니다.

Job workspace는 영속 Home에 남습니다. Worker 밖에서 사용할 연구 자료와 산출물은 Agent가 control plane 드라이브에 게시합니다.

[Background Agent Jobs](../background-jobs/)와 [Deep Research](../deep-research-job/)를 참조하십시오.

## AIGateway: AI capability를 위한 하나의 경계

AIGateway는 모델 capability와 Agent 실행을 분리합니다. 메인 Agent, Job, Brain, 외부 API 클라이언트가 LLM, embedding, rerank, 이미지, Web Search, Web Fetch Provider에 같은 경계를 사용합니다.

Agent model profile이 실행 모델을 선택합니다. 각 테넌트가 선택한 Brain maintainer Agent의 `light`, `heavy`, `web_fetch` profile이 Brain 작업을 담당합니다. 사이트 AppConfigure가 embedding 모델을 선택하고 테넌트 AppConfigure가 rerank 모델을 선택합니다. 컨트롤 플레인은 Provider credential을 암호화해 저장하고 AIGateway가 업스트림 요청에 사용합니다.

Agent와 Worker는 사용할 수 있는 모델 선택과 호출 결과만 받습니다.

AIGateway는 기록을 저장하지 않는 호출과 이어 갈 수 있는 모델 세션 상태를 모두 지원합니다. 요청 변환, 스트림 이벤트, tool 결과, 컨텍스트 compaction, 사용량 기록, 최종 결과 커밋을 소유합니다.

Worker는 Provider마다 별도의 수명 주기를 구현하지 않습니다.

tool 카탈로그가 크면 모델은 Tool Search를 통해 필요할 때 tool을 검색하거나, Programmatic Tool Calling을 통해 많은 tool을 호출하고 결과만 반환하는 프로그램 하나를 제출할 수 있습니다. AIGateway와 Workflow는 stateless `ankole-function-runtime` isolate(`POST /v1/program/run`)에서 결정론적 TypeScript 프로그램을 실행합니다. 네이티브 지원이 있는 Provider는 네이티브 호출을 그대로 전달하고, AIGateway는 다른 모든 Provider를 위해 gateway에서 같은 capability를 제공합니다. 또한 Provider 하나가 ChatGPT 구독 같은 계정 credential을 포함해 여러 credential을 풀로 보유할 수 있습니다. 실패 귀속, 재시도, 사용량 기록은 credential별로 유지됩니다.

[AIGateway](../ai-gateway/)와 [LLM Provider 추가](../adding-a-provider/)를 참조하십시오.

## 엔터프라이즈 identity, 접근, 확장

Ankole은 사람, Agent, 시스템 서비스를 Principal로 나타냅니다. Pod와 Console 전반의 통합 패스워드리스 인증은 개인 `SiteCredential` Email OTP와 테넌트 엔터프라이즈 Identity Provider(OIDC/OAuth SSO 및 조직 디렉터리 동기화)를 통해 비밀번호를 저장하지 않고 워크스페이스 구성원과 관리자를 인증합니다.

채팅 channel이 메시지를 보내고 받습니다. 이 Provider들은 서로 다른 플랫폼을 사용할 수 있습니다.

AuthZ는 Principal, 권한 그룹, 리소스, 작업, 조건에서 런타임에 결정합니다. 접근은 prompt의 문장이 아니며 모델이 스스로 권한을 가졌다고 선언할 수 없습니다.

컴파일 타임에 결합되는 사이트 범위 Control Plane Plugins는 서브시스템 어댑터(Signals, Identity Provider, AI Gateway provider, Worker provider), 감독되는 OTP 프로세스, 외부 HTTP plug, 범위가 지정된 확장 JSON:API 라우트, 도메인 트랜잭션 훅, `AppConfigure` 구성 필드 및 타입이 지정된 UI 슬롯을 제공합니다. Agent Plugins는 tool과 workspace 템플릿을 추가합니다.

Skill은 어떤 유형의 작업을 수행하는 방법을 설명하며 메인 Agent나 Background Agent Jobs로 제한할 수 있습니다.

외부 MCP server는 Skill을 통해 들어옵니다. Skill이 연결을 선언하고, Worker가 실행별 구성을 생성했다가 실행이 끝나면 제거하며, 모델은 모든 MCP tool의 상주 목록 하나를 마주하지 않습니다.

[Principal과 권한 그룹](../principal-and-groups/), [신호 라우팅 규칙](../signal-bindings/), [Agent Library](../skills/), [MCP server 참조](../mcp/)를 참조하십시오.

## 내구성 경계

PostgreSQL 18+ 컨트롤 플레인 데이터베이스는 identity, 접근, 구성, Pod 메타데이터 및 문서, 메시지, 세션, Job, memory, 전달 상태, audit 기록 같은 내구성 있는 도메인 사실을 저장하며, 물리 **Base 샤드 데이터베이스(`BASE_DB_URLS`)**는 테넌트 Base 테이블 행을 저장합니다. 시점 복구(PITR) 시 모든 Base 샤드의 복구 목표 시점은 컨트롤 플레인 데이터베이스 복구 목표 시점 이상(`>=`)이어야 합니다. 시스템이 결과를 커밋했는지 결정할 때 이 PostgreSQL 기록들을 사용하십시오.

오브젝트 스토리지(control plane 파일 저장소)는 Pod 파일, Pod 및 대화 첨부 파일, 컴파일된 Applet 번들, 게시한 파일, Skill, Automation 스크립트를 저장합니다. 영구 Home은 작업 공간, 사용자 패키지, Codex 스레드를 따로 보존합니다. 컨트롤 플레인 PostgreSQL 데이터베이스, 모든 물리 Base 샤드 데이터베이스, 오브젝트 스토리지, 모든 Home, 원래 배포 암호화 키를 함께 백업하세요.

RuntimeFabric, `ankole-function-runtime` isolate, Worker 프로세스, 스트림 미리 보기, `/var/cache/ankole`은 stateless이거나 다시 만들 수 있습니다. 영구 Home은 인스턴스 삭제 후에도 유지해야 하며 스토리지 백업이 필요합니다. [백업 및 복원](../backup-and-restore/)을 참조하세요.

## 세 가지 deployment 형태

| 형태 | 컨트롤 플레인, Function Runtime 및 Worker | 영속화 |
| --- | --- | --- |
| **Docker Compose · 단일 호스트 권장** | Linux, macOS, Windows 호스트 하나가 컨트롤 플레인과 `ankole-function-runtime`을 실행하고, 컨트롤 플레인이 Docker socket을 통해 Agent마다 Worker 컨테이너 하나를 만듦 | PostgreSQL 18+(구성된 `BASE_DB_URLS` 샤드 포함), 오브젝트 스토리지, Agent별 전용 영구 Home volume |
| **Kubernetes · 엔터프라이즈 deployment 권장** | Helm 배포가 컨트롤 플레인과 `ankole-function-runtime` Deployment를 실행하고, 컨트롤 플레인이 Kubernetes API를 통해 Agent마다 Worker Pod 하나를 만듦 | PostgreSQL 18+와 물리 Base 샤드 데이터베이스, 오브젝트 스토리지, Home PVC 또는 공유 스토리지. 캐시 volume은 별도 |
| **소스 설치** | `bun run services:start`가 PostgreSQL 18과 `ankole-function-runtime`을 시작하고, `bun dev`가 컨트롤 플레인을 실행해 Agent마다 watch 모드의 Docker Worker 컨테이너를 만듦 | PostgreSQL 18, `var/ankole-dev/files`, 전용 Docker 영구 Home volume |

논리적 경계는 모든 형태에서 같습니다. 인스턴스에는 컨트롤 플레인이 하나 있으며, 컨트롤 플레인이 각 Agent에 자신의 Worker를 제공합니다. 전체 절차는 [빠른 시작](../quickstart/#deployment)을 참조하십시오.

## 다섯 가지 기술적 결정

| 결정 | 해결하는 문제 |
| --- | --- |
| **Virtual Actor가 AI 작업을 담당** | 각 세션에 주소, 메일박스, 수명 주기, 복구 위치를 제공 |
| **OTP 감독 트리가 장애 도메인을 정의** | 전체 인스턴스를 실패시키지 않고 Agent 또는 연결 브랜치 하나를 복구 |
| **Phoenix Channel이 실시간 제어를 전달** | Agent 실행 중 웨이크업, 스티어링, 진행, 백프레셔를 전달 |
| **Agent Computer Worker가 실행을 제공** | 각 Agent에게 tool, 파일, 터미널, 브라우저, Codex를 위한 자신의 컴퓨터를 제공 |
| **PostgreSQL 원장이 사실을 저장** | 메시지, Job, memory, 결정, 커밋된 작업을 재개 가능하고 감사 가능하게 만듦 |

이 결정들은 하나의 결과를 지원합니다. Agent가 몇 시간 동안 일하고, 실행 중에 새 정보를 받고, 독립적으로 실패하고 복구하며, 각 커밋된 작업에 추적을 남길 수 있습니다.
