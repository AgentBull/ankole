Ankole is an enterprise Agent Harness with a Company Brain. It runs on company infrastructure and gives models the context, authority, persistent execution, and feedback that company decisions require.

An Agent can work for hours, use the shared Company Brain, act through browsers, terminals, files, and connected systems, and deliver a judgment that people can inspect and later outcomes can test.

The Harness identifies each actor, applies access rules, restores long work, keeps context current, and carries corrections into later decisions.

## System map

<DocsArchitectureDiagram lang="en-US" />

One private deployment instance has one logical control plane and one Agent Computer Worker for each Agent. The control plane manages identity, state, and scheduling, and it creates the Workers. Each Worker provides the compute environment where its Agent works.

Workplace and external adapters record conversation messages. Signals admits messages, external events, and schedules; Sessions executes their work. Identity Providers supply people and the organization directory. AIGateway provides one boundary for models, embeddings, reranking, images, and web capabilities.

## Control plane and Agent Computer Workers

### The control plane stores state and makes decisions

The Elixir/OTP control plane owns the Console, Principals and access, system configuration, signal routing, sessions, Brain, Background Agent Jobs, AIGateway, and Control Plane Plugins.

All these modules use the same rule. State that changes a user-visible result goes to PostgreSQL before it drives execution or external delivery.

A process can restart, but accepted messages, Job state, memory, and audit records must remain.

OTP supervision trees give Agents, connections, and Jobs separate failure domains. If one execution branch hangs or crashes, the control plane can recover that branch without failing the complete deployment instance.

### A Worker is the Agent's work computer

The control plane runs the main Agent loop. It starts the Agent Computer Worker when environment tools or Codex need the Agent's computer. The Worker executes tools, Skills, browsers, terminals, file operations, automation scripts, and Codex Jobs. The control plane commits durable results.

Each Agent has one Worker identity and at most one admitted Worker instance at a time, and Agents never share a Worker, a cache disk, or a credential. The Worker container or Pod is the only isolation boundary: the Agent's commands run without an inner sandbox and may change the Agent's own computer. On Kubernetes, the Pod template's runtime class can add gVisor.

The control plane manages each Worker through its selected provider: Docker, Kubernetes, Cloudflare, Vercel, AWS Lambda MicroVMs, or Alibaba Function Compute. Agent Home is persistent storage at `/workspace`; `/var/cache/ankole` holds disposable caches. Commands run as uid 1000 without sudo.

RuntimeFabric connects the control plane and Workers over one Phoenix Channel per Worker. It carries wakeups, steering, cancellation, progress, and execution results.

It is a low-latency live channel, not a database. Recovery still uses PostgreSQL state after a connection fails.

### Worker pools select the platform and configuration

Operators configure Worker pools through **Settings → Worker providers**. Each provider is one site-level pool with a platform type, YAML configuration, and encrypted platform credentials. Several Agents can use the same pool, but each keeps its own computer and persistent Home. Different types or instance sizes use separate pools.

Agent creation selects a pool explicitly or uses the site's default. The binding stays with that Agent. The control plane starts its Worker on demand, releases or pauses it when idle, and replaces an outdated instance while preserving Home. The cache can be rebuilt separately. See [Worker pools](../worker-management/).

Each Worker has its own capacity for environment workspaces and Codex turns. Main conversation and Workflow model calls run in the control plane and do not consume that capacity. More pools provide more placement choices; they do not move an existing Agent's work between shared computers.

## How one message becomes resumable work

### Conversations preserve messages

A conversation is a shared space for people and Agents. `Ankole.Conversations` stores its participants and messages. Workplace writes native messages directly. An adapter observes messages in an external conversation; the external platform remains their authority.

Conversation messages and Agent work have separate records. Messages belong to participants. Model calls, tool results, and compaction belong to the session's model state in AIGateway. A session does not cross conversations, so one conversation's work cannot enter another conversation.

### Signals admit every stimulus

A message that addresses the Agent creates a signal. Time, external events, check-back, and task completion also create signals. `Ankole.Signals` records the source, source event ID, target, attribution, and authorization before it wakes a session.

Native messages and their signals commit in one transaction. Admission removes duplicates by `(Agent, source, id)`. This does not guarantee that every later action happens once.

A signal can name a session explicitly. Otherwise, participation or a Signal Routing Rule selects the target. A conversation-host adapter observes messages and delivers replies. An event-source adapter only supplies signals. Automation Jobs can perform mechanical checks and send a signal to the parent session when judgment is needed. See [Automation Jobs](../automation-jobs/).

### Sessions execute and recover work

`Ankole.Sessions` owns the queue, Admission, Driver, Run, tools, and recovery. One session runs one Run at a time. Admission checks the tenant, Agent state, authorization, and quota whenever execution starts.

Each Agent has its own session in the conversation. All conversation participants can see that work. An addressed turn uses the requester's authorization. An intervention uses the Agent's identity by default. It uses a person's authorization only when the existing intervention policy identifies that person as the current requester.

Cron rules and background tasks have separate sessions. They publish results into a target conversation. The conversation's next turn reads those new messages without importing the other session's internal work.

AIGateway stores and continues model session state. The runtime selects inputs, instructions, tools, continuation, and compaction. The Driver's PostgreSQL epoch rejects stale writes. Recovery uses committed progress: model calls can repeat, recorded tool results are reused, and uncertain tool operations are reported as interrupted.

### Presentation and Delivery commit visible results

Presentation decides the visible reply once. A native reply becomes a message in the completion transaction. A silent turn creates no message. An external reply creates a durable Delivery intent, which the adapter sends.

A confirmed external send becomes a message in the transaction that records delivery success. A later platform event with the same message ID refers to the same message. Failed, expired, and unknown deliveries do not create messages. An unknown outcome is not sent again blindly.

Streamed text shows current progress. It becomes conversation history only after message commit. A disconnected page reads committed history and execution state; it does not replay a partial stream.

See [Conversations, signals, and sessions](../conversations-signals-sessions/) for the design choices, costs, and source-checked comparison.

## Brain: a world model that stays current

Brain is not a vector database filled with chat excerpts. It maintains an evolving world model. New evidence can extend, revise, or retire earlier claims. When evidence conflicts, Dreaming records the contradiction for human review instead of silently rewriting the claims.

Knowledge can come from conversations with the Agent, eligible group messages that nobody addressed to it, and registered file or URL Sources.

All Agents in one tenant share one knowledge space. Tenants have separate knowledge spaces. Each protected passage, claim, and timeline event uses a `world`, permission-group, or Principal audience scope. A Source or external conversation records provenance; it does not grant access to the learned knowledge.

During a turn, unified recall supplies the long-term context that the current work needs. Offline Dreaming organizes new evidence, finds patterns, grades earlier predictions, and flags conflicts for review.

[Brain](../brain/) owns “what the world is like now.” [Skill Lessons](../skill-lessons/) preserve Agent-specific process guardrails learned from repeated work evidence. They accompany the relevant Skill without changing its source and retire when they no longer apply.

This structure implements the homepage promise that an Agent learns the team's rules over time. Compounding does not mean a longer log. It means that the next job starts from better knowledge and a better method.

Long-term memory is the user view of this system. Brain owns storage, Dreaming, and write authority.

## Background Agent Jobs: long work without blocking the main session

A main Agent can delegate research, data analysis, file work, code changes, and Deep Research to a Background Agent Job. The main session remains available and can continue talking to the user.

The control plane stores the Job lifecycle. After instance replacement, the Worker resumes from workspace and Codex thread files in persistent Home. PostgreSQL owns the accepted work and its recovery state.

The main Agent and Job can continue to communicate. A Job can ask for input, return failures and final results, or stay silent when requested. When it waits for a person, it releases its execution slot and resumes after the answer arrives.

Deep Research is an advanced use of this architecture. An Agent Plugin supplies the workspace template, Skills supply the research method, and a Background Agent Job supplies durable execution.

The Job workspace remains in persistent Home. The Agent publishes research material and deliverables to its control-plane drive when they must be available outside the Worker.

See [Background Agent Jobs](../background-jobs/) and [Deep Research](../deep-research-job/).

## AIGateway: one boundary for AI capabilities

AIGateway separates model capabilities from Agent execution. Main Agents, Jobs, Brain, and external API clients use the same boundary for LLM, embedding, rerank, image, Web Search, and Web Fetch Providers.

Agent model profiles select models for Agent execution. Each tenant selects a Brain maintainer Agent whose `light`, `heavy`, and `web_fetch` profiles serve Brain work. Site AppConfigure selects the embedding model; tenant AppConfigure selects the rerank model. The control plane stores Provider credentials in encrypted form, and AIGateway uses them for upstream requests.

Agents and Workers receive only the model choices and call results that they can use.

AIGateway supports calls that store no history and model session state that can continue. It owns request conversion, stream events, tool results, context compaction, usage records, and final-result commits.

Workers do not implement a separate lifecycle for each Provider.

When the tool catalog is large, a model can search tools on demand through Tool Search, or submit one program that calls many tools inside a restricted sandbox and returns only the results. A Provider with native support passes these calls through, and AIGateway supplies the same capability in the gateway for every other Provider. One Provider can also hold several credentials as a pool, including account credentials such as a ChatGPT subscription. Failure attribution, retries, and usage records stay per credential.

See [AIGateway](../ai-gateway/) and [Add an LLM Provider](../adding-a-provider/).

## Enterprise identity, access, and extensions

Ankole represents people, Agents, and system services as Principals. An Identity Provider supplies Console SSO and synchronizes employees, contacts, and the organization directory.

A chat channel sends and receives messages. These Providers can use different platforms.

AuthZ decides at runtime from the Principal, permission group, resource, action, and condition. Access is not a sentence in a prompt, and a model cannot declare that it has a permission.

Control Plane Plugins connect IdPs, chat channels, and other control-plane capabilities. Agent Plugins add tools and workspace templates.

Skills describe how to do a type of work and can be limited to the main Agent or Background Agent Jobs.

External MCP servers enter through Skills. A Skill declares its connection, the Worker generates a per-execution configuration and removes it when the execution ends, and the model never faces one resident list of every MCP tool.

See [Principals and permission groups](../principal-and-groups/), [Signal routing rules](../signal-bindings/), [Agent Library](../skills/), and the [MCP server reference](../mcp/).

## Durability boundaries

PostgreSQL stores durable domain facts such as identity, access, configuration, messages, sessions, Jobs, memory, delivery state, and audit records. Use these records to decide whether the system committed a result.

The control-plane drive stores attachments, published files, Skills, and Automation scripts in its file store. Persistent Home separately stores workspaces, local packages, and Codex threads. Back up PostgreSQL, the file store, all Homes, and the original deployment encryption key together.

RuntimeFabric, live Worker processes, stream previews, and `/var/cache/ankole` are rebuildable. Persistent Home must survive instance deletion and needs a storage backup. See [Backup and restore](../backup-and-restore/).

## Three deployment forms

| Form | Control plane and Workers | Persistence |
| --- | --- | --- |
| **Docker Compose · recommended for one host** | One Linux, macOS, or Windows host runs the control plane, which creates one Worker container through the Docker socket for each Agent | PostgreSQL, the file store, and a private persistent Home volume for each Agent |
| **Kubernetes · recommended for enterprise deployment** | One control plane creates one Worker Pod through the Kubernetes API for each Agent | PostgreSQL, the file store, and persistent Home PVCs or shared storage; cache volumes are separate |
| **Source installation** | `bun dev` runs the control plane, which creates a Docker Worker container for each Agent; the container runs the local Agent Computer source in watch mode | PostgreSQL, `var/ankole-dev/files`, and private persistent Docker Home volumes |

The logical boundary is the same for every form. The instance has one control plane, and the control plane gives each Agent its own Worker. See [Quick start](../quickstart/#1-deploy-ankole) for the complete procedures.

## Five technical decisions

| Decision | Problem it solves |
| --- | --- |
| **Virtual Actors carry AI work** | Give each session an address, mailbox, lifecycle, and recovery position |
| **OTP supervision trees define failure domains** | Recover one Agent or connection branch without failing the complete instance |
| **Phoenix Channels carry live control** | Move wakeups, steering, progress, and backpressure while an Agent runs |
| **Agent Computer Workers provide execution** | Give each Agent its own computer for tools, files, terminals, browsers, and Codex |
| **The PostgreSQL ledger stores facts** | Make messages, Jobs, memory, decisions, and committed operations resumable and auditable |

These decisions support one result. An Agent can work for hours, accept new information while it runs, fail and recover independently, and leave a trace for each committed action.
