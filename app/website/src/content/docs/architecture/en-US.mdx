Ankole is an enterprise Agent Harness built around a Company Brain. Running on your organization's infrastructure, it gives models the institutional context, scoped authority, persistent execution, and feedback loops that enterprise decisions require.

Within the Harness, an Agent can work across multi-hour tasks, draw on the shared Company Brain, act through browsers, terminals, files, and connected systems, and deliver judgments that people can inspect and real-world outcomes can validate. At every step, Ankole identifies the acting Principal, enforces access rules, recovers interrupted work, keeps context current, and carries corrections forward into future decisions.

## System map

<DocsArchitectureDiagram lang="en-US" />

A private deployment instance consists of one logical control plane, a stateless `Function Runtime` (`ankole-function-runtime`) service, and a dedicated Agent Computer Worker for each Agent. The control plane manages identity, durable state, and scheduling; hosts Pod collaborative workspaces; invokes `Function Runtime` isolates for Pod Applet backend functions and deterministic TypeScript programs; and provisions Workers so each Agent operates inside its own compute environment.

Across the workspace, Pod (pages, real-time documents, two-tier Base tables on physical shards, Applets, and multiplayer Pod Chat) and external channel adapters record conversation messages. From there, `Ankole.Signals` admits incoming messages, external events, and scheduled triggers, and `Ankole.Sessions` executes the resulting work. Unified authentication and Identity Providers supply passwordless Email OTP (`SiteCredential`), enterprise SSO, and organization directory sync, while AIGateway provides a single boundary for models, embeddings, reranking, images, and web capabilities.

## Control plane, Function Runtime, and Agent Computer Workers

### The control plane stores state and makes decisions

The Elixir/OTP control plane owns Pod (pages, documents, Base tables and physical shards, Applets, and multiplayer Pod Chat), the Console, Principals and access control, system configuration, signal routing, sessions, Brain, Workflows, Background Agent Jobs, AIGateway, and Control Plane Plugins. Every module follows one durability rule: any state change that affects a user-visible result commits to PostgreSQL before driving execution or external delivery. Consequently, processes can restart at any time while accepted messages, Job state, memory, and audit records remain intact.

At runtime, OTP supervision trees place Agents, external connections, and Jobs in separate failure domains, so if one execution branch hangs or crashes, the control plane recovers that branch without taking down the deployment instance. Formal verification also checks critical control-plane code and core state machines to ensure key state transitions and boundary invariants hold across retries, restarts, and concurrent inputs.

### A Worker is the Agent's work computer

The control plane runs the main Agent loop and starts the Agent Computer Worker on demand whenever environment tools or Codex need the Agent's computer. Inside the Worker, the Agent runs tools, Skills, browsers, terminals, file operations, automation scripts, and Codex Jobs, while the control plane commits durable results.

Each Agent has one Worker identity and at most one admitted Worker instance at a time, and Agents never share a Worker, a cache disk, or credentials. That Worker container or Pod serves as the isolation boundary: commands run as `uid` `1000` without `sudo` or an inner sandbox and may modify the Agent's own computer (on Kubernetes, the Pod template's runtime class can add gVisor). Depending on the selected provider—Docker, Kubernetes, Cloudflare, Vercel, AWS Lambda MicroVMs, or Alibaba Function Compute—the control plane mounts persistent Agent Home at `/workspace` and disposable caches at `/var/cache/ankole`.

RuntimeFabric connects the control plane and Workers over one Phoenix Channel per Worker, carrying wakeups, steering, cancellation, progress updates, and execution results. Because RuntimeFabric is a low-latency live transport rather than a database, crash recovery always reads committed state from PostgreSQL after a disconnect.

### Worker pools select the platform and configuration

Operators configure Worker pools under **Settings → Worker providers**, where each provider defines a site-level pool with a platform type, YAML configuration, and encrypted platform credentials. Multiple Agents can share a pool while keeping separate computers and persistent Home directories; use separate pools when you need different platforms or instance sizes.

When creating an Agent, the operator either picks a pool explicitly or uses the site default, permanently binding the Agent to that pool. From then on, the control plane starts the Worker on demand, pauses or releases it when idle, and replaces outdated instances while preserving Home and rebuilding `/var/cache/ankole` separately; see [Worker pools](../worker-management/).

Each Worker tracks its own slot capacity for environment workspaces and Codex turns, whereas main-conversation and Workflow model calls run in the control plane without consuming Worker capacity. Adding pools gives operators more placement options rather than migrating an existing Agent's work across shared machines.

## How one message becomes resumable work

### Conversations preserve messages

A conversation is a shared space for people and Agents whose participants and messages live in `Ankole.Conversations`. Pod writes native messages directly to PostgreSQL, whereas channel adapters observe messages in external conversations where the external platform remains the system of record.

Ankole stores conversation messages separately from internal Agent execution state: messages belong to participants, while model calls, tool results, and context compaction belong to the Session's model chain in AIGateway. Because a Session never crosses conversations, internal work from one conversation cannot leak into another.

### Signals admit every stimulus

Whenever a message addresses an Agent—or when a schedule fires, an external event arrives, a check-back timer triggers, or a background task completes—`Ankole.Signals` records the source, source event ID, target, attribution, and authorization before waking a Session.

Native Pod messages and their Signals commit in a single transaction. During admission, `Ankole.Signals` removes duplicates by `(Agent, source, id)` to prevent double-enqueueing, though downstream actions still rely on their own idempotency and receipts.

A Signal can target a Session explicitly; otherwise, Ankole selects the target through conversation participation or a Signal Routing Rule. Conversation-host adapters both observe incoming messages and deliver replies, whereas event-source adapters only emit Signals. Likewise, Automation Jobs can run mechanical checks on a Worker and send a Signal to the parent Session only when model judgment is needed; see [Automation Jobs](../automation-jobs/).

### Sessions execute and recover work

`Ankole.Sessions` owns the queue, Admission, Driver, Run, tools, and recovery. Each Session executes one Run at a time, and Admission verifies the tenant, Agent state, authorization, and token quota whenever execution begins.

Each Agent has its own Session in a conversation, and its visible output is shared with the conversation participants. Every turn accesses resources as the executing Agent, including interactive, human-woken `may_intervene`, scheduled and service-triggered turns. Agent messages never wake other Agents. Human employment and instruction versions still determine whether delegated work may continue; they do not intersect Human grants with Agent resource access.

Cron schedules and background tasks run in separate Sessions and publish finished messages into a target conversation; on its next turn, that conversation reads the published messages without importing the background Session's internal tool history.

AIGateway persists and continues model session state while the runtime selects inputs, instructions, tools, continuation checkpoints, and compaction. A monotonic PostgreSQL epoch on the Driver fences off stale writes, and recovery resumes from committed progress: interrupted model calls can repeat, committed tool results are reused, and uncertain Worker tool calls surface as `interrupted`.

### Presentation and Delivery commit visible results

At the end of a turn, Presentation determines the visible reply once: a silent turn produces no message, a native Pod reply commits as a message in the completion transaction, and an external reply writes a durable Delivery intent for the adapter to send.

Once an external platform confirms delivery, Ankole commits the conversation message in the same transaction that marks delivery succeeded, and any later platform echo carrying the same external message ID reconciles to that row. Failed, expired, and unknown deliveries never create messages, and Ankole never blindly resends a delivery whose outcome is unknown.

Live token streaming previews progress in real time, entering conversation history only once the final message commits. Consequently, a browser client that reconnects after a drop reads committed history and live execution state rather than replaying a partial stream.

See [Conversations, signals, and sessions](../conversations-signals-sessions/) for the design rationale, trade-offs, and code-level comparison.

## Brain: a world model that stays current

Rather than acting as a vector database of raw chat excerpts, Brain maintains an evolving world model. Knowledge enters from direct conversations with an Agent, eligible group messages that nobody addressed directly to it, and registered file or URL Sources. As new evidence arrives, Brain extends, revises, or retires earlier claims, and when evidence conflicts, offline Dreaming records the contradiction for human review instead of silently overwriting prior claims.

All Agents in a tenant share one knowledge space (strictly separated across tenants), where each protected passage, claim, and timeline event carries a `world`, permission-group, or Principal audience scope. Registering a Source or observing an external conversation records provenance without widening access to the learned knowledge.

During live turns, unified recall supplies the long-term context that the current task needs; offline, Dreaming consolidates fresh evidence, identifies patterns, grades earlier predictions, and flags conflicts for review. While [Brain](../brain/) owns “what the world is like now,” [Skill Lessons](../skill-lessons/) capture Agent-specific process guardrails learned from repeated execution evidence, attaching them to the relevant Skill without modifying its source and retiring them when invalidated.

Together, Brain and Skill Lessons fulfill Ankole's core promise that Agents learn how your team works over time—compounding not by growing longer logs, but by starting each new task with sharper knowledge and a better method. Users experience this system as long-term memory, while Brain owns storage, Dreaming, and write authority.

## Background Agent Jobs: long work without blocking the main session

A foreground Agent can delegate extended research, data analysis, file work, code changes, and Deep Research to a Background Agent Job while keeping the main Session free to continue talking with the user.

The control plane persists the Job lifecycle in PostgreSQL, and if a Worker instance is replaced, the new Worker resumes from the Job workspace and Codex thread files stored in persistent Home. Throughout execution, the main Agent and the Job can communicate: a Job can request human input (releasing its Worker execution slot while waiting and resuming once answered), return failures and final results, or stay silent when asked.

Deep Research builds directly on these primitives: an Agent Plugin provides the workspace template, Skills provide the research methodology, and a Background Agent Job provides durable execution. While the scratch workspace stays in persistent Home, the Agent publishes research materials and deliverables to its control-plane Files drive whenever they must be accessible outside the Worker.

See [Background Agent Jobs](../background-jobs/) and [Deep Research](../deep-research-job/).

## AIGateway: one boundary for AI capabilities

AIGateway separates upstream AI capabilities from Agent execution so foreground Agents, Jobs, Brain, and external API clients all share one boundary for LLM, embedding, rerank, image, Web Search, and Web Fetch Providers.

Agent model profiles select models for Agent turns, while each tenant designates a Brain maintainer Agent whose `light`, `heavy`, and `web_fetch` profiles serve Brain operations; site AppConfigure selects the embedding model, and tenant AppConfigure selects the rerank model. The control plane stores Provider credentials encrypted at rest and uses them for upstream requests, exposing only permitted model selectors and call outputs to Agents and Workers so Workers never manage per-Provider lifecycles.

Supporting both stateless calls and continuable model sessions, AIGateway handles request conversion, stream normalization, tool results, context compaction, usage accounting, and final-result commits. When the tool catalog is large, a model can discover tools dynamically through Tool Search or submit a single TypeScript orchestration program through Programmatic Tool Calling. AIGateway and Workflow run those deterministic programs inside stateless `ankole-function-runtime` isolates (`POST /v1/program/run`), passing native calls straight through when a Provider supports them and providing the same capability in the gateway for every other Provider. Each Provider can also pool multiple credentials—including account-backed OAuth pools such as a ChatGPT subscription—keeping failure attribution, retries, and usage records scoped to the individual credential.

See [AIGateway](../ai-gateway/) and [Add an LLM Provider](../adding-a-provider/).

## Enterprise identity, access, and extensions

Ankole represents people, Agents, and system services uniformly as Principals. Passwordless authentication spans Pod and the Console: personal `SiteCredential` Email OTP and tenant Enterprise Identity Providers (OIDC/OAuth SSO and directory sync) authenticate workspace members and administrators without stored passwords, while chat channels send and receive messages across the same or separate platforms.

`Ankole.AuthZ` evaluates every permission check at runtime against the Principal, permission groups, resource, action, and conditions—access is never enforced by a prompt instruction, and a model cannot grant itself permissions.

Compile-time, site-scoped Control Plane Plugins contribute subsystem adapters (Signals, Identity Providers, AIGateway providers, and Worker providers), supervised OTP processes, outer HTTP plugs, scoped extension JSON:API routes, domain transaction hooks, `AppConfigure` fields, and typed UI slots. Agent Plugins contribute Codex tools and workspace templates, while Skills teach specific workflows and can be scoped to foreground turns, Background Agent Jobs, or both. External MCP servers likewise enter through Skills: when a Skill declares an MCP connection, the Worker generates an ephemeral per-execution config and removes it afterward so the model never faces one permanently resident list of every MCP tool.

See [Principals and permission groups](../principal-and-groups/), [Signal routing rules](../signal-bindings/), [Agent Library](../skills/), and the [MCP server reference](../mcp/).

## Durability boundaries

PostgreSQL 18+ stores durable domain facts in the control-plane database—identity, access, configuration, Pod metadata and documents, messages, sessions, Jobs, memory, delivery state, and audit records—while physical **Base shard databases (`BASE_DB_URLS`)** store tenant Base table rows. During point-in-time recovery, every Base shard recovery target must be greater than or equal to (`>=`) the control-plane database recovery target. Treat these PostgreSQL records as the source of truth for whether Ankole committed an outcome.

The object store (control-plane file store) holds Pod files, Pod and conversation attachments, compiled Applet bundles, published files, Skills, and Automation scripts, while persistent Home separately holds workspaces, local packages, and Codex threads. Always back up the control-plane PostgreSQL database, all physical Base shard databases, the object store, all Agent Homes, and the deployment encryption key together.

RuntimeFabric connections, `ankole-function-runtime` isolates, live Worker processes, stream previews, and `/var/cache/ankole` are stateless or rebuildable, whereas persistent Home must survive instance replacement and requires durable storage backups; see [Backup and restore](../backup-and-restore/).

## Three deployment forms

| Form | Control plane, Function Runtime, and Workers | Persistence |
| --- | --- | --- |
| **Docker Compose · recommended for one host** | One Linux, macOS, or Windows host runs the control plane and `ankole-function-runtime`, and the control plane creates one Worker container through the Docker socket for each Agent | PostgreSQL 18+ (plus any configured `BASE_DB_URLS` shards), the object store, and a private persistent Home volume for each Agent |
| **Kubernetes · recommended for enterprise deployment** | One Helm deployment runs the control plane and `ankole-function-runtime` deployments, and the control plane creates one Worker Pod through the Kubernetes API for each Agent | PostgreSQL 18+ and physical Base shard databases, the object store, and persistent Home PVCs or shared storage; cache volumes are separate |
| **Source installation** | `bun run services:start` runs PostgreSQL 18 and `ankole-function-runtime`; `bun dev` runs the control plane, which creates a Docker Worker container in watch mode for each Agent | PostgreSQL 18, `var/ankole-dev/files`, and private persistent Docker Home volumes |

Every deployment form preserves the same logical boundary: one control plane orchestrates the instance and provisions an isolated Worker per Agent. See [Quick start](../quickstart/#1-deploy-ankole) for step-by-step installation procedures.

## Five technical decisions

| Decision | Problem it solves |
| --- | --- |
| **Virtual Actors carry AI work** | Give each session an address, mailbox, lifecycle, and recovery position |
| **OTP supervision trees define failure domains** | Recover one Agent or connection branch without failing the complete instance |
| **Phoenix Channels carry live control** | Move wakeups, steering, progress, and backpressure while an Agent runs |
| **Agent Computer Workers provide execution** | Give each Agent its own computer for tools, files, terminals, browsers, and Codex |
| **The PostgreSQL ledger stores facts** | Make messages, Jobs, memory, decisions, and committed operations resumable and auditable |

Together, these five choices let an Agent work for hours, absorb new context mid-run, fail and recover in isolation, and leave an auditable record of every committed action.
