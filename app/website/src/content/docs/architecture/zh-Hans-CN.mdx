Ankole 是一套配备公司大脑的企业级 Agent Harness。Ankole 部署在企业基础设施中，为企业 Agent 提供公司知识、权限控制、长任务恢复和结果反馈。

Agent 可以连续工作数小时，使用共享的公司大脑，通过浏览器、终端、文件和外部系统执行任务。Agent 交付的判断附带可供人工检查的证据，并由后续结果检验。

Harness 识别每个行动主体，执行访问规则，恢复中断的长任务，根据新信息更新上下文，并将人工纠正用于后续决策。

## 系统总图

<DocsArchitectureDiagram lang="zh-Hans-CN" />

每个私有部署实例包含一个逻辑控制面、无状态的 `Function Runtime`（`ankole-function-runtime`）服务，并为每个 Agent 提供一台 Agent Computer Worker。控制面管理身份、状态和调度，运行 Pod 协作工作区，通过 `Function Runtime` isolate 执行 Pod Applet 后端函数与确定性 TypeScript 程序，并负责创建 Worker。每台 Worker 为它的 Agent 提供专属执行环境。

Pod（页面、实时文档、基于物理分片的双层 Base 多维表、Applet 小应用以及多人协作 Pod Chat）和外部适配器记录对话发言；Signals 接纳发言、外部事件和定时刺激，Sessions 执行相应工作。统一认证与身份提供商提供免密 Email OTP（`SiteCredential`）、企业 SSO 与组织目录同步。AIGateway 统一处理模型、Embedding、Rerank、图像和 Web 工具调用。

## 控制面、Function Runtime 与 Agent Computer Worker

### 控制面保存状态并提交决策

控制面使用 Elixir/OTP，负责 Pod（页面、文档、Base 多维表与物理分片、Applet 小应用和多人 Pod Chat）、Console、主体与权限、系统配置、信号路由、执行会话、Brain、Workflow、后台 Agent 任务、AIGateway 和 Control Plane Plugin。

所有会改变用户可见结果的状态都先写入 PostgreSQL，再驱动执行或对外投递。进程重启后，已接收的消息、任务状态、记忆和审计记录仍然保留。

OTP 监督树为 Agent、连接和后台任务划分独立故障域。某个执行分支卡住或崩溃时，控制面只恢复该分支，其他部分继续运行。

控制面对关键代码和重要状态机使用形式化验证，确保核心状态迁移与边界不变量在重试、重启和并发输入下保持成立。

### Worker 提供 Agent 工作环境

控制面运行主 Agent loop，需要环境工具或 Codex 时才启动 Agent Computer Worker。Worker 执行工具、Skills、浏览器、终端、文件操作、自动化脚本与 Codex Job，持久结果由控制面提交。

每个 Agent 有一个 Worker 身份，同时最多接纳一个 Worker 实例，Agent 之间从不共享 Worker、缓存盘或凭证。Worker 容器或 Pod 是唯一的隔离边界：Agent 的命令运行时没有内层沙盒，可以改动 Agent 自己的电脑。在 Kubernetes 上，可以通过 Pod 模板的 runtime class 加上 gVisor。

控制面通过 Agent 选定的 provider 管理 Worker：Docker、Kubernetes、Cloudflare、Vercel、AWS Lambda MicroVMs 或阿里云函数计算。Agent Home 是 `/workspace` 上的持久存储，`/var/cache/ankole` 只放可丢失的缓存。命令以 uid 1000 运行，没有 sudo。

RuntimeFabric 通过每个 Worker 一条 Phoenix Channel 连接控制面与 Worker，传递唤醒、引导、取消、进度和执行结果。RuntimeFabric 负责低延迟实时通信。连接中断后，控制面根据 PostgreSQL 中的状态恢复任务。

### WorkerPool 选择平台与实例配置

运维通过 **Settings → Worker providers** 配置 WorkerPool。一个 provider 就是一个站点级池，包含平台类型、YAML 配置与加密的平台凭据。多个 Agent 可以使用同一个池，每个 Agent 仍有自己的电脑和持久 Home。不同类型或实例规格使用不同池。

创建 Agent 时明确选择池，或使用站点默认池。此后绑定保持不变。控制面按需启动 Worker，空闲时回收或暂停，实例过时时保留 Home 并替换；缓存可独立重建。见 [WorkerPool](../worker-management/)。

每台 Worker 单独限制环境工作区和 Codex 回合容量。主对话与 Workflow 的模型调用在控制面执行，不占这部分容量。增加池提供更多部署选择，不会把已有 Agent 的工作迁到共享电脑上。

## 一条消息如何变成可恢复的工作

### 对话保存参与者的发言

对话是人和 Agent 共享的空间。`Ankole.Conversations` 保存参与者与发言。Pod 直接写入原生发言；适配器观察外部对话中的发言，内容仍以外部平台为准。

对话发言与 Agent 的工作分开记录。发言属于参与者；模型调用、工具结果和压缩属于执行会话在 AIGateway 中的模型会话状态。执行会话不跨对话，一个对话中的工作不会进入另一个对话。

### 所有刺激由 Signals 接纳

点名 Agent 的发言派生 signal。时间到达、外部事件、check-back 和任务完成也都是 signal。`Ankole.Signals` 先持久保存来源、来源事件 ID、目标、归因和授权，再唤醒执行会话。

原生发言与它派生的 signal 在同一事务中提交。接纳按 `(Agent, source, id)` 去重；这不代表后续的所有动作都只执行一次。

signal 可以显式指定执行会话；也可以由对话参与关系或信号路由规则选择目标。对话宿主适配器观察发言并执行投递，事件源适配器只产生 signal。Automation Job 可以先完成确定性检查，需要判断时向父执行会话接纳 signal。参见 [Automation Job](../automation-jobs/)。

### Sessions 执行并恢复工作

`Ankole.Sessions` 拥有队列、Admission、Driver、Run、工具和恢复。一个执行会话同时只运行一个 Run。每次开始执行时，Admission 检查租户、Agent 状态、授权与配额。

每个 Agent 在对话中拥有自己的执行会话，其中的工作对全体参与者可见。交互式及由人类触发的回合——包括人类唤醒的 `may_intervene` 主动介入回合（Agent 消息绝不会唤醒其他 Agent）——均在 **`Human ∩ Agent` 权限交集**（`%Ankole.AuthZ.Actor{principal: agent, interactive_principal: human}`）下执行，要求人类与 Agent 双方同时具备访问权限。无交互人类参与的自主非人类回合（`cron`、`webhook` 及后台服务触发器）使用 Agent 自身的权限运行。

cron 规则和后台任务在独立执行会话中工作，再向目标对话发言。对话的下一轮读取这些新发言，不引入其他执行会话的内部过程。

AIGateway 保存和续接模型会话状态；运行时决定输入、指令、工具、续接与压缩。Driver 用 PostgreSQL 中的 epoch 拒绝过期写入。恢复从已提交进度继续：模型调用可能重做，已记录的工具结果直接复用，结果不明的工具调用标记为中断。

### Presentation 与 Delivery 提交可见结果

Presentation 只决定一次可见回复。原生回复在完成事务中追加为发言；silent turn 不发言。外部回复先创建持久的 Delivery 意图，再由适配器发送。

平台确认成功后，在标记投递成功的同一事务中写入发言。平台随后推送的相同消息 ID 合并为同一条发言。失败、过期和结果不明的投递不产生发言；结果不明时不盲目重发。

流式文本表示当前进度，发言提交后才进入对话历史。页面断线后重新读取已提交历史和执行状态，不补发半段文本。

设计选择、代价与经过源码核对的比较见[对话、信号与执行会话](../conversations-signals-sessions/)。

## Brain 维护当前世界模型

Brain 将聊天、Source 和 Agent 写入的内容整理为可更新的世界模型。新证据可以补充、修正或取代已有 Claim。证据发生冲突时，Dreaming 保留冲突并提交人工复核，原有 Claim 继续保留来源和历史。

知识可以来自 Agent 参与的对话、未明确提及 Agent 但符合学习条件的群聊消息，以及已注册的文件或 URL Source。

同一租户中的所有 Agent 共用一个知识空间，租户之间的知识空间隔离。每个受保护的正文段落、Claim 和时间线事件都使用以下一种可见范围：`world`、权限组或单个 Principal。Source 或 Channel 记录出处。学习所得知识的访问权限由可见范围决定。

运行中的 Agent 通过统一的召回接口获得当前任务需要的长期上下文。离线 Dreaming 整理新证据、发现模式、评估到期预测，并标记等待复核的冲突。

[Brain](../brain/) 负责维护当前世界状态。[Skill Lessons](../skill-lessons/) 保存 Agent 从重复工作中学到的规则。Skill Lesson 随对应 Skill 提供，保留 Skill 的来源，并在失效后停用。

Brain 为 Agent 提供长期记忆，并负责存储、Dreaming 和写入权限。

## 后台 Agent 任务运行长时工作

主 Agent 可以将调研、数据分析、文件处理、代码修改和 Deep Research 等边界明确的工作交给后台 Agent 任务。后台任务运行期间，主会话仍可继续与用户交流。

控制面保存 Job 生命周期。实例替换后，Worker 从持久 Home 的工作区与 Codex 线程文件恢复；PostgreSQL 保存已接纳的工作与恢复状态。

主 Agent 与后台任务可以继续通信。后台任务可以请求用户补充信息、返回失败信息和最终结果，也可以按要求静默运行。等待用户输入时，后台任务释放执行资源，并在收到回答后恢复。

Deep Research 使用这套机制。Agent Plugin 提供工作区模板，Skill 提供研究方法，后台任务负责持久执行。任务工作区保存在持久 Home；需要在 Worker 外访问的研究资料与交付物，由 Agent 发布到控制面云盘。

参见 [后台 Agent 任务](../background-jobs/) 和 [Deep Research](../deep-research-job/)。

## AIGateway 统一模型调用边界

AIGateway 是模型调用的统一边界。主 Agent、后台任务、Brain 和外部 API 客户端都通过 AIGateway 使用 LLM、Embedding、Rerank、图像、Web Search 和 Web Fetch 服务。

Agent 的模型档案指定执行所用的模型。每个租户选择 Brain 维护 Agent，使用其 `light`、`heavy` 和 `web_fetch` profile 执行 Brain 工作。站点级 AppConfigure 设置 Embedding 模型，租户级 AppConfigure 设置 Rerank 模型。控制面加密保存 Provider 凭证，AIGateway 使用这些凭证请求上游服务。

AIGateway 支持不保存历史的单次调用和可继续的模型会话状态。AIGateway 负责请求转换、流式事件、工具结果、上下文压缩、用量记录和最终结果提交，并统一处理各 Provider 的生命周期。

工具数量较多时，模型可以通过 Tool Search 按需检索工具，也可以通过编程式工具调用（Programmatic Tool Calling）提交程序，批量调用工具并只返回结果。AIGateway 与 Workflow 在无状态 `ankole-function-runtime` isolate（`POST /v1/program/run`）中运行确定性 TypeScript 程序。原生支持这些能力的 Provider 直接处理原生请求，其他 Provider 由 AIGateway 在网关内提供相同能力。一个 Provider 可以配置多个凭证组成凭证池，其中包括 ChatGPT 订阅等账号凭证。系统按单个凭证记录失败、重试和用量。

参见 [AIGateway](../ai-gateway/) 和 [添加 LLM Provider](../adding-a-provider/)。

## 企业身份、权限与扩展

Ankole 将人员、Agent 和系统服务统一表示为主体（Principal）。统一的免密认证覆盖 Pod 与 Console：个人 `SiteCredential` 邮箱验证码（Email OTP）以及租户级企业身份提供商（OIDC/OAuth SSO 与组织架构目录同步）共同认证工作区成员与管理员，系统不存储用户密码。聊天渠道负责收发消息，身份提供商和聊天平台可以不同。

AuthZ 根据主体、权限组、资源、动作和条件，在运行时作出授权决定。AuthZ 判定由运行时执行，提示词和模型输出不能授予权限。

编译期集成的站点级 Control Plane Plugin 可以提供各子系统适配器（Signals、身份提供商、AI Gateway Provider、Worker Provider）、受监督的 OTP 进程、外层 HTTP Plug、带作用域的扩展 JSON:API 路由、领域事务钩子、`AppConfigure` 配置字段和类型化 UI 插槽。Agent Plugin 为 Agent 增加工具和工作区模板。Skill 描述完成某类工作的步骤，并可限定在主 Agent 或后台任务中使用。

外部 MCP 服务器通过 Skill 接入。Skill 声明连接，Worker 为每次执行生成配置，并在执行结束后删除配置。模型只会看到当前 Skill 声明的 MCP 工具。

参见 [主体与权限组](../principal-and-groups/)、[信号路由规则](../signal-bindings/)、[Agent 能力库](../skills/) 和 [MCP 服务器参考](../mcp/)。

## 持久化边界

PostgreSQL 18+ 控制面数据库保存身份、权限、配置、Pod 元数据与文档、消息、会话、任务、记忆、投递状态和审计记录等权威领域状态；物理 **Base 分片数据库（`BASE_DB_URLS`）**保存租户 Base 物理表数据。执行时间点恢复（PITR）时，每个 Base 分片的恢复目标时间必须大于或等于（`>=`）控制面数据库的恢复目标时间。需要判断一项工作是否已经提交时，以这些 PostgreSQL 记录为准。

对象存储（控制面文件存储）保存 Pod 文件、Pod 与会话附件、编译后的 Applet 产物包、发布的文件、Skill 和 Automation 脚本。持久 Home 单独保存工作区、用户软件与 Codex 线程。控制面 PostgreSQL 数据库、全部物理 Base 分片数据库、对象存储、全部 Home 与原部署加密密钥需要一起备份。

RuntimeFabric、`ankole-function-runtime` isolate、Worker 进程、流式预览和 `/var/cache/ankole` 为无状态或可重建状态。持久 Home 必须撑过实例删除，并需要存储备份。参见[备份与还原](../backup-and-restore/)。

## 三种部署形态

| 形态 | 控制面、Function Runtime 与 Worker | 持久化 |
| --- | --- | --- |
| **Docker Compose · 单机推荐** | 一台 Linux、macOS 或 Windows 主机运行控制面与 `ankole-function-runtime`，控制面通过 Docker socket 为每个 Agent 创建一个 Worker 容器 | PostgreSQL 18+（及配置的 `BASE_DB_URLS` 分片库）、对象存储与每个 Agent 的独享持久 Home 卷 |
| **Kubernetes · 企业级推荐** | Helm 部署运行控制面与 `ankole-function-runtime` Deployment，控制面通过 Kubernetes API 为每个 Agent 创建一个 Worker Pod | PostgreSQL 18+ 与物理 Base 分片数据库、对象存储与持久 Home PVC 或共享存储；缓存卷独立 |
| **源码安装** | `bun run services:start` 启动 PostgreSQL 18 与 `ankole-function-runtime`；`bun dev` 运行控制面，并以 watch 模式为每个 Agent 创建 Docker Worker 容器 | PostgreSQL 18、`var/ankole-dev/files` 与独享 Docker 持久 Home 卷 |

三种部署方式使用相同的逻辑边界。每个实例包含一个控制面，由控制面为每个 Agent 提供自己的 Worker。完整步骤见 [快速开始](../quickstart/#1-部署-ankole)。

## 支撑运行时的五项技术选择

| 机制 | 作用 |
| --- | --- |
| **Virtual Actor 承载 AI 工作** | 让每个会话拥有地址、信箱、生命周期和恢复点 |
| **OTP 监督树划分故障域** | 让一个 Agent 或连接失败时只恢复对应分支 |
| **Phoenix Channel 承载实时控制** | 在 Agent 执行期间低延迟传递唤醒、插话、进度和背压 |
| **Agent Computer Worker 提供执行环境** | 为每个 Agent 提供自己的电脑，运行工具、文件、终端、浏览器与 Codex |
| **PostgreSQL 保存权威状态** | 让消息、任务、记忆、决策和已提交操作可以恢复与审计 |

Agent 可以连续工作数小时，并在运行中接收新信息。运行时可以独立恢复失败的执行分支，并为每项已提交的工作保留审计记录。

更完整的运行时论证见 <a href="https://ding.ee/zh-Hans-CN/why-otp-is-a-better-runtime-for-multi-agent-orchestration/" target="_blank" rel="noreferrer">《为什么 OTP 是更好的多智能体编排运行时》</a>。
