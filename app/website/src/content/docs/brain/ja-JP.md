Brain は GBrain に着想を得た長期記憶システムであり、Palantir 型のオントロジーにもとづいて組織の「現在の世界モデル」を維持します。日々の会話、ファイル、Web ページに含まれる中長期的に有用な情報を、出所（provenance）まで追跡できる構造化された組織知識として整理し、明確な開示境界のもとで Agent が想起・修正・忘却できるようにします。

Brain は、増え続けるチャットログをそのまま記憶として溜め込む仕組みではありません。人物、組織、出来事、意思決定、およびそれらの関係性について「いま何が成り立っているか」という最新の見取り図を保ち続けます。新しい事実や証拠が入ってくれば既存の Claim（主張）を補強・修正・更新でき、食い違いが見つかった場合も、根拠となった証拠と変更前の状態が人間から確認できる形で保全されます。

同一の Ankole テナントに属するすべての Agent は、同じ知識空間を共有します（Agent ごとに別々のデータベースを複製する方式ではありません）。そのうえで記憶ごとに個別の開示範囲（audience）が設定されるため、同じ基盤を共有していても情報が無制限に公開されることはありません。

## Brain が学習できる情報

Brain が知識を取り込む経路は次の 3 つです。

| 経路 | 結果 | 前提条件 |
| --- | --- | --- |
| Agent が `remember` を呼び出す | 1 件の事実または判断がその場で永続記憶として保存される | Agent が原子的な 1 つの Claim、出所、有効な開示範囲を指定すること |
| Signals 学習が会話を処理する | 明示的に `remember` を呼ばなくても、長期的に有用な事実・判断・未完了の約束が自動抽出される | 対象チャネルがダイレクトメッセージまたは IM グループであり、Brain メンテナンス Agent に利用可能な `light` プロファイルがあること（グループ学習では同期済みのメンバー権限グループも必要） |
| 運用者が Source を登録する | ファイルや Web ページが検索可能になり、そこから Claim も自動抽出される | Claim 抽出にはメンテナンス Agent の `light` プロファイルが必要。ファイルはデプロイ環境から読み取り可能で、ファイルおよび取得したページ本文が 10 MiB 以下の有効な UTF-8 テキストであること（URL の場合はさらに `web_fetch` プロファイルが必要） |

Signals 学習は、対象のチャネルが一定時間アイドル状態になるか、関連する会話が終了したタイミングで、未処理のメッセージをまとめて処理します。このとき読み取られるのはチャネルに保存された会話メッセージであり、Agent 内部の非公開なモデル思考履歴ではありません。ダイレクトメッセージから抽出された知識の既定の開示範囲は「対話相手本人」、グループ会話から抽出された知識の既定の開示範囲は「そのチャネルに対応するメンバー権限グループ」となります。

Agent による `remember` 呼び出しが成功した時点で、その記憶の書き込みは確定します。たとえ同じターンの後続処理がエラーになったり、キャンセルやリトライが発生したりしても、一度確定した記憶は取り消されません。

運用者が登録する各 Source にも既定の開示範囲を設定します。業務上その情報を必要とするメンバーに届く範囲のうち、最も狭いスコープを指定してください。なお、Source をアーカイブすると以降の追加学習は止まりますが、すでに抽出・保存された知識自体は削除されません。

## Brain が知識を表す方法

Brain では、問いの性質に応じて複数の形式で知識を表現します。

- **ページ（Page）**: 人物、企業、出来事、プロジェクト、文書、概念など、1 つの対象についての現在の全体像をまとめた説明です。
- **Fact**: 検証や更新が可能な 1 つの客観的な観察事実です。確信度、時点、出所、保持者（holder）、開示範囲を持ちます。
- **Take**: 人間、Agent、または Brain 自身が持つ見解、予測、仮説、判断です。重みを持ち、後から実際の結果に照らして採点・確定できます。
- **Timeline**: ある対象に関して「いつ・何が起きたか」を時系列で記録します。
- **Link**: 2 つのページ間の関係性を記録します。

ここで `holder` とは「その Claim を主張・保持している人物または Agent」を指し、文の主語（対象）とは異なります。たとえば「Alex がある取引先について納期面に不安があると述べた」という場合、この Take の `holder` は取引先ではなく Alex になります。

1 つの Claim には、単独で真偽や状態が変化し得る最小単位の主張を 1 つだけ含めます。Brain はすべての Claim の出所を記録するとともに、ページの過去バージョンや置き換えられた古い Claim も履歴として残します。知識を修正すると「現在の見取り図」は更新されますが、そこに至るまでの変遷が消えることはありません。

## Agent が記憶を使う方法

Brain は、通常の会話の中で自動的に関連知識を補います。まず会話の開始時とコンテキスト圧縮の直後に、会話の参加者、最近話題に上った対象、重要な現在の Fact、および未完了の約束事をまとめたサイズ上限付きのコンテキストパックを組み立てます。さらに毎回のテキストターンでも、新着メッセージ内に登場した固有名詞などに一致するページを Agent に提示できます。

これらの自動注入処理では推論モデルを呼び出さず、もしタイムアウトやエラーが発生した場合は空の結果を返してターンをそのまま続行します。なお、注入された記憶はあくまで参考用の背景情報であり、Agent への命令ではありません（情報が古くなっていたり一部欠けていたりする可能性もあります）。

作業の中で明示的に記憶を検索・更新したい場合、Agent は次のツールを呼び出せます。

| ツール | 動作内容 |
| --- | --- |
| `learn_source` | Web URL を 1 件 Source として登録し、バックグラウンドで取り込みを開始する |
| `recall` | トークン上限の範囲内で、まず現在の Fact と Take を返し、続けて関連ページの断片を返す |
| `get_page` | slug または自然言語の名称から、開示範囲でフィルタ済みのページ全文を読み取る（名称が曖昧な場合は推測せず候補一覧を返す） |
| `entity` | 主要な Fact、関係性、被リンク数を含む対象サマリーカードを返す |
| `whoknows` | 閲覧可能な知識の範囲から、特定のテーマに詳しい人物・Agent・企業をランク付けして返す |
| `delta` | 指定した期間内に追加または失効した Claim と Timeline イベントを抽出する |
| `synthesize` | 想起した根拠にもとづき、特定の問いに答える永続的な分析ページを作成する |
| `forget` | 理由を記録したうえで、Fact の失効、Take の非アクティブ化、またはページの論理削除を行う |

### Brain からだけ想起する Skill を発見する

同梱 Skill の中には、関連する業務にあたるときだけ参照すればよい専門的な SOP や調査手法も含まれています。そうした Skill に `brain-recall-only: true` が指定されていると、毎ターンのプロンプト内にある Skill カタログからは省かれ、必要なときに Brain 検索を通じて見つけられるようになります。

この場合、Brain 側には Skill の `name`・`description`・`tags` だけが `lazyload-agent-skills/<skill-name>` という `world` スコープの発見用レコードとしてインデックスされます。Skill の本文や付属ファイル、Agent 固有の教訓は元の保存先に残ったままであり、実際の読み込みは `skill_view` を通じて行われます。`recall` でこのレコードが見つかったら、Agent は `skill_view` を呼び出します。ローダーは `ankole-runtime` の宣言に従い、現在の実行環境と互換性があれば手順本文を返し、メイン Agent がバックグラウンド専用の Skill を開こうとした場合は Job へ委任するための案内を返し、それ以外の非互換な読み取りは拒否します（この発見用レコードに対して `get_page` を呼んだ場合も、内部で `skill_view` に委譲されて同じ結果が返ります）。

また、Brain は検索候補を返す前に、その Agent における Agent Plugin と Skill の現在の実効有効化状態を確認します。そのため、無効化されている Skill は検索結果にも現れず、読み込むこともできません。一方でテナント共有の発見用投影レコード自体は削除されないため、後から再び有効化すれば再インデックスなしですぐに利用できます。

検索時には、Embedding モデルが設定されていれば全文検索とベクトル検索の候補が組み合わされ、Rerank モデルが設定されていれば統合後の候補がさらに再順位付けされます。Embedding モデルが未設定でも全文検索単独で動作し、Rerank モデルが未設定の場合はスコア統合後の順序がそのまま使われます。

## 知識境界と開示境界

保護対象のページ本文セクション、Fact、Take、および Timeline イベントには、それぞれ次のいずれかの開示範囲が設定されます。

| 範囲 | 取得を許可される Principal |
| --- | --- |
| `world` | テナント内の有効な人間メンバー（`membership = member`）、有効な Agent、およびシステム Principal（`membership = guest` の外部ゲストおよび無効化済みの Principal は除外） |
| `group:<name>` | 該当する権限グループに現在所属しているメンバー |
| `principal:<uid>` | 指定された単一の Principal のみ |

権限グループへの所属判定は、知識の読み書きを行うその都度、最新の所属状態にもとづいて評価されます。そのため、人事異動などでメンバーの所属グループが変わった場合も、既存の記憶レコードを書き換えることなく次回以降の検索結果へ即座に反映されます。

自分が作成した Claim や Timeline イベントは作成者自身が取得できます。また、Agent の所有者は、その Agent 専用の非公開スコープの記憶や、その Agent が作成・保持する知識を監査できます。ただし「Agent の所有者である」というだけでは、その Agent が参加しているグループの共有知識までは閲覧できません（閲覧するには所有者自身もそのグループに所属している必要があります）。

さらにグループ会話では、応答時に 2 段階目の開示チェックが行われます。

- **Strict（既定値）**: チェック対象となる会話参加者全員が閲覧権限を持っている場合に限り、グループ範囲の記憶を開示します。
- **Relaxed**: 質問者本人の権限だけを確認し、同席している他の参加者によって結果が絞り込まれることはありません。

ダイレクトメッセージでは、どちらのモードでも同じ動作になります。

なお、Source や Channel の記録はあくまで「その知識がどこから得られたか」という出所を示すものであり、そこから学習された知識へのアクセス権を付与するものではありません。閲覧可否は常に知識アイテム自体に設定された開示範囲で決まります。ページの slug、タイトル、種別、およびページが存在すること自体はテナント内で共有されますが、保護された本文セクションや構造化 Claim は開示範囲に応じて切り詰められます。

Agent が自ら `remember` を呼び出す際は、`ConfidentialityPolicy.md` の指針に従って開示範囲を選択します。ただし、この範囲選択自体はモデルによるベストエフォートの判断であるため、誤分類の可能性はゼロではありません。選択された範囲のアクセス制御はシステムが決定論的に強制しますが、分類自体の妥当性までを自動保証するものではない点に留意してください。厳格なコンプライアンス分離が求められる領域では、記憶の分類だけに頼るのではなく、[Principal と権限グループ](../principal-and-groups/)によって Agent にアクセスできる利用者自体を制限してください。

## 知識を現在に保つ方法

Dreaming は、モデルの推論を伴う定期的な知識メンテナンス処理です。主に次の作業を行います。

- 互いに関連する複数の Fact から、Brain 自身が保持する慎重な仮説・見解（Take）を導き出す。
- 複数のページにまたがる傾向やパターンを見つけ、根拠への Link を備えた分析記事を書く。
- エンティティ間の関係性や Timeline イベントを抽出する。
- 評価期限を迎えた過去の Take を実際の結果と照らし合わせて採点し、予測精度（キャリブレーション）の集計を更新する。
- 既存の知識との間に潜む矛盾候補を検出する。

矛盾候補を見つけた場合でも、Dreaming が独断で片方を消したり既存の Claim を密かに書き換えたりすることはありません。検出内容を記録として残し、人間が Console 上で確認して解決または却下できるようにします。

また、各 Fact は知識の種類と経過時間に応じて検索ランキング上の重みが少しずつ減衰していきます。ただし、この減衰によって保存済みの確信度や履歴が書き換わることはありません。現在の有効状態そのものが変わるのは、明示的に忘却（`forget`）を実行したときだけです（Fact は失効、Take は非アクティブ化、ページは論理削除となります）。論理削除されたページは、設定された完全消去期限が来るまでいつでも復元でき、失効・置換された Claim も監査およびキャリブレーション履歴として残ります。

これとは別に、Self-healing タスクが検索用のインデックス投影を健全に保ちます。古くなったチャンクや Embedding の再生成、検索インデックスの整合性確認、未学習チャネルの検出などを推論モデルを使わずに実行します。

## Console で Brain を管理する

Console の **Brain** セクションでは、蓄積された知識空間を用途別のビューで確認・操作できます。

- **Objects**: ページ一覧、表示本文、Fact、Timeline、Link、バージョン履歴の確認と、ロールバック・削除・復元を行えます。
- **Claims**: Fact と Take の出所や現在の状態を確認し、内容の修正、忘却、採点確定を実行できます。
- **Contradictions**: 人間による確認待ちの矛盾候補が一覧表示されます。
- **Sources**: ファイルや URL の新規登録、取り込み開始、アーカイブを行えます。
- **Search preview**: 特定の Principal と開示モードを指定して、実際にどのような記憶が想起されるかをテストできます。
- **Principal audit**: 特定の Principal が holder・作成者・閲覧対象になっている知識を横断的に一覧表示します。
- **Health**: 各モデルの準備状態、学習キューの滞留、Embedding の失敗、チャネル側の前提条件、インデックス投影の健全性を確認できます。

テナント単位の Brain 設定ではメンテナンス担当 Agent と Rerank モデルを指定し、サイト単位の設定では Embedding モデルとその次元数を指定します。Brain が行うすべてのモデル呼び出しは、ここで指定されたメンテナンス Agent の ID で実行され、トークン使用量もその Agent に計上されます。そのため、メンテナンス Agent は常に有効な状態に保ってください。もし無効化されると、Brain はヘルス異常を報告し、再有効化または別 Agent への切り替えが行われるまでモデル呼び出しと URL Source の取り込みをすべて停止します（その間も、保存済みの知識の参照と全文検索は引き続き利用可能です）。

| 設定箇所 | 有効になる機能 |
| --- | --- |
| メンテナンス Agent の `light` プロファイル | Signals 学習および Source からの Claim 抽出 |
| メンテナンス Agent の `heavy` プロファイル | モデル推論を使う Dreaming 処理および `synthesize` |
| メンテナンス Agent の `web_fetch` プロファイル | URL Source からの本文抽出（未設定の場合、URL Source は学習されない） |
| Brain の Embedding モデル | ベクトル検索および Fact の意味的な重複判定 |
| Brain の Rerank モデル | 全文検索とベクトル検索を統合した後の再順位付け |

任意のモデルが未設定の場合は、該当する機能だけが制限されます。裏で曖昧に縮退することはなく、どの機能が停止しているかは **Health** ページに明示されます。Brain 自体を無効化すると、記憶ツールと自動コンテキスト注入がオフになりバックグラウンド処理も停止しますが、すでに保存されている知識データはそのまま保全されます。

なお、すべてのテナントには基本語彙を定義する `general` Schema Pack が標準で含まれています。さらに初期設定や設定画面から、プライベートエクイティ／ベンチャーキャピタル、公開市場、コンシューマービジネス、法務、ソフトウェア、コンサルティング向けの専門 Schema Pack を追加することもでき、導入した語彙はテナント内の全 Agent で共有されます。

## 現在の対応範囲

現時点で Brain が会話のやり取りを自動学習できるチャネルは、ダイレクトメッセージと IM グループのみです。また、登録可能な Source はファイルと URL に限られており、外部コネクタ、Webhook、アラートストリームから直接自動学習することはできません。

Brain はあくまで根拠付きの知識を整理・保管するシステムであり、記録された内容の完全性や無謬性を自動的に保証するものではありません。重要な業務判断に用いる際は、出所、記録時点、確信度、holder、および矛盾候補の有無をあわせて確認してください。

システム全体における Brain の位置づけについては[アーキテクチャ](../architecture/)を、実行時パラメータについては [AppConfigure](../app-configuration/) を、そして実際の作業経験から手順上のガードレールを学ぶ仕組みについては [Skill Lessons](../skill-lessons/) を参照してください。
